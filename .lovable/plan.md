
# پلن: ویژگی‌های عمومی پویا با انواع مقدار

## وضعیت فعلی

تب «ویژگی‌های عمومی» الان ۵ نوع **ثابت کدشده** دارد: برند، دسته‌بندی، رنگ، ظرفیت، مدل. مدیر فقط می‌تواند **مقادیر** درون این انواع ثابت را اضافه/غیرفعال کند و نمی‌تواند:
- نوع جدید بسازد (مثلاً «جنس»، «گارانتی»، «وزن»)
- تعیین کند که هر نوع، **کشویی** است یا **متنی آزاد** یا **عددی**
- عنوان فارسی نوع را ویرایش کند

جدول `product_attributes` فقط ستون‌های `id, type(enum), name, is_active` دارد و enum محدود است.

## هدف

مدیر بتواند **گروه‌های ویژگی عمومی** بسازد، عنوان فارسی‌شان را ویرایش کند، و برای هر گروه مشخص کند که نوع ورودی‌اش **کشویی / متنی / عددی** است.

## طراحی

### ۱. جدول جدید: `product_attribute_groups`

```text
id              uuid pk
key             text unique         -- شناسهٔ ماشینی (color, capacity, ...)
label_fa        text not null       -- عنوان فارسی قابل ویرایش
value_type      text not null       -- 'select' | 'text' | 'number'
is_active       boolean default true
is_system       boolean default false  -- برای brand/category که قابل حذف نیستند
sort_order      int default 0
created_at, updated_at, created_by
```

- RLS: مشاهده برای کاربران مجاز محصولات؛ نوشتن فقط با `products.update`.
- Seed: ردیف‌های موجود enum (color/capacity/model = select، brand/category = select+system) به‌صورت idempotent درج می‌شوند.

### ۲. تطبیق جدول `product_attributes`

افزودن ستون `group_id uuid references product_attribute_groups(id)` (nullable در ابتدا، سپس backfill بر اساس ستون `type` فعلی، سپس not null). ستون `type` فعلی برای سازگاری عقب‌رو نگه داشته می‌شود (در migration بعدی حذف می‌شود).

> برای گروه‌های `select` ردیف‌های مقادیر در `product_attributes` ذخیره می‌شوند. برای `text` و `number` نیازی به ردیف مقدار نیست — مقدار آزاد در فرم محصول ثبت می‌شود.

### ۳. تب «ویژگی‌های عمومی» — UI جدید

ساختار جدید:

```text
[ + گروه ویژگی جدید ]    [ جستجو ]   [ فیلتر نوع ]

┌─ کارت گروه: «رنگ» (کشویی)        [ویرایش عنوان] [غیرفعال] ─┐
│  مقادیر:  سفید · سیلور · مشکی · ...           [+ افزودن]   │
│  هر مقدار: [ویرایش] [Switch فعال]                          │
└────────────────────────────────────────────────────────────┘

┌─ کارت گروه: «گارانتی» (متنی)     [ویرایش عنوان] [غیرفعال] ─┐
│  این گروه مقدار آزاد می‌گیرد — نیازی به تعریف مقادیر نیست. │
└────────────────────────────────────────────────────────────┘

┌─ کارت گروه: «وزن (کیلوگرم)» (عددی) [ویرایش] [غیرفعال] ────┐
│  این گروه مقدار عددی می‌گیرد.                              │
└────────────────────────────────────────────────────────────┘
```

**دیالوگ گروه جدید / ویرایش گروه:**
- عنوان فارسی (label_fa)
- شناسه (key) — فقط هنگام ساخت، خودکار از label تولید می‌شود
- نوع مقدار: `کشویی` / `متنی` / `عددی`
- وضعیت فعال

**دیالوگ مقدار (فقط برای گروه‌های select):**
- نام مقدار + وضعیت فعال

برای گروه‌های `is_system = true` (برند/دسته‌بندی): فقط ویرایش عنوان فارسی مجاز است؛ تغییر نوع مقدار و حذف ممنوع.

### ۴. هماهنگی با فرم محصول (ProductForm)

- برای هر گروه فعال، یک فیلد در فرم نمایش داده می‌شود:
  - `select` → کامبوباکس از مقادیر فعال آن گروه
  - `text`   → Input متنی
  - `number` → Input عددی
- مقادیر در همان جدول `product_attribute_values` (موجود) با ارجاع به گروه ذخیره می‌شوند.
- برای حفظ سازگاری: گروه‌های قدیمی (color/capacity/model/brand/category) دقیقاً مثل قبل کار می‌کنند.

### ۵. تأثیر بر «ساخت نام خودکار» و «ویژگی‌های اختصاصی دسته‌بندی»

- ماژول name-template از key گروه استفاده می‌کند (همان keyهای فعلی حفظ می‌شوند) → بدون شکست.
- تب «ویژگی‌های اختصاصی دسته‌بندی» جداگانه است و دست نمی‌خورد.

## مراحل اجرا

1. **Migration**:
   - ساخت جدول `product_attribute_groups` + RLS + indexها
   - Seed پنج گروه موجود به‌صورت idempotent با key‌های `brand, category, color, capacity, model`
   - افزودن `group_id` به `product_attributes`، backfill از `type`، سپس not null
   - افزودن trigger `updated_at`
2. **لایهٔ داده** (`src/lib/products/attributes.ts` جدید):
   - `fetchAttributeGroups()`, `createGroup()`, `updateGroup()`, `toggleGroup()`
   - `fetchAttributeValues(groupId)`, CRUD مقادیر
3. **بازنویسی تب «ویژگی‌های عمومی»** در `_app.products.attributes.tsx`:
   - حذف enum hardcoded `AttrType`
   - رندر بر اساس گروه‌های پویا
   - دیالوگ گروه + دیالوگ مقدار
4. **به‌روزرسانی ProductForm** برای رندر فیلد بر اساس `value_type` گروه.
5. **Audit log** برای ساخت/ویرایش/فعال/غیرفعال گروه.

## معیارهای پذیرش

- مدیر می‌تواند گروه ویژگی جدید با نوع کشویی/متنی/عددی بسازد.
- مدیر می‌تواند عنوان فارسی هر گروه (شامل برند/دسته‌بندی) را ویرایش کند.
- مدیر می‌تواند گروه را غیرفعال کند (داده حذف نمی‌شود).
- فرم محصول بر اساس نوع گروه، فیلد مناسب نشان می‌دهد.
- محصولات قدیمی همچنان نمایش داده می‌شوند و قابل ویرایش‌اند.
- RLS فعال؛ فقط `products.update` حق نوشتن دارد؛ audit log ثبت می‌شود.
- migration reversible و idempotent است.

## ریسک‌ها

- **سازگاری عقب‌رو**: کدهایی که از enum `type` استفاده می‌کنند (در `category-attrs.ts`, `name-template.ts`, `ProductForm`) باید با key گروه کار کنند. چون keyها همان‌نام enum انتخاب می‌شوند، تغییر حداقلی است.
- **حجم تغییرات UI**: تب فعلی ~۲۹۰ خط بازنویسی می‌شود ولی منطق کارت‌بندی و dialog مشابه می‌ماند.
