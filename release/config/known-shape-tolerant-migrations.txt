# known-shape-tolerant-migrations.txt — versions pre-declared as safe to survive a "missing
# object" error during rehearsal replay, without aborting the whole run.
#
# Format: <14-digit version>|<substring that must appear in the captured mig_apply output>
# Comment lines start with #. Consumed by release/lib/shape-tolerance.sh via
# release/rehearse.ps1 -ShapeTolerant <this file>.
#
# WHAT THIS FILE IS FOR
#   release/lib/rehearse-engine.sh's replay loop normally treats ANY non-zero mig_apply exit as
#   fatal (mig_apply's own --single-transaction guarantee already rolled the migration back, so
#   nothing is left half-applied -- but by default the whole rehearsal still stops, because most
#   replay failures ARE real bugs). Naming a version here, with the EXACT error substring it is
#   expected to raise on a shape lacking the object it alters, tells the engine "this specific
#   failure is understood and explained -- record it as a finding, write no ledger row for it,
#   and continue" instead of aborting.
#
# NOTHING IS TOLERATED BY DEFAULT. An empty file (as shipped) changes no behaviour at all: every
# mig_apply failure still stops the rehearsal, exactly as before this file existed. A version only
# becomes tolerated when a human adds a line here AND the live error text matches it exactly --
# see release/lib/shape-tolerance.sh's own header for why both conditions are required.
#
# CLAUDE.md rule 6 still applies: nothing here authorizes editing an old migration file. If a
# version below turns out to fail this way on production's ACTUAL shape (not just some rehearsal
# restore), the fix is a NEW forward migration that hardens the old one's logic (catalogue-driven,
# same pattern as migrations 523/524/525 and E-2's hardened 531,
# supabase/migrations/20260913095000_531_*.sql on branch feature/conv-db-fixes commit b77622f6) --
# never editing the file this list points at.
#
# HOW THIS LIST WAS BUILT (E-4, 2026-09-13) -- MEASURED, NEVER SPECULATIVE
#   This file shipped EMPTY. Both entries below were added only after a real rehearsal replay
#   against prod_rehearsal_e4b raised the error, and the exact text was copied from that run's
#   own captured output -- not predicted from reading the files.
#
#   The occurrence (release/runs/e4b/02-replay-0001-0008.md, first attempt):
#
#     === apply 20260818150000_336_drop_dead_receipt_posting_path.sql (version 20260818150000) ===
#     SET
#     psql:/tmp/mig_20260818150000.sql:35: ERROR:  wrong database: prod_rehearsal_e4b (expected afrakala)
#     CONTEXT:  PL/pgSQL function inline_code_block line 4 at RAISE
#     *** APPLY FAILED: ... exit 3 -- transaction rolled back, ledger NOT written ***
#
#   Migrations 336 and 343 each open with, verbatim:
#
#       DO $guard$
#       BEGIN
#         IF current_database() <> 'afrakala' THEN
#           RAISE EXCEPTION 'wrong database: % (expected afrakala)', current_database();
#         END IF;
#       END
#       $guard$;
#
#   This is NOT a rehearsal artefact. **Production's database is named `postgres`**, not
#   `afrakala` (CLAUDE.md's working-environments table). So these two files abort on production
#   too, and always did -- 527's and 528's own headers record that they already did, and that
#   NONE of 343's objects were ever created there as a result. It is the same defect class as
#   migration 477: logic written against one shape and asserted against another.
#
#   They are tolerated here rather than applied because their work is already re-issued, guard
#   removed, by FORWARD migrations in this very release:
#       336 -> 527  (20260913091000_527_drop_dead_receipt_posting_path_no_guard.sql)
#       343 -> 528  (20260913092000_528_posted_entry_immutability_no_guard.sql)
#   Both 527 and 528 are in the same apply plan and DO run. So tolerating 336/343 loses no work:
#   the effect still lands, via the file that can actually execute. Neither old file is edited
#   (CLAUDE.md rule 6), and neither gets a ledger row from this rehearsal.
#
#   The substring is '(expected afrakala)' rather than the whole line on purpose: the full text
#   embeds the scratch database's name, which differs on every run and on production. Matching
#   the guard's own expectation is stable and still pins the match to this exact guard.
#
#   CONSEQUENCE FOR THE RELEASE DOCUMENT: both versions are reported SHAPE_TOLERATED, and
#   release/emit-blocks.ps1 emits a "HUMAN REVIEW REQUIRED" block for each -- never an automatic
#   mig_apply. A human confirms on the real target before anything is done with them.

20260818150000|(expected afrakala)
