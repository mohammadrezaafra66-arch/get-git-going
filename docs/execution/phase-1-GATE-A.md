Database: `afrakala` on `afrakala-lan-db` (test computer). Production was never contacted.
Method: read-only. Every write shown below ran inside `BEGIN … ROLLBACK` and was verified reverted.

**Verdict: FAIL**

The phase is well built and unusually well documented, and most of it holds up under attack. It fails
Gate A on one defect and one defect only: **migration 341 broke all three functions that currently
write to the ledger, and the phase recorded the opposite.** Three shipped, user-facing features are
dead on the test database as of this review. Nothing in phase 1 can close while that is true.

Seven further defects are graded MAJOR — none of them blocks phase 1's own tasks, but each one is
load-bearing for phase 2, 3 or 4 and is cheaper to fix now than after an RPC is written on top of it.

## What I could not verify

- **Idempotency of `assign_document_number` under genuine concurrency for the same `source_id`.** Proving it requires one transaction to commit while another waits on the advisory lock; committing is a write and outside this review's authority. My reasoning is that it holds at READ COMMITTED — the post-lock re-read takes a fresh snapshot and sees the committed row — and that at REPEATABLE READ the loser hits `UNIQUE (doc_type, source_id)` and aborts loudly rather than duplicating. Neither is measured. See m2.
- **Whether B1 reproduces through the browser.** I proved it at the SQL boundary with a real `post_receipt_accounting` call. Clicking the button on `/accounting/receipts/<id>` is a human step and is listed as such.
- **Production.** Not contacted, by instruction. Whether production's ledger writers differ from test is Q5 in ground-truth and remains `UNKNOWN`; B1's fix must be re-verified there before phase 9.
- **The 70-error typecheck baseline.** I did not re-run `tsc`; phase 1 changed only SQL, and the Lead's recorded 70/70 is consistent with D14.
- **Whether `document_attachments` orphans matter commercially.** The table holds 0 rows today. M4 is graded on the mechanism, not on present damage.

## Judgement on the Lead's raised gates (OG-8 .. OG-13)

**OG-8 — may `trg_post_receipt_on_approve()` also be dropped?**
The Lead was right to refuse and escalate. OG-2 named two objects; dropping a third would have exceeded written authorisation, and the Observer's "it is dead code" is true but not urgent. I verified independently that it is inert: it cannot be called directly (`0A000`), no trigger references it, and its definition is captured in the progress file so the drop is recoverable. **Endorsed. Low priority.** The only residual concern is m6 — its body references a function that no longer exists, so it fails rather than no-ops if anyone re-attaches it.

**OG-9 — should the serial reset each Jalali year?**
Correctly identified as an accountant's convention rather than a technical choice, and correctly resolved by mirroring `asan_assign_document_number` as the checklist instructed. **Endorsed.** One point the Lead did not make, which strengthens the case for asking: because the serial is global and the year is only a label, `RCP-1405-000042` → `RCP-1406-000043` is not merely unusual, it makes the year in the number carry no information the serial does not already carry. That is worth putting to the owner in those terms.

**OG-10 — can an own cheque be issued to an external party, not only a supplier?**
Real, correctly raised, correctly *not* pre-empted (widening the validator on speculation would be the worse error). **Endorsed — but incomplete.** The identical question exists on the receipt side and lands a phase earlier: see M6. Ask both halves together.

**OG-11 — remove `post_receipt_accounting`'s back-fill branch, or let it edit a posted entry?**
The Lead's reading of the function is accurate and the decision not to grant an exemption is correct — an exemption would be a hole in the guarantee task 1.6 exists to create. **Endorsed on the merits.** But the surrounding claim is wrong, and that is B1: while OG-11 was being carefully documented as a partial-failure edge case, the function's *primary* branch had already been broken by migration 341 two files earlier. The gate is right; the risk assessment around it is not.

**OG-12 — is `ledger-documents` the right module string?**
Well reasoned, and the warning attached to it is the important part: an unseeded module is open, so whatever string phase 6's wizard registers must be seeded before the wizard ships. **Endorsed, and I would raise its priority** — this is the kind of item that is trivially cheap to answer now and becomes a live default-open permission hole the moment phase 6 lands with a different string.

**OG-13 — should `manager` get `can_view` to match its RLS SELECT?**
Correctly spotted, but framed too narrowly as a cosmetic mismatch between two mechanisms. It is not cosmetic: `manager` currently passes the spec's canonical role gate and the attachments INSERT policy, yet is refused by `assign_document_number` with `42501` — a mid-transaction failure waiting for phase 2. **Endorsed and escalated to MAJOR (M3).** Answer it as one question covering all four surfaces, before phase 2 writes `create_receipt`.

## Closing note

Nine migrations, all atomic, all idempotent, all with a down file that actually runs, every
`SECURITY DEFINER` function carrying `search_path`, zero tables without RLS, a Jalali conversion that
agrees with the front end's library on 513 dates including every Nowruz boundary for seventy years,
and a numbering scheme whose race backstop fires loudly rather than silently. The engineering here is
better than most of what this repository has seen, and the self-reported reviewer dialogue caught two
real defects before they shipped.

It still fails, for a reason worth naming precisely. The phase repeatedly verified *the thing it had
just built* and did not sweep *what already depended on the thing it had just changed*. Migration 341
correctly reasoned that a `DEFAULT` on `doc_kind` would hide a future omission — and then made the
column mandatory without asking which existing writers omit it. All three do. The same shape produced
M1 (the grant was checked, the granularity was not), M2 (the new tables' RLS was asserted, the spec's
other two rows were not), and M4 (write-time integrity was built, delete-time was not).

Fix B1 first; it is a one-migration change and three live features are down until it lands.

— Supervising Engineer (مهندس ناظر), 2026-08-18
