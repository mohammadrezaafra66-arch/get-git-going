## ۲ — قوانین سراسری (رعایت اجباری در تمام فازها)

**استقلال، با سه مرز روشن برای توقف**
مستقل و بدون وقفه کار کن — منتظر حضور من نمان — **مگر** به یکی از این‌ها برسی:
(الف) عملیات DELETE/DROP روی داده‌ای که در این فایل به‌صراحت مجاز نشده،
(ب) داده‌ی مالی با مبلغ واقعی غیرصفر،
(ج) ابهامی که نتیجه‌اش اگر اشتباه باشد جبران‌ناپذیر است.
در این سه حالت متوقف شو و بپرس. در غیر این صورت، اگر چیزی مبهم بود: اول در کد و
دیتابیس زنده تحقیق کن؛ اگر باز هم روشن نشد، امن‌ترین فرض را انتخاب کن، ادامه بده، و آن
را با دلیلش در بخش Assumptions گزارش نهایی ثبت کن.

**هماهنگی چندعامله (حیاتی — ۶ عامل دیگر هم‌زمان روی همین branch کار می‌کنند)**
- قبل از هر commit و قبل از انتخاب هر شماره‌ی migration: `git pull --rebase origin feature/navigation-modernization`.
- شماره‌ی migration را **لحظه‌ی نوشتن** با `ls supabase/migrations | tail -5` بگیر، هرگز از قبل حدس نزن.
- اگر push به‌خاطر non-fast-forward رد شد: rebase کن و شماره‌ی migration را دوباره چک کن (شاید عامل دیگری همان شماره را گرفته)، سپس push کن. **force-push ممنوع.**

**قوانین SQL و پایگاه‌داده (Mission Control پروژه)**
- SQL فارسی هرگز از پایپ PowerShell عبور نکند — همیشه `docker cp` سپس `psql -f` داخل کانتینر.
- قبل از بازنویسی هر تابع: `pg_get_functiondef` بگیر، در `docs/verification/pre-<NNN>/` snapshot کن.
- هر migration: dry-run داخل `BEGIN ... ROLLBACK` اول، `--single-transaction -v ON_ERROR_STOP=1` برای اجرای واقعی، و یک `docs/verification/<NNN>-down.sql` منطبق.
- بعد از هر migration: `docker restart afrakala-lan-rest`.
- دیتابیس زنده `afrakala` روی `afrakala-lan-db` است (نه `postgres`). owner: `supabase_admin`.
- schema را کشف کن، حدس نزن — همیشه از `information_schema` بخوان.

**حذف/تغییر = یادداشت، نه سکوت**
هیچ‌وقت چیزی را بی‌سروصدا حذف نکن. هر حذف باید یک کامنت یا یک خط در گزارش داشته باشد که
بگوید: چه بود، چرا حذف شد، چه تاریخی، و اگر لازم شد چطور برگردانده می‌شود.

**کیفیت**
- کد و convention موجود را بخوان، از همان استفاده کن.
- fake data / mock / جعل‌کردن pass تست ممنوع. تست شکسته را با دلیل رفع کن، با ضعیف‌کردن assertion نه.
- خروجی ترمینال فقط انگلیسی (حتی هنگام توصیف رشته‌های فارسی) — فارسی فقط داخل فایل‌هایی که می‌نویسی.

## ۳ — فازها با جزئیات

### فاز ۱ — seed کردن role_permissions

ممیزی امروز ثابت کرد این ماژول‌ها **صفر ردیف** در `role_permissions` دارند:
`accounting`, `bank`, `customers`, `cheques`, `hr`, `market-rates`.

نتیجه: `has_dynamic_permission` به fallback قدیمی می‌افتد (دسترسی گسترده به `view` برای
اکثر نقش‌ها) — یک حفره‌ی امنیتی، نه فقط یک نقص UX.

1. برای هر یک از ۶ ماژول، الگوی ماژول‌های مشابه و کامل (مثلاً `sales`, `warehouse`) را
   بخوان تا ببینی چطور نقش‌ها به `view/create/update/delete` نگاشت می‌شوند.
2. برای هر ماژول، بر اساس route guardهای واقعی که همین امروز کشف شدند (مثلاً
   `/accounting/bank-accounts` با `requireAnyRole(["admin","manager","accountant"])`)
   یک نگاشت منطقی بساز — یعنی ردیف‌های `role_permissions` باید با آنچه route واقعاً
   اجازه می‌دهد **بخوانند**، نه برعکس (مگر دلیل روشنی برای عکسش داری، که در این صورت
   Assumption بنویس).
3. یک migration بساز که این ردیف‌ها را INSERT کند.
4. تست: برای هر ماژول، با JWT واقعی هر نقش، `has_dynamic_permission` را صدا بزن و
   مطمئن شو دیگر به fallback نمی‌افتد.

### فاز ۲ — یکپارچگی ارجاع‌های چندریختی

`stock_movements.ref_id` و `journal_lines.account_ref_id` هیچ‌کدام FK ندارند (به‌خاطر
چندریختی بودن — یک ستون می‌تواند به چند جدول متفاوت اشاره کند). این دقیقاً همان الگویی
بود که مهاجرت ۳۰۴ را شکست.

1. برای هر ستون، تمام مقادیر واقعی `ref_type`/`account_ref_type` (یا معادلش) را زنده
   لیست کن.
2. برای هر مقدار، جدول مقصد واقعی را پیدا کن.
3. یک تابع یا تریگر اعتبارسنجی بساز که هنگام INSERT/UPDATE، بر اساس نوع ارجاع، وجود
   ردیف مقصد را چک کند (نه FK واقعی، چون چندریختی است، ولی معادل عملکردی‌اش).
4. یک کوئری تشخیصی هم بنویس که ارجاع‌های یتیم موجود (اگر بودند) را گزارش دهد — پاک
   نکن، فقط گزارش بده، چون این خارج از scope این فاز است.
5. تست: یک ارجاع نامعتبر بساز، مطمئن شو رد می‌شود؛ یک معتبر بساز، مطمئن شو رد نمی‌شود.

### فاز ۳ — رفع شمارش ثابت در export-sales

`e2e/asan/export-sales.spec.ts:116` دارد `ASAN_PERSON_CODE_COUNT = 11` هاردکد شده.
هر بار کسی از کد آسان تازه استفاده کند (که الان واقعاً استفاده می‌شود)، این تست می‌شکند.

1. آن ثابت را با یک کوئری زنده جایگزین کن: `SELECT count(*) FROM person_identifiers WHERE kind='asan_person_code' AND status != 'revoked'` (یا معادل دقیقش — از قبل کشف کن، حدس نزن).
2. مطمئن شو تست بعد از این تغییر هم روی داده‌ی فعلی و هم بعد از افزودن یک کد جدید سبز می‌ماند.

### فاز ۴ — حذف یک ردیف تکراری امن (P0.2، فقط ۲۷۱d7c44)

طبق استثنای بالا، فقط `271d7c44` را پاک کن. قبل از پاک کردن:
1. زنده تأیید کن این ردیف هنوز صفر تراکنش دارد (خرید، فروش، رسید، دفتر).
2. یک migration با dependency-order مناسب بنویس، dry-run کن.
3. down-script بنویس.
4. اجرا کن، `docker restart afrakala-lan-rest`.

### فاز ۵ — حذف دو فایل xlsx مرجع آسان

`docs/asan/reference/اشخاص.xlsx` و `کالا.xlsx` — طبق تصمیم مالک حذف شوند، ولی این دو
فایل fixture مستقیم دو تست e2e هستند: `import-persons.spec.ts:23` و
`import-products.spec.ts:28`.

1. آن دو فایل را از git حذف کن (`git rm`).
2. دو spec وابسته را باز کن. **آن‌ها را ساکت skip نکن.** یا:
   (الف) اگر بخش دیگری از آن spec بدون فایل هم معنا دارد، فقط قسمت وابسته به فایل را حذف کن و بقیه را نگه دار،
   (ب) اگر کل spec به فایل وابسته است، آن را با `test.skip` و یک کامنت واضح («فیکسچر xlsx طبق تصمیم مالک حذف شد، تاریخ X، اگر بازسازی import لازم شد این spec باید فیکسچر جدید بگیرد») نشان‌دار کن — silent skip ممنوع.
3. در گزارش نهایی صریح بنویس این دو spec دیگر پوشش کامل ندارند — این یک **پیامد
   شناخته‌شده و تأییدشده** است، نه یک regression پنهان.
