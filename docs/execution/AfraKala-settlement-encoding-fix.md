## B.1 — 🔴 روش اجرای UTF-8-safe (حیاتی — علت اصلی باگ همین بود)

**هرگز** متن فارسی را از طریق pipe در PowerShell به psql نفرست (`@"..."@ | psql`). دقیقاً همین کانال تک‌بایتی بود که ۵ ردیف را به `????` تبدیل کرد. به‌جایش:

1. فایل migration را با encoding **UTF-8** روی دیسک بنویس (مطمئن شو ادیتور/ابزار BOM اضافه نمی‌کند مگر لازم باشد؛ UTF-8 بدون BOM استاندارد است).
2. فایل را با `docker cp` به داخل کانتینر کپی کن.
3. psql را **از داخل کانتینر** روی فایلِ کپی‌شده اجرا کن، با `client_encoding=UTF8` صریح.

الگوی امن:
```powershell
$pw = (docker exec afrakala-lan-db printenv POSTGRES_PASSWORD).Trim()
docker cp "D:\AfraKalaTest\app\supabase\migrations\<FILE>.sql" afrakala-lan-db:/tmp/fix.sql
docker exec -e PGPASSWORD=$pw afrakala-lan-db psql -U supabase_admin -d afrakala -v ON_ERROR_STOP=1 -c "SET client_encoding='UTF8'" -f /tmp/fix.sql
```
> اگر `-c` و `-f` با هم مشکل داشت، `SET client_encoding='UTF8';` را به‌عنوان اولین خط **داخل خود فایل** بگذار و فقط با `-f /tmp/fix.sql` اجرا کن.

**قبل از اجرا، تأیید کن فایل روی دیسک سالم است** (نه `????`):
```powershell
Get-Content "D:\AfraKalaTest\app\supabase\migrations\<FILE>.sql" -Encoding UTF8 | Select-String "روزه|نقدی|چک"
```
اگر اینجا `????` دیدی، یعنی ابزار نوشتن فایل خودش خراب می‌کند — **متوقف شو و گزارش بده** (نباید ادامه بدهی وگرنه همان باگ تکرار می‌شود).

## B.2 — محتوای migration

یک فایل جدید بساز: `20260726<HHMMSS>_2<NN>_fix_payment_terms_encoding.sql` (شماره را از آخرین migration ادامه بده؛ محتوای پوشه را چک کن تا تکراری نشود).

منطق مورد نیاز:

1. **اول با `days` هماهنگ کن، نه با `name`** (چون `name` همان چیزی بود که خراب و تکراری شد). برای هر یک از پنج نوع، بر اساس `days` یکتا:
   - اگر ردیفی با آن `days` هست → `UPDATE` نامش به مقدار درست.
   - اگر نیست → `INSERT`.
   - این کار را idempotent با الگوی «UPDATE؛ اگر ردیف نخورد INSERT» یا `INSERT ... ON CONFLICT` روی کلید درست انجام بده.

2. **مشکل ریشه‌ای `UNIQUE(name)`:** بررسی کن آیا `days` می‌تواند/باید یکتا باشد. اگر constraint یکتا فقط روی `name` است و همین باعث حذف خاموش شد:
   - **گزینهٔ امن‌تر (بدون تغییر ساختار):** فقط مطمئن شو نام‌ها بعد از رفع یکتا هستند (که با نام‌های درستِ متفاوت، خودبه‌خود یکتا می‌شوند). این کافی است تا مشکل برطرف بماند.
   - **اگر خواستی محکم‌تر شود:** می‌توانی یک `UNIQUE(days)` هم اضافه کنی تا در آینده دو ردیف با یک `days` ساخته نشود — **ولی فقط اگر** داده فعلی اجازه دهد (هیچ `days` تکراری نباشد). قبل از افزودن constraint، تکراری‌نبودن را چک کن؛ اگر تکراری بود، **متوقف شو و گزارش بده** (ریسک شکست constraint).

3. **ساختار درست هر ردیف** (مطابق جدول هدف بخش A):

   | days | sort_order | name |
   |---|---|---|
   | 0 | 1 | نقدی |
   | 30 | 2 | تسویه ۳۰ روزه |
   | 60 | 3 | تسویه ۶۰ روزه |
   | 90 | 4 | تسویه ۹۰ روزه |
   | 45 | 5 | چک ۴۵ روزه |

   - از ستون‌های واقعی جدول استفاده کن (اول `\d public.payment_terms` را بخوان تا نام دقیق ستون‌ها — `days`, `sort_order`, `is_active`, ... — و ستون‌های NOT NULL را بدانی).
   - ارقام داخل نام‌ها را **فارسی** بنویس (۳۰/۶۰/۹۰/۴۵) تا با بقیهٔ UI یکدست باشد — دقیقاً مثل فایل migration اصلی سالم.

4. **کل migration در یک `BEGIN; ... COMMIT;`** با `ON_ERROR_STOP=1`.

## B.3 — اصلاح جانبی: گارد نبودِ `/admin/payment-terms`

تحقیق نشان داد route `admin/payment-terms` برخلاف بقیهٔ `/admin/*` گارد `beforeLoad` ندارد. (نشتی نوشتن نیست چون RLS هست، ولی برای یکدستی.)
- فایل route را پیدا کن (`rg -n "createFileRoute" src/routes | rg -i "payment-terms"`).
- الگوی گارد را از یک route همسایهٔ `/admin/*` کپی کن (مثلاً همان `requireAdmin()`/`requireAnyRole([...])` که بقیهٔ `admin/*` دارند) و به `beforeLoad` این route اضافه کن.
- **این تنها تغییر کد فرانت این بخش است**؛ build باید سبز بماند.

## B.4 — تست تأیید (بعد از اجرا)

```sql
SET client_encoding='UTF8';
-- هر ۵ ردیف با نام سالم فارسی
SELECT days, sort_order, name,
       char_length(name) AS chars, octet_length(name) AS bytes
FROM public.payment_terms
ORDER BY sort_order;
```
- **انتظار:** پنج ردیف (days = 0/30/60/90/45)، و برای ردیف‌های فارسی `bytes > chars` (اثبات اینکه بایت‌های فارسی سالم‌اند، نه `????`).
- **هیچ ردیفی نباید `char_length = octet_length` داشته باشد** به‌جز جایی که نام کاملاً ASCII است (که اینجا نداریم؛ همه فارسی‌اند).
- **هیچ `?` در هیچ نامی نباشد:**
  ```sql
  SELECT count(*) AS should_be_zero FROM public.payment_terms WHERE name LIKE '%?%';
  ```
- build فرانت سبز.
- **تأیید بصری (گزارش‌شده):** dropdown «زمان تسویه» در `/purchases/create` و `/accounting/purchase-payments` هر پنج گزینه را درست نشان دهد.
- **تأیید عدم تخریب:** سه خرید موجود هنوز نوع تسویهٔ درست را نشان دهند (رجوع با `payment_term_id`):
  ```sql
  SELECT p.id, p.payment_term_id, pt.name
  FROM public.purchases p LEFT JOIN public.payment_terms pt ON pt.id = p.payment_term_id
  ORDER BY p.created_at DESC LIMIT 5;
  ```

## B.6 — یادآوری‌های حیاتی

- **متن فارسی را هرگز از pipe در PowerShell عبور نده** — علت اصلی باگ همین بود. فقط `docker cp` + `-f`.
- **قبل از اجرا، سالم‌بودن فایل روی دیسک را چک کن** (B.1). اگر فایل `????` داشت، متوقف شو.
- **idempotent:** فرض کن ممکن است بخش A قبلاً داده را درست کرده باشد؛ migration نباید در آن حالت چیزی خراب کند.
- **constraint جدید فقط با تأیید داده:** اگر `UNIQUE(days)` اضافه می‌کنی، اول تکراری‌نبودن `days` را تأیید کن.
- دادهٔ موجود مقدس است: هیچ `DROP`/`TRUNCATE`.
