## ۲ — قوانین سراسری

**استقلال، با سه مرز توقف — در این مأموریت به‌خصوص جدی بگیر**
مستقل کار کن — **مگر**: (الف) هر DELETE/DROP فراتر از صریح این فایل، (ب) **هر
migration یا تست که مبلغ واقعی غیرصفر می‌نویسد یا می‌خواند از داده‌ی زنده** —
حتی در فاز dry-run، اگر متوجه شدی خروجی روی رکورد واقعی اثر می‌گذارد، متوقف شو،
(ج) ابهام جبران‌ناپذیر درباره‌ی جهت بدهکار/بستانکار یا منطق تسویه.

**هماهنگی چندعامله**
- `git pull --rebase origin feature/navigation-modernization` قبل از هر commit و قبل
  از هر انتخاب شماره‌ی migration.
- شماره‌ی migration را لحظه‌ی نوشتن با `ls supabase/migrations | tail -5` بگیر.
- non-fast-forward → rebase، دوباره تلاش. force-push ممنوع.

**قوانین SQL/پایگاه‌داده**
- SQL فارسی فقط `docker cp` + `psql -f`.
- `pg_get_functiondef` + snapshot قبل از بازنویسی هر تابع مالی — این‌ها حساس‌ترین
  توابع پروژه‌اند، سخت‌گیرانه‌تر عمل کن.
- dry-run در `BEGIN...ROLLBACK` برای **هر** migration، `--single-transaction`،
  down-script کامل و تست‌شده.
- `docker restart afrakala-lan-rest` بعد از هر migration.
- schema را کشف کن، هرگز حدس نزن.

**کیفیت**
جعل تست مطلقاً ممنوع، مخصوصاً در این مأموریت — تست جعلی روی منطق مالی یعنی باگ مالی
پنهان. خروجی ترمینال فقط انگلیسی.

## ۳ — فازها با جزئیات

### فاز ۱ — افزودن `supplier_payable`

مالک تأیید کرد: **فقط یک کشوی هفتم** اضافه شود، نه دو. `mutual_settlement` **یک
account_kind جداگانه نیست** — تسویه‌ی متقابل یک نوع سند است (چند خط ترکیبی)، نه یک نوع
حساب. این تمایز را در طراحی رعایت کن.

1. `journal_lines.account_kind` را با `pg_get_functiondef`/`information_schema` زنده
   بخوان — الان شش مقدار دارد: `customer_credit, bank, external_party, invoice_ar,
   clearing, other`.
2. یک migration بنویس: چون CHECK است نه enum، این یعنی DROP CONSTRAINT + ADD CONSTRAINT
   با هفت مقدار به‌جای شش — اتمیک و برگشت‌پذیر.
3. جهت حسابداری را دقیق مستند کن (این را در کامنت migration بنویس تا هیچ توسعه‌دهنده‌ی
   بعدی اشتباه نکند):
   - **بدهکار کردن `supplier_payable`** = کاهش بدهی ما به تأمین‌کننده (پرداخت کردیم)
   - **بستانکار کردن `supplier_payable`** = افزایش بدهی ما (خرید نسیه کردیم)
4. dry-run: یک سند آزمایشی بساز داخل `BEGIN...ROLLBACK` که یک خط `supplier_payable`
   دارد، مطمئن شو رد نمی‌شود. rollback کن.
5. down-script بنویس.

### فاز ۲ — تکمیل پرداخت شخص ثالث

سمت دریافت (`PaymentReceiptForm.tsx`) از قبل کامل است: انتخاب انحصاری بین «حساب بانکی
ما» و «طرف خارجی»، `receiver_party_id` با FK واقعی به `external_parties`،
`beneficiary_accounting_code` مستقل. **این الگو را عیناً کپی کن، نسازش از صفر.**

سمت پرداخت (`payment_vouchers` + صفحه‌ی `/accounting/purchase-payments`) ستون‌های لازم
را از قبل دارد (`payee_party_id` با FK به `external_parties`, `payee_name`,
`tracking_number`) ولی RPC پارامتر هویت گیرنده ندارد و صفحه هیچ‌کدام را نشان نمی‌دهد.

**زیرفاز ۲-الف — RPC:**
1. `pay_purchase_with_voucher` (یا نام دقیقش را زنده تأیید کن) را با `pg_get_functiondef`
   بخوان، snapshot بگیر.
2. امضایش را گسترش بده تا پارامترهای هویت گیرنده را بپذیرد — دقیقاً هم‌شکل با XOR سمت
   دریافت (یا حساب بانکی خودمان، یا یک `external_parties` id).
3. **مهم‌ترین رفع این فاز:** این تابع الان **هیچ سند دفتر نمی‌زند**. باید یک ثبت
   `journal_entries`/`journal_lines` بسازد: بدهکار `supplier_payable` (کاهش بدهی) +
   بستانکار `bank` (خروج نقد) — دو خط متوازن ساده. اگر گیرنده شخص ثالث بود، مثل سمت
   دریافت، `external_party` را هم به‌عنوان متادیتا (نه خط دفتر جداگانه، مگر منطق سمت
   دریافت خلاف این را نشان دهد — همان الگو را دنبال کن) ثبت کن.

**زیرفاز ۲-ب — فرم:**
1. صفحه‌ی `/accounting/purchase-payments` را باز کن، فیلدهای هویت گیرنده (حساب
   بانکی/شخص ثالث با همان XOR) و شماره‌ی پیگیری را طبق پترن `PaymentReceiptForm.tsx`
   اضافه کن.

**تست فاز ۲:** یک پرداخت آزمایشی داخل `BEGIN...ROLLBACK` بساز — حتماً rollback کن، مبلغ
واقعی هرگز commit نشود مگر مالک صریح تأیید کند. تأیید کن سند دفتر درست ساخته می‌شود و
متوازن است (`sum(debit) = sum(credit)`).

### فاز ۳ — صفحه‌ی تسویه‌ی متقابل

1. تابع `person_settlement_position(_person_id uuid)` بساز: `receivable` (جمع
   `customer_credit` تسویه‌نشده)، `payable` (جمع `supplier_payable` تسویه‌نشده)، `net`،
   `direction` (`customer_pays`/`we_pay`/`balanced`). `SECURITY DEFINER`، فقط
   admin/accountant.
2. صفحه‌ی `/accounting/mutual-settlement`: لیست اشخاص دو‌نقشی (کسانی که هم `customer`
   هم `supplier` context link دارند — اگر عامل `p1-dual-role` هنوز تمام نشده، ممکن است
   فقط یک نمونه‌ی واقعی موجود باشد؛ `git pull --rebase` بزن و ببین وضعیتش چیست، طبیعی
   است اگر این لیست فعلاً کوتاه است).
3. فرم تسویه: جهت (خودکار پر می‌شود، قابل ویرایش)، مبلغ (خودکار `|net|`، قابل ویرایش
   برای تسویه‌ی جزئی)، نقد/بانک، یادداشت.
4. ثبت: یک سند متوازن با `source_type='mutual_settlement'` — بدهکار طرف بدهکار،
   بستانکار طرف بستانکار، به‌علاوه‌ی خط نقد/بانک برای تفاوت اگر بود (طبق مثال واقعی
   امروز، گاهی هیچ تفاوتی نیست و نیازی به خط نقد نیست).
5. بعد از ثبت: `receivable` و `payable` هر دو باید صفر یا کاهش‌یافته شوند.

**تست فاز ۳ (فقط داخل rollback، مبلغ واقعی هرگز commit نشود بدون تأیید صریح مالک):**
یک شخص دو‌نقشی آزمایشی با receivable=۱۰ و payable=۸ بساز، تسویه کن، تأیید کن سند
متوازن است و مانده‌ها درست به‌روز می‌شوند.

### فاز ۴ — غنی‌سازی ستون شرح (P4، گسترش‌یافته)

طراحی اصلی P4 (که قبلاً آماده شده بود): `asan_list_journal_export` را با
`payment_receipts` جوین بده تا شرح شامل نام پرداخت‌کننده، شماره‌ی پیگیری، و هدف باشد —
با COALESCE مرحله‌ای (کامل → متوسط → fallback به شرح موجود → هرگز خالی).

**گسترش لازم امروز:** این تابع باید سندهای منبع‌گرفته از `payment_vouchers` (فاز ۲) و
`mutual_settlement` (فاز ۳) را هم پوشش دهد — نه فقط `payment_receipts`. فیش‌های قدیمی
(قبل از این مأموریت) دست نخورند؛ روی آن‌ها یک نشان «شرح ساده» نشان بده (طبق طراحی قبلی).
