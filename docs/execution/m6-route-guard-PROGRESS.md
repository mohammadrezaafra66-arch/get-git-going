### ۰.۱ — هر دو مسیر fail-open، در متن زندهٔ `src/lib/rbac/route-guards.ts`

```ts
async function resolveAuthWithRetry() {
  if (typeof window === "undefined") return null;      // ← مسیر ۱ (SSR)
  let auth = await ensureAuthReady();
  if (!auth.user && (auth.loading || !auth.initialized)) auth = await ensureAuthReady(true);
  return auth;
}

export async function requireAnyRole(allowed: readonly AppRole[]) {
  const auth = await resolveAuthWithRetry();
  if (!auth) return { user: null, roles: [] as AppRole[] };   // ← مسیر ۱ بدون throw برمی‌گردد
  const user = auth.user;
  if (!user) { … throw redirect({ to: "/login" }); }
  if (auth.rolesLoading || auth.profileLoading || auth.loading)
    return { user, roles: auth.roles };                        // ← مسیر ۲، باز هم بدون throw
  if (auth.rolesError) throw new Error(`بارگذاری نقش‌های کاربر ناموفق بود: ${auth.rolesError}`);
  const roles = auth.roles as AppRole[];
  if (!roles.some((r) => allowed.includes(r))) throw redirect({ to: "/unauthorized" });
  return { user, roles };
}
```

`requirePermission` (خط ۲۲ و ۳۲) و `requireAdmin` (خط ۵۰ و ۵۷) **دقیقاً همین دو خط را
دارند**. هر سه نگهبان، هر دو مسیر. ادعای سند مأموریت تأیید شد.

و مسیر ۱ عمدی است، نه سهو: کامنت خطوط ۶۵–۷۶ می‌گوید فاز ۶.۷ سه مسیر را که
`ensureAuthReady` را دستی صدا می‌زدند اصلاح کرد، چون کاربرِ واردشده را در هر ناوبری
سمت‌سرور به `/login` پرت می‌کردند. **این همان تلهٔ «با deny در SSR درستش کن» است که سند
مأموریت هشدارش را می‌دهد، و در همین مخزن یک بار افتاده‌اند.**

## بازبینی مستقل — دور ۱ از ۲ — حکم PASS با هشت یافته

بازبین نقص را مستقل بازتولید کرد (۱۳/۱۳ رد برای `sales`، ۲۶/۲۶ بدون قفل‌شدن برای
`admin`/`accountant`) و چیزی پیدا کرد که من ندیده بودم: **پوشش حسابداری کامل‌تر از آن است که
فکر می‌کردم** — سه مسیر قدیمی `_app.accounting.*capital*` صرفاً به `dynamic-capital` هدایت
می‌کنند و روی یک مسیر گیت‌دار می‌نشینند، پس هر ۱۷ فایل مسیر حسابداری پوشیده‌اند نه ۱۴.

### آنچه اصلاح شد

**F-1 (MEDIUM) — دروازه شکست‌پذیر بود.** فهرست سیزده مسیر دستی بود، پس مسیری که نگهبان
صدا می‌زند ولی `staticData` ندارد fail-open است و هر ۱۷ ادعا سبز می‌ماند. بازبین این را
روی مسیرهای **موجود** نشان داد: `sales` همین حالا `/admin/audit` و `/admin/documents` را
کامل می‌بیند. فهرست حالا از `src/routes/` **مشتق** می‌شود و یک بررسی ایستا ادعا می‌کند هر
مسیر حسابداری گیت‌دار `staticData`ی دارد که فهرست نقشش با `requireAnyRole` خودش برابر است.

هر دو حفره پیش از اعتماد روی دروازهٔ تعمیرشده بازتولید شد:

```
حذف staticData از treasury  → «calls a route guard but carries no staticData.gate —
                                RouteRoleGate cannot see it and this route is fail-open»
افزودن viewer به فهرستش      → «staticData.gate.allowed disagrees with requireAnyRole —
                                one of the two silently widens or narrows access»
```

**F-2 (LOW/MED) — بُعد `manager`/`viewer` نامرئی بود.** هیچ آزمون رفتاری روی این سرور
نمی‌تواند ببیندش، چون هر دو کاربر `status=rejected`اند و لایهٔ `_app` پیش از هر نگهبانی
هدایتشان می‌کند (OG-36). مقایسهٔ سطح-منبع بالا آن را می‌بیند — همان اختلال `viewer`.

**F-3 (LOW) — دو آزمون ۱۳بارگذاری در ۵۵ تا ۱۰۰٪ بودجهٔ ۴۵ ثانیه‌ای می‌دویدند** و بازبین
دو بار قرمزشان دید. به آزمون تک‌مسیره شکسته شدند. **۱۷ ادعا شد ۵۹، هر ۵۹ سبز.**

**F-5 (LOW) — شاخهٔ `permission` حذف شد، نه اصلاح.** `requirePermission` پیش از

می‌کند آینه‌اش است واگرا می‌شود. هیچ مسیری امروز از آن استفاده نمی‌کند، پس فرستادنش یعنی
یک شاخهٔ آزمایش‌نشده که به شکلی غلط است که هیچ چیز اینجا نمی‌بیندش — **همان شکلی که همین

### ادعایی از خودم که پس می‌گیرم

**تشخیص router-context را بیش از شواهدش محکم گفته بودم، و بازبین درست گفت.** نوشته بودم
«مقدار بازگشتی `beforeLoad` از SSR به کلاینت منتقل نمی‌شود». این برنامه router را با
context ریشهٔ خالی می‌سازد (`src/router.tsx`: `context: {}`) و **هیچ مسیری در مخزن چیزی از
`beforeLoad` برنمی‌گرداند**، پس `ctxKeys: []` روی هر سه match — از جمله `__root__` — به
همان اندازه با «این برنامه اصلاً context تنظیم نکرده» توضیح داده می‌شود.

آنچه واقعاً ثابت شده باریک‌تر و کافی است: مکانیزم ساخته شد، مستقر شد، و مشاهده شد که هیچ
چیز را عوض نمی‌کند؛ و حالتی که اهمیت دارد دقیقاً بارگذاری سرد است، جایی که کلاینت هنگام
hydration `beforeLoad` مسیر اولیه را دوباره اجرا نمی‌کند. **نتیجه سرجایش است؛ توضیحش
بیش‌ازحد محکم بود.** کامنت `RouteRoleGate` اصلاح شد.
