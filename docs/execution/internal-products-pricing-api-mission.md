## ۲ — قوانین سراسری

**استقلال، با سه مرز توقف**
مستقل کار کن — **مگر**: (الف) DELETE/DROP روی هر چیزی خارج از آنچه این فایل می‌سازد،
(ب) داده‌ی مالی واقعی لمس شود (این مأموریت فقط باید بخواند، نه بنویسد — اگر جایی نیاز به
نوشتن پیدا شد، متوقف شو)، (ج) ابهام جبران‌ناپذیر درباره‌ی طراحی امنیتی.

**قبل از ساختن، بررسی کن از قبل چیزی نیست**
طبق الگوی همیشگی این پروژه («ساخته شد ولی وصل نشد» یا برعکس، «دوباره ساخته شد»): اول بگرد
ببین آیا از قبل یک view، RPC، یا مسیر مشابه برای خواندن قیمت محصولات وجود دارد که فقط
وصل/مستند نشده — قبل از ساخت چیز تازه.

**قوانین SQL/پایگاه‌داده**
- SQL فارسی فقط `docker cp` + `psql -f`، هرگز پایپ.
- schema را کشف کن، حدس نزن — این پروژه چند نوع قیمت مختلف دارد (خرید، فروش نقدی/چکی/همکاری،
  کف قیمت، قیمت سریع، لیست‌های قیمت) و دقیق نمی‌دانیم کدام‌ها زنده و کدام‌ها یتیم‌اند.
- dry-run در `BEGIN...ROLLBACK`، `--single-transaction`، down-script.
- `docker restart afrakala-lan-rest` بعد از هر migration.
- خروجی ترمینال فقط انگلیسی؛ فارسی فقط داخل فایل‌های مستندات.

## ۳ — فازها با جزئیات

### فاز ۱ — کشف کامل «قیمت» در این پروژه

قبل از طراحی هر چیزی:

1. هر جدول و ستونی که به قیمت محصول مربوط است را زنده لیست کن —
   `information_schema.columns` روی هر جدولی که اسمش شامل `price`, `pricing`, `cost` است.
2. برای هر کدام، تشخیص بده: زنده و پرداده است، یا خالی/یتیم؟ (شمارش ردیف زنده بگیر)
3. مشخص کن آیا قیمت‌ها ثابت هستند یا وابسته به زمان/نرخ ارز (چون این پروژه نرخ دلار و
   بازار را هم دنبال می‌کند — چک کن آیا این مرتبط است).
4. یک جدول خلاصه در گزارش نهایی بگذار: هر نوع قیمت، جدول مبدأ، تعداد ردیف، آیا برای این
   API لازم است.

### فاز ۲ — طراحی شکل خروجی

1. بر اساس فاز ۱، یک یا چند **view فقط‌خواندنی** طراحی کن که محصول را با همه‌ی انواع قیمت
   مرتبطش (که در فاز ۱ زنده تشخیص دادی) در یک شکل تمیز و قابل‌فهم ترکیب کند.
2. اگر منطق محاسباتی‌ای برای بعضی قیمت‌ها از قبل در یک تابع وجود دارد (مثلاً محاسبه‌ی
   کف قیمت)، از همان تابع استفاده کن — دوباره‌اش را ننویس.
3. طرح را قبل از ساخت واقعی، به‌صورت خلاصه در گزارش میانی بنویس.

### فاز ۳ — امنیت و دسترسی

این بخش حساس‌ترین قسمت است — دقیق باش:

1. یک **نقش تازه‌ی Postgres** بساز، مخصوص همین API (مثلاً `products_api_readonly`) — کاملاً
   جدا از نقش‌های موجود اپ (`admin`, `sales`, و غیره).
2. این نقش فقط اجازه‌ی `SELECT` روی view(های) فاز ۲ داشته باشد — هیچ دسترسی دیگری، نه به
   جدول‌های خام، نه به هیچ چیز دیگر.
3. یک RLS policy مناسب بنویس اگر view از جدولی می‌آید که RLS دارد.
4. بررسی کن این پروژه (Supabase self-hosted با Kong) چطور credential/API key صادر می‌کند —
   زنده بخوان، حدس نزن. یک credential اختصاصی برای این نقش تولید/مستند کن (نه استفاده از
   کلید admin عمومی سیستم).
5. تأیید کن این credential **فقط** به این view دسترسی دارد — یک تست زنده بزن: با این
   credential سعی کن جدول دیگری را بخوانی، باید رد شود.

### فاز ۴ — فعال‌سازی و تست واقعی

1. Migration ها را اعمال کن (با dry-run و down-script طبق قانون همیشگی).
2. `docker restart afrakala-lan-rest`.
3. یک درخواست واقعی از **بیرون** (مثل یک `curl` جدا، شبیه‌سازی یک اسکریپت خارجی) با
   credential تازه بزن — تأیید کن داده‌ی واقعی و درست برمی‌گردد.
4. یک درخواست **بدون** credential یا با credential اشتباه بزن — تأیید کن رد می‌شود.
5. سرعت/حجم پاسخ را برای یک درخواست معمولی گزارش کن (فقط برای اطلاع، محدودیت نرخ لازم
   نیست چون استفاده شخصی و کم‌حجم است).
