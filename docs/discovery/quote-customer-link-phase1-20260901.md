## بند ۳ — منطق فعلی اتصال، و پنج اثرش

`src/routes/_app.sales.quotes.new.tsx:166-172` — کامنت بالایش نشان می‌دهد این **عمدی** بوده:

```ts
// MONEY-SAFETY: keep the customer link only while the name and phone still match…
const linkedCustomerId = useMemo(() => {
  if (!selectedCustomer) return null;
  const nameMatches  = selectedCustomer.name.trim() === customerName.trim();
  const phoneMatches = selectedCustomer.phone.replace(/\D/g,"") === customerPhone.replace(/\D/g,"");
  return nameMatches && phoneMatches ? selectedCustomer.id : null;
}, [selectedCustomer, customerName, customerPhone]);
```

## بند ۸ — تشخیص، و چهار جا که طرح فاز ۲ با واقعیت نمی‌خواند

### تشخیص

قاعدهٔ `166-172` برای محافظت از پول نوشته شده، ولی چیزی که واقعاً می‌کند این است: چون سرور اصلاً
تطابق نمی‌خواهد و ۵۹٪ مشتریان شماره ندارند، **مقایسه در اکثر موارد یک رشتهٔ تایپ‌شده را با رشتهٔ
خالی می‌سنجد** و اتصال را می‌شکند. بعد سرور آن سند بی‌اتصال را رد می‌کند مگر با پرچم
`accounting_approval`. نتیجه: فروش عادی از درِ تأیید حسابداری رد می‌شود و سابقهٔ حسابرسی چیزی را ثبت
می‌کند که رخ نداده.

### 🔴 چهار تعارض که باید شما تصمیم بگیرید — من جایگزین انتخاب نکردم

**۱. گام ۲-۴ می‌گوید «`p_customer_id` الزامی شود».** ولی سرور **از قبل** الزامش می‌کند، مگر از راه
`accounting_approval`. و `NOT NULL` کردن ستون روی **۳ ردیف موجود** می‌شکند که **۲تایشان سندهای مهمانِ
عامدانه و تأییدشدهٔ حسابداری‌اند** (۲۸ و ۳۱ اوت، وضعیت accepted). یعنی این گام یا از قبل انجام شده،
یا اگر به‌شکل `NOT NULL` پیاده شود دادهٔ مشروع را می‌شکند.

**۲. گام ۲-۴ می‌گوید «نام و شماره از رکورد مشتری خوانده شود».** ولی **۵۱ از ۸۶ مشتری شماره ندارند** و
تابع بررسی حضور شماره دارد. اگر شماره از رکورد خوانده شود، برای ۵۹٪ مشتریان خالی می‌آید و ثبت
**غیرممکن** می‌شود. خودتان در گام ۲-۲ این را پیش‌بینی کرده‌اید («وگرنه فروش قفل می‌شود») — این سند
فقط عدد دقیقش را می‌دهد: **۵۹٪، نه چند مورد.**

**۳. گام ۲-۳ می‌گوید فرم اشخاص را هم بگردد.** ولی جست‌وجوی اشخاص برای کاربر فروش **کمتر** نشان
می‌دهد (۱۸ در برابر ۷۳ مشتری)، پس هدفِ «شخص هست، مشتری نیست» را برآورده نمی‌کند مگر آن ۵۶ لینک
context پر شوند — و آن کار **دید فروش را چهاربرابر می‌کند** و کامنت `person_create_inline` صریحاً
ردش کرده. این یک تصمیم حریم خصوصی است، نه یک جزئیات پیاده‌سازی.

**۴. گام ۲-۷ می‌گوید شمارهٔ مشتری از موبایل شخص پر شود.** ولی **هیچ‌کدام از آن ۵۱ مشتری بی‌شماره،
شناسهٔ موبایل هم ندارند.** اسکریپت پرکردن، منبعی برای خواندن ندارد. این گام روی دادهٔ فعلی
**بی‌اثر** است.

### 🟡 یک ناهمخوانی که هنوز حل نشده

۵۷ از ۶۰ پیش‌فاکتور متصل، بعد از backfill نوشته شده‌اند، ولی **۵۲تایشان شماره‌ای دارند که از قاعدهٔ
UI رد نمی‌شد.** یعنی یا مسیر دیگری هم `customer_id` می‌نویسد، یا داده بعداً عوض شده. **قبل از
فاز ۲ باید روشن شود** — وگرنه نمی‌دانیم قاعده واقعاً چقدر اثر داشته.

### تغییراتی که مایگریشن می‌خواهند (و آن‌هایی که نمی‌خواهند)

| تغییر | مایگریشن؟ |
|---|---|

### ریسک‌ها

1. **قفل‌شدن فروش** اگر ۲-۴ بدون ۲-۲ برود — ۵۹٪ مشتریان.
2. **باز شدن دید فروش** اگر لینک‌های context برای جست‌وجوی اشخاص پر شوند.
3. **شکستن ۳ سند موجود** اگر `customer_id` به `NOT NULL` تبدیل شود.
4. **پاک شدن هم‌زمان `customer_person_id`** — تریگر و CHECK آن را با `customer_id` قفل کرده‌اند.
5. **ارقام فارسی** — نرمال‌ساز کلاینت و دیتابیس یکی نیستند.

### و منشأ آن ۴ سند قدیمی — و ریشهٔ خودِ قاعده

`supabase/migrations/20260723170000_147_link_sales_quotes_to_customers.sql` (۲۳ ژوئیه، **یک روز

```sql
ON regexp_replace(COALESCE(c.phone,''),'\D','','g')
 = regexp_replace(COALESCE(sq.customer_phone,''),'\D','','g')
AND btrim(c.name) = btrim(sq.customer_name)
HAVING count(*) = 1
```

# `guest_no_link` چه چیزی را حل می‌کند و چه چیزی را نه — ۲۰۲۶-۰۹-۰۳

**هدف `guest_no_link` این است که قطع اتصال دیگر زیر عنوان دروغینِ `accounting_approval` ثبت نشود.**
امروز تنها راهِ ثبت یک پیش‌فاکتور بدون پرونده، فرستادن `accounting_approval` است — تابع زنده در
شاخهٔ `p_customer_id IS NULL` هر مقدار دیگری را رد می‌کند. یعنی سندی که هیچ‌کس از حسابداری تأییدش
نکرده، در دیتابیس «تأیید حسابداری» ثبت می‌شود. اندازه‌گیری: از ۱۸ سند `accounting_approval`،
**۲** واقعاً مهمان بوده‌اند (`credit_check_snapshot->>'mode' = 'guest_accounting_approval'`).

**آنچه `guest_no_link` حل نمی‌کند: اجباری‌بودن شمارهٔ تماس.** این یک نقص نیست، یک تصمیم است:

- مراجع حضوری شماره **دارد**؛ کارشناس دستی واردش می‌کند. آنچه ندارد پروندهٔ ثبت‌شده است.
- اجباری‌بودن شماره در هر دو لایه سرِ جای خود می‌ماند و **شل نمی‌شود**:
  `src/lib/sales/quotes.ts:98` و ستون `sales_quotes.customer_phone` که `NOT NULL` است.
- مشکلِ جدا و واقعیِ «مشتری **ثبت‌شده** که شماره ندارد» با دکمهٔ «افزودن شماره به پرونده» حل شده
  است، نه با مسیر مهمان.

> پس `guest_no_link` راهِ فرار از شماره نیست. اگر روزی کسی با این تصور به آن دست زد، این بند
> پاسخ است.
