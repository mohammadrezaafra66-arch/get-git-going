# Corrupted Persian text — full scan, classification and repair

Produced by ASAN mission M1, phase 1.1.

## How the corruption works, and why the repair is provable

The 2026-07-11 PowerShell-pipe incident did not garble the text randomly. It replaced
**every UTF-8 byte** of every non-ASCII character with a literal `?`, and left ASCII
untouched. So `سطح` (3 characters, 6 bytes) became `??????`, and `ثبت‌شده` — which
contains a 3-byte ZWNJ — became a 15-character run, not 14.

That makes recovery a proof rather than a guess. Define
`mask(s)` = each non-ASCII character replaced by one `?` per UTF-8 byte, ASCII kept.
A candidate string is the original **iff** `mask(candidate)` equals the stored value
byte for byte. Every repair in this phase satisfies that identity against a string still
present in `supabase/migrations/` or `src/`. Nothing was reworded or invented.

Where one masked value had several candidates, the row was pinned by anchors that must
appear near the candidate in the source: the row's own `key`/`code`, sibling columns of
the same row already recovered, and whether the candidate is a whole quoted literal
rather than a slice of a longer one. 86 multi-column rows were then re-checked to confirm
all their recovered columns come from the same source record.

## The `dynamic_table_cells` finding

266 of the 702 findings are label cells in the product price observatory. They were not
corrupted individually: the function that writes them,
`sync_product_price_observatory_rows()`, joins product labels with `string_agg`, and its
**separator literal** had been corrupted from `'، '` (U+060C + space) to `'?? '`. A diff of
the live `pg_get_functiondef` against migration `20260516161314` shows that separator is
the only difference between the live function and the repo. Migration 279 repairs the
function first and then rewrites the 266 cells it had already produced. Verified before
writing: every `?` in that table belongs to that separator, and no other column is affected.
