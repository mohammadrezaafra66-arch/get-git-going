# دروازهٔ قیمت سمت سرور، و بدهیِ تستِ skip‌شده

۲۰۲۶-۰۹-۰۳ · اندازه‌گیری روی پایگاه دادهٔ **تست**. production لمس نشد.
**هیچ‌کدام از این دو بخش پیاده‌سازی نشده؛ هر دو منتظر تصمیم مالک‌اند.**

---

## بخش ۱ — واقعیت محصول: دروازهٔ قیمت فقط جایی فعال است که کف تعریف شده باشد

**این یک باگ نیست، یک واقعیت است که باید ثبت شود، و تصمیم دربارهٔ آن با مالک است. بخشی از این
انتشار نیست.**

تابع `create_sales_quote_with_items` قیمت زیر کف را رد می‌کند:

```sql
IF _floor IS NOT NULL AND _effective < _floor THEN
  IF NOT COALESCE(p_below_list_ack, false) THEN
    RAISE EXCEPTION 'قیمت وارد شده برای «%» از کف مجاز تسویهٔ % (%) کمتر است.' …
```

نکته در `_floor IS NOT NULL` است. `_floor` از `product_computed_prices` می‌آید و به **سه‌تایی**
(محصول، نوع قیمت، نوع تسویه) گره خورده است. **اگر برای آن سه‌تایی ردیفی نباشد، `_floor` تهی است و
شرط اصلاً اجرا نمی‌شود — یعنی هر قیمتی، حتی ۱ تومان، پذیرفته می‌شود.**

اندازه‌گیری روی تست: **۸۶۴** سه‌تایی کف دارند. تعداد کل سه‌تایی‌های ممکن بسیار بیشتر است، پس سهم
پوشش‌داده‌نشده معلوم نیست و اینجا ادعا نمی‌شود.

**چرا اهمیت دارد:** «کف قیمت» به‌نظر یک قاعدهٔ سراسری می‌آید، ولی در عمل یک قاعدهٔ **نقطه‌ای** است.
فروشندهٔ خوش‌نیت هم می‌تواند روی محصولی که کف ندارد زیر قیمت بفروشد بی‌آنکه هیچ هشداری ببیند —
نه کلاینت می‌سنجدش (هیچ بررسی کفی سمت کلاینت نیست) نه سرور، چون داده‌ای برای سنجیدن نیست.

**گزینه‌های ممکن — هیچ‌کدام انتخاب نشده:**

| گزینه | کار | ریسک |
|---|---|---|
| بستنِ پیش‌فرض | نبودِ کف = رد کردن | فروش را روی هر محصولی که هنوز قیمت‌گذاری نشده متوقف می‌کند |
| هشدار بدون رد | نبودِ کف = پیام، نه بن‌بست | همان چیزی است که امروز نیست؛ کم‌ریسک ولی قابل نادیده‌گرفتن |
| پر کردن داده | کف برای همهٔ سه‌تایی‌های فعال تعریف شود | کار انسانیِ قیمت‌گذاری، نه کار فنی |
| رها کردن آگاهانه | همین رفتار، ولی مستند | تصمیم است، نه غفلت — که هدف همین سند است |

## بخش ۲ — بدهی: تست «رد سرور» نباید برای همیشه skip بماند

**وضعیت امروز:** `e2e/security/og95-…spec.ts` تست «a server refusal is recorded» را فقط با
`QT_ALLOW_SERVER_REFUSAL=1` اجرا می‌کند.

**چرا skip شد:** تنها ردی که کلاینت پیش‌دستی نمی‌کند، همان کف قیمت است. ولی تست از انتخابگر عبور
می‌کند و **نخستین نتیجه** را برمی‌دارد — یعنی سه‌تایی‌ای که به آن می‌رسد تصادفی است. وقتی آن
سه‌تایی کف نداشته باشد، ثبت **موفق** می‌شود و تست به‌جای اثبات یک رد، یک سند واقعی می‌سازد. این
دو بار رخ داد (SQ-2026-000239 و -000240).

### طرح قطعی‌کردن — پیاده نشده

**ایده:** تست نباید به شانس انتخابگر وابسته باشد. یک fixture سه‌تایی مشخص را تضمین کند.

**گام ۱ — کشف، نه ساخت.** پیش از هر چیز بسنجید که آیا سه‌تایی‌ای هست که هم کف دارد و هم از راه
رابط کاربری با یک جست‌وجوی مشخص قابل رسیدن است:

```sql
SELECT c.product_id, c.sale_price_type_id, c.settlement_type_id, c.rounded_sale_price
FROM product_computed_prices c
JOIN products p        ON p.id = c.product_id        AND p.is_active
JOIN settlement_types s ON s.id = c.settlement_type_id AND s.is_active
WHERE c.rounded_sale_price > 1000
LIMIT 5;
```

اگر هست، **هیچ fixture لازم نیست** — کافی است نام محصول و عنوان نوع قیمت و نوع تسویه از طریق
متغیر محیطی به تست داده شود و تست به‌جای «نخستین نتیجه»، همان‌ها را **با نام** انتخاب کند.

**گام ۲ — فقط اگر گام ۱ خالی بود:** یک fixture که در `beforeAll` یک ردیف `product_computed_prices`
برای یک محصول آزمایشی می‌سازد و در `afterAll` برش می‌دارد. **این یک نوشتن است** و باید جداگانه
تأیید شود؛ روی دیتابیس مشترک، fixtureای که پاک نشود بدتر از تست skip‌شده است.

**گام ۳ — انتخاب با نام، نه با ترتیب.** حتی با داده‌های درست، `getByRole("option").first()` شکننده
است. تست باید نوع قیمت و نوع تسویه را با متن دقیقشان انتخاب کند.

**گام ۴ — محافظ شمارش می‌ماند.** `beforeEach`/`afterEach` که شمار پیش‌فاکتور را می‌سنجد باید سر
جایش بماند، حتی وقتی تست قطعی شد. همان چیزی بود که دومین سند ناخواسته را گرفت.

**برآورد:** گام ۱ حدود نیم ساعت اندازه‌گیری. اگر جواب داد، گام ۳ حدود یک ساعت و بدون هیچ نوشتنی.
اگر گام ۲ لازم شد، نیم روز به‌علاوهٔ تأیید مالک برای نوشتن fixture.

**ریسکِ نپرداختن این بدهی:** مسیر `server_rpc` در ثبت ردها فقط یک بار، دستی، اثبات شده
(ردیف‌های `audit_logs` شمارهٔ ۶۰۳۳۳ و ۶۰۳۳۵). اگر روزی بشکند، هیچ تستی نمی‌گیردش.
