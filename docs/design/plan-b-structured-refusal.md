# راه‌حل ب — بازگرداندن نتیجهٔ ساخت‌یافته به‌جای `RAISE`

> **طرح است، نه کار. هیچ چیزی از این سند پیاده نشده و نباید بشود مگر با تأیید جداگانه.**

۲۰۲۶-۰۹-۰۳ · اندازه‌گیری‌ها روی پایگاه دادهٔ **تست**. production لمس نشد.

## مسئله در یک جمله

وقتی `create_sales_quote_with_items` رد می‌کند، `RAISE EXCEPTION` می‌زند؛ تراکنش برمی‌گردد؛ و هر
تلاشی برای ثبت آن رد **در همان تراکنش** با آن برمی‌گردد. برای همین امروز رد فقط از سمت کلاینت و
پس از واقعه ثبت می‌شود — با متن آزاد فارسی، بدون شناسهٔ سند، و **فقط اگر کاربر انتخاب کند**.

## آنچه سنجیده شد

- **۲۶ `RAISE EXCEPTION`** در تابع زنده. هیچ `EXCEPTION WHEN` ندارد و تنها **یک** `RETURN` دارد.
- تفکیک: **۲ مجوز** (`42501`)، **۱۷ اعتبارسنجی ورودی** (`22023`)، **۷ رد کسب‌وکاری** (`22023`)،
  **صفر** خطای یکپارچگی.
- **هر ۲۶ تا پیش از نخستین `INSERT` رخ می‌دهند.** یعنی یک شاخهٔ رد می‌تواند پیش از هر نوشتنی
  `RETURN` کند و چیزی برای بازگرداندن وجود ندارد.
- **صفر فراخوان درون‌دیتابیسی**: هیچ تریگر، ویو یا تابع دیگری آن را صدا نمی‌زند.
- **شش فراخوان بیرونی** در چهار فایل، به‌علاوهٔ نوع تولیدشده.
- PostgREST این دو را از هم تفکیک می‌کند و **اندازه‌گیری شد**: مسیر `RAISE` با `HTTP 401` و بدنهٔ
  `{"code":"42501",...}` برگشت؛ یک تابع دیگر که `jsonb` برمی‌گرداند با `HTTP 200` و خودِ مقدار.

## شکل خروجی — با پیشینهٔ درون‌خانگی

مخزن همین الگو را از قبل دارد: `public.validate_price_settlement_compatibility` نتیجهٔ ساخت‌یافته
برمی‌گرداند به‌جای `RAISE`، و ۹ تابع دیگر پوشش `jsonb_build_object('ok', true, …)` دارند.

```jsonc
// موفقیت — دقیقاً همان شکل امروزی، تا مصرف‌کننده‌های موجود نشکنند
{ "ok": true, "id": "…", "quote_number": "…" }

// رد کسب‌وکاری — تازه
{ "ok": false,
  "reason": "credit_ceiling_exceeded",   // کد ماشین‌خوان، پایدار
  "message": "…",                        // همان جملهٔ فارسی امروز، دست‌نخورده
  "refusal_id": "…" }                    // ردیف ثبت‌شدهٔ رد
```

`reason` همان چیزی است که «چند بار و چرا رد می‌شود» را **قابل پرس‌وجو** می‌کند — کاری که متن آزاد
امروز نمی‌کند.

## امضا: آیا `DROP` لازم است؟

**اگر فقط بدنه و مقدارِ بازگشتی عوض شود، نه.** خروجی همچنان `jsonb` است، پس `CREATE OR REPLACE`
کافی است و قاعدهٔ ۵ فایل `CLAUDE.md` فعال نمی‌شود. مهاجرت‌های ۴۱۵، ۴۲۰ و ۴۲۱ همین کار را کرده‌اند.

**`DROP` فقط وقتی لازم است که پارامتری اضافه شود** — مثلاً `p_dry_run boolean DEFAULT false`. آن
وقت پارامتر پیش‌فرض‌دار **جایگزین نمی‌شود، overload می‌سازد**، هر دو با فراخوان برنامه مطابقت
می‌کنند و PostgreSQL آن را مبهم اعلام می‌کند — همان چیزی که مهاجرت ۲۲۲ صریحاً نوشته و مهاجرت ۲۱۲
چهار امضای تاریخی را برای همین دلیل drop کرده است.

الگوی مخزن، اگر لازم شد:

```sql
DROP FUNCTION IF EXISTS public.create_sales_quote_with_items(
  text,text,text,timestamptz,numeric,numeric,numeric,jsonb,
  uuid,uuid,boolean,numeric,boolean,uuid,uuid,text,integer,numeric,text
);
CREATE OR REPLACE FUNCTION public.create_sales_quote_with_items( … );
```

| مسیر | ریسک |
|---|---|
| **بدون پارامتر تازه** (فقط شکل خروجی) | کم. ولی هر شش مصرف‌کننده باید هم‌زمان تغییر کنند وگرنه رد به سکوت تبدیل می‌شود |
| **overload** | **ممنوع.** فراخوان برنامه با هر دو امضا مطابقت می‌کند و ثبت پیش‌فاکتور یکسره می‌شکند |
| **`DROP` + `CREATE`** | امضا لحظه‌ای وجود ندارد؛ باید در همان تراکنش باشد. اگر مهاجرت وسط کار بیفتد، تابع نیست |

## مهاجرت تدریجی بدون شکستن مصرف‌کننده‌ها

۱. **کلاینت اول، دیتابیس دوم.** هر شش محل طوری تغییر کنند که *هم* `error` و *هم* `ok === false` را
   بفهمند. زیر تابع فعلی این تغییر بی‌اثر است، چون `ok` هرگز نمی‌آید.
۲. سپس تابع تغییر کند. مصرف‌کننده‌ها از قبل آماده‌اند.
۳. اسپک‌های ۲۱۲ به‌روزرسانی شوند تا هر دو شکل را بپذیرند، بعد فقط شکل تازه.
۴. **آزمون پیش از هر چیز در تراکنش برگشتی** با JWT شبیه‌سازی‌شده (قاعدهٔ ۷): ثابت شود رد،
   ردیف ثبت می‌گذارد و `RAISE` نمی‌گذارد.

هیچ‌یک از این چهار گام هنوز برداشته نشده.

## آنچه سنجیده نشد

- کد وضعیت HTTP که PostgREST برای کلاس `22023` می‌دهد — یعنی **هر هفت رد کسب‌وکاری** — اندازه‌گیری
  نشد؛ فقط مسیر `42501` سنجیده شد. مستندات PostgREST کلاس ۲۲ را ۴۰۰ می‌گوید، ولی این استنتاج است.
- هیچ پروب رفتاری روی یک `CREATE OR REPLACE` برگشتی اجرا نشد؛ آن یک نوشتن روی دیتابیس مشترک است.
