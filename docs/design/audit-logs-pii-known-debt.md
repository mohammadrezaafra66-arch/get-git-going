# بدهی شناخته‌شده — نام و شمارهٔ مشتری در `audit_logs`

> **این سند فقط ثبت است. هیچ اصلاحی انجام نشده و هیچ‌کدام از گزینه‌های بخش آخر اجرا نشده است.**
> تریگر موجود دست‌نخورده باقی می‌ماند. تغییر آن خارج از دامنهٔ تأییدشده است.

تاریخ اندازه‌گیری: ۲۰۲۶-۰۹-۰۳ · پایگاه دادهٔ **تست** (`afrakala`). production لمس نشد.

## یافته

هر بار که یک پیش‌فاکتور ثبت می‌شود، یک تریگر نام و شمارهٔ تماس مشتری را داخل ستون `diff` جدول
`audit_logs` می‌نویسد.

| | |
|---|---|
| تریگر | `trg_audit_sales_quotes` روی `public.sales_quotes` |
| تابع | `public.audit_sales_quotes()` |
| مایگریشن مبدأ | `supabase/migrations/20260426041331_e5adbc61-9f3f-4479-a031-bf7b104a0f98.sql:13-14` |
| کلیدهای هویتی نوشته‌شده | `customer_name`، `customer_phone` (به‌همراه `quote_number`) |
| ردیف‌های موجود با این کلیدها | **۹۲** |

```sql
-- خطوط ۱۳-۱۴ همان مایگریشن، عیناً
'customer_name', new.customer_name,
'customer_phone', new.customer_phone,
```

## چه کسی می‌تواند بخواند

```
admins read audit logs | SELECT | has_role(uid(), 'admin')
viewer_restricted      | ALL    | (NOT is_viewer_only(uid()))
system inserts audit logs | INSERT | -
```

خواندن عملاً محدود به نقش **admin** است. هیچ سیاست `UPDATE` یا `DELETE` وجود ندارد، پس این ردیف‌ها
**پاک‌شدنی نیستند**.

## چرا این «افشای تازه» نیست

همان نام و شماره روی خودِ سند `sales_quotes` هم ذخیره است و `customer_phone` در آنجا `NOT NULL`
است. پس داده جای دیگری هم هست و دستهٔ تازه‌ای از افشا ایجاد نشده. آنچه هست یک **نسخهٔ دوم و
پاک‌نشدنی** است که عمر متفاوتی از خود سند دارد.

نکتهٔ مرتبط با کار جاری: تسهیل ثبت پیش‌فاکتور مهمان **حجم** این ردیف‌ها را زیاد می‌کند — نام و
شمارهٔ مراجعانی که پروندهٔ ثبت‌شده ندارند. این تغییرِ مقدار است، نه تغییرِ نوع.

## گزینه‌های اصلاح آینده — هیچ‌کدام اجرا نشده

| گزینه | کاری که می‌کند | ریسک |
|---|---|---|
| **حذف دو کلید از `diff`** | تریگر دیگر نام و شماره ننویسد | تاریخچه دوپاره می‌شود: ۹۲ ردیف قدیمی دارند، بعدی‌ها ندارند. هر گزارشی که امروز روی این کلیدها تکیه کند می‌شکند — پیش از حذف باید مصرف‌کننده‌ها شمرده شوند. **مایگریشن ۴۱۸ خودش از `audit_logs` می‌خواند**، پس این مسیر بی‌مصرف نیست. |
| **ماسک‌کردن** (مثلاً چهار رقم آخر شماره) | ردیابی‌پذیری می‌ماند، هویت کامل نه | همچنان شبه‌شناسه است و در جمعیت کوچک قابل بازشناسی؛ ارزش حفاظتی کمتر از چیزی است که به‌نظر می‌رسد |
| **محدودکردن بیشتر دسترسی** | مثلاً فقط ستون‌های غیرهویتی از طریق یک view | خواندن `audit_logs` همین حالا admin-only است، پس سود کم است مگر نقش تازه‌ای تعریف شود |
| **پاک‌سازی دوره‌ای ردیف‌های قدیمی** | حجم را محدود می‌کند | `DELETE` روی جدول حسابرسی — با قاعدهٔ ۳ فایل `CLAUDE.md` در تضاد است و تاریخچه را نابود می‌کند |

## قید برای کار جاری

ردیف `audit_logs` تازه‌ای که برای مسیر مهمان نوشته می‌شود **هیچ نام، شماره، آدرس یا کد ملی
نمی‌نویسد** — فقط کاربر، شناسهٔ سند، نوع استثنا، دلیل و زمان. این قید مستقل از بدهی بالاست و آن را
جبران نمی‌کند.
