## ۶) توابع سرور (۲۰ ماژول `*.functions.ts`) — ریسک سرتاسری

بسیاری از این توابع `SECURITY DEFINER`اند و **RLS را دور می‌زنند** (مثلاً `get_workflow_setting[s]`, `get_recent_purchase_label`, `create_inquiry`/`reply_inquiry`, توابع امتیازدهی). پوشش فعلی **غیرمستقیم** است (از طریق UI ماژول‌ها). ⚠️ چون این توابع مرز RLS را رد می‌کنند، یک باگ در آن‌ها می‌تواند داده را فارغ از RLS افشا کند — این کلاس نیازمند تست مستقیم ورودی/خروجی است، نه فقط تست UI.

## ۷) نقاط پرریسک سرتاسری (ارجاع به `BLOCKERS.md`)

1. **الگوی سیستمی permissive-SELECT** (دیتابیس زندهٔ `afrakala`: ۳۸ policyٔ `qual=true`): ۴ LEAK + ۶ CONFIG در migration `20260719120000_rls_permissive_select_fix.sql` بسته شدند؛ ۵ ⚠️ نیازمند تصمیم؛ ۲۳ REFERENCE عمداً باز.
2. **P0 واقعی:** `inquiry_price_cache` (قیمت خرید مذاکره‌شده) و `didar_activities` (فعالیت CRM) — هر دو `qual=true`، تأییدشده از live.
3. **کلاس `auth.role()='authenticated'`** (جدا از ۳۸): `academy_lessons/quizzes/knowledge_articles` — شدت پایین (کلید پاسخ‌ها قفل است). ممکن است جدول‌های دیگری هم داشته باشد → sweep بعدی.
4. **RLS مالکیت‌محور فروش** (`sales_quotes.salesperson_id`): تست منفیِ «فروشندهٔ الف دادهٔ ب را نبیند» **مسدود** تا ساخت `test.sales2` (بخش ۵-۳ فهرست).
5. **نبود guard سطح-route**: صفحات دستهٔ الف/ب/ج در `BLOCKERS.md` (RLS محافظت می‌کند، ولی بدهی defense-in-depth).
6. **واگرایی سیاست نوشتن** (دستهٔ ه): `suppliers` — manager/accountant فراتر از UI می‌توانند حذف/تغییر کنند.
7. **ریسک زیرساخت** (دستهٔ و): دیتابیس دومِ `postgres` با کپی دادهٔ کسب‌وکار + drift انوم `app_role` — پیش از production تعیین‌تکلیف شود.
8. **فیلتر برچسب محصول** فقط برای کلید API ربات اعمال می‌شود، نه کاربر لاگین‌شده (اگر انتظار فیلتر برچسبی برای فروشنده است، در RLS نیست).

## ۸) پیش‌نیازهای مسدودکننده (از `00-index.md` و `BLOCKERS.md`)
