# ماژول ۰۶ — خرید و تأمین‌کنندگان (لیست تأمین‌کننده، تأیید، پنل خرید، درخواست خرید، دستیار هوشمند)

**تستر مسئول:** حانیه (`test.accountant` برای مشاهده و مدیریت تأمین‌کننده؛ سپس `test.manager` برای پنل خرید، فضای درخواست خرید و مشاور خرید) و محمدرضا (`test.admin`) برای موارد فقط-ادمین — تست منفیِ نقش‌ها: محمدرضا (`test.viewer`).
**مسیرها:** `/suppliers`، `/suppliers/$supplierId` (و `.../new`)، `/purchases`، `/purchases/create`، `/purchase`، `/operations/purchase-advisor`.

## الف) این ماژول چه کاری می‌کند
این ماژول دو کار جدا را پوشش می‌دهد: **۱) تأمین‌کنندگان** — ثبت، ویرایش، جستجو، فیلتر وضعیت و «تأیید/رد» تأمین‌کننده به‌همراه سطح اعتماد؛ **۲) خرید** — «پنل خرید» و فرم «ثبت خرید جدید» (خرید تک‌محصولی با تأمین‌کننده، قیمت، ارز، تعداد، تاریخ و قیمت نقدی امتیازآور) و «فضای خرید» برای ثبت و پیگیری «درخواست خرید». افزون بر آن، «دستیار هوشمند خرید» با انتخاب محصول یک توصیهٔ خرید مبتنی بر تاریخچهٔ قیمت و نرخ ارز از هوش مصنوعی می‌دهد.

دسترسی (از کد، نه فرض):
- **مشاهدهٔ تأمین‌کننده** (`requirePermission("suppliers","view")`): admin، manager، accountant ⚙️ (viewer **ندارد**). **ساخت/ویرایش/تأیید** در UI فقط admin و accountant (`canManage = hasAnyRole(["admin","accountant"])`).
- **مشاهدهٔ خرید** (`requirePermission("purchases","view")`): admin، manager، accountant، **viewer** ⚙️. **ثبت خرید** (`requirePermission("purchases","create")`): admin، manager.
- **مشاور خرید** (`requireAnyRole(["admin","manager"])`): فقط admin و manager.
- **RLS:** خواندن `suppliers`/`purchases`/`purchase_items`/`product_suppliers`/`purchase_prices` نقش‌محور است (admin/manager/accountant) — هیچ `SELECT=true` روی این جدول‌ها نمانده. `purchase_requests` مالکیت‌محور است: هر کاربر فقط درخواست خودش (`requested_by`) یا واگذارشده به خودش (`assigned_to`) را می‌بیند؛ ثبت درخواست فقط برای sales/manager/admin مجاز است.

> پیش‌نیاز کلی: دادهٔ مرجع seed اجرا شده باشد (۵ تأمین‌کنندهٔ `QA-`، محصولات `QA-`، حداقل یک «زمان تسویه» فعال). حانیه رکوردهای خودش را با پیشوند `HAN-` بسازد. توجه: همهٔ مسیرهای این ماژول **guard سطح-route دارند** — بنابراین (برخلاف چند ماژول دیگر) اینجا صفحهٔ بدون-guard نداریم.

> ### 📌 یادداشت یافته — ناسازگاری UI/RLS در نوشتنِ «تأمین‌کننده» (PUR-N09)
> لایهٔ برنامه، ساخت/ویرایش/حذف تأمین‌کننده را محدودتر از RLS می‌داند:
> - **ماتریس `PERMISSIONS`** (`src/lib/rbac/roles.ts`): `suppliers.create`/`update` = admin, accountant؛ `delete` = فقط admin.
> - **UI** (`_app.suppliers.tsx` و `SupplierForm.tsx`): `canManage = hasAnyRole(["admin","accountant"])` — یعنی manager دکمهٔ ساخت/تأیید/ویرایش را نمی‌بیند.
> - **اما RLS** (`suppliers_insert_privileged` در migration `20260505122501`، و `suppliers_update_privileged`/`suppliers_delete_privileged` در `20260427143147`): نوشتن/به‌روزرسانی/حذف برای **admin/manager/accountant** مجاز است.
>
> نتیجه: یک کاربرِ **manager** با فراخوانی مستقیم PostgREST می‌تواند تأمین‌کننده بسازد، ویرایش کند، تأیید/رد کند و حتی **حذف** کند — کاری که UI و ماتریس مجوزها از manager دریغ کرده‌اند (حذف حتی از accountant هم دریغ شده ولی RLS به accountant اجازهٔ حذف می‌دهد). چون manager نقشی مورد اعتماد است، این «نشت خواندنیِ نقش‌پایین» نیست؛ بلکه **واگرایی سیاستِ نوشتن (RLS گشوده‌تر از برنامه)** است. ⚠️ نیاز به تصمیم توسعه‌دهنده: یا RLS نوشتن به admin/accountant محدود شود (هم‌راستا با ماتریس)، یا ماتریس/UI به‌روزرسانی شود.
