# پرامپت ممیزی کامل موارد 211 تا 218 دستیار هوشمند افراکالا

## 1. مأموریت

شما باید در پروژه «دستیار هوشمند افراکالا» یک ممیزی فنی، عملکردی و قابل‌اثبات انجام دهید تا مشخص شود نیازمندی‌های شماره 211 تا 218:

1. کاملاً ساخته و قابل استفاده هستند؛
2. ساخته شده‌اند اما ناقص‌اند؛
3. فقط ظاهر یا بخشی از آن‌ها ساخته شده است؛
4. اصلاً ساخته نشده‌اند؛
5. به علت مانع فنی یا نبود داده قابل بررسی نیستند.

این مرحله در ابتدا فقط **ممیزی و تحقیق Read-Only** است. تا قبل از ارائه گزارش نهایی ممیزی، هیچ اصلاحی انجام ندهید.

## 2. محیط و مسیرهای اصلی

مخزن:

```text

```

فرانت تست:

```text

```

سرویس گزارش واتساپ:

```text

```

ابتدا فایل زیر را بخوانید:

```text

```

اگر وجود نداشت:

```text
D:\AfraKalaTest\app\docs\execution\PROGRESS.md
```

## 3. قوانین ایمنی

1. ابتدا فقط تحقیق و ممیزی انجام دهید.
2. هیچ Migration را اجرا یا ایجاد نکنید.
3. هیچ داده زنده‌ای را تغییر ندهید.
4. هیچ سرویس نامرتبطی را Restart نکنید.
5. فایل‌های Untracked نامرتبط را حذف، Stage یا Commit نکنید.
6. Branch را تغییر ندهید.
7. Reset، Restore، Clean، Stash و Force Push ممنوع است.
8. وجود Route، دکمه، کامپوننت، عنوان فارسی یا پاسخ HTTP 200 را دلیل تکمیل قابلیت ندانید.
9. برای اعلام «کامل»، زنجیره فرانت، Backend، Database، Permission، ذخیره‌سازی و تست واقعی باید اثبات شود.
10. در این مرحله اصلاح انجام ندهید؛ ابتدا گزارش و برنامه اصلاح ارائه کنید.
11. اگر تست نیازمند نوشتن روی داده واقعی است، آن را انجام ندهید و «نیازمند تست کنترل‌شده» اعلام کنید.
12. Secret، Token، شماره تلفن کامل یا داده حساس را گزارش نکنید.
13. شناسه‌های موقت Radix مانند `#radix-_r_g_` معیار معتبر نیستند.

# 5. مورد 211 — رد پیش‌فاکتور و اطلاع‌رسانی

منطق نهایی:

1. سیستم ثبت پیش‌فاکتور باید تا حد ممکن با فیلترهای سخت‌گیرانه جلوی پیش‌فاکتور خلاف قانون را بگیرد.
2. اگر پیش‌فاکتور به نظارت حسابدار رسید و رد یا لغو شد، حسابدار باید دلیل کامل وارد کند.
3. دلیل باید در دیتابیس ذخیره شود.
4. دلیل باید به همان کارشناس فروش نمایش داده شود.
5. اعلان باید تا زمان مشاهده و زدن «دیده شد» باقی بماند.
6. زمان ثبت دلیل، حسابدار، کارشناس، پیش‌فاکتور و زمان مشاهده باید ثبت شود.
7. کارشناس دیگر نباید پیام را ببیند.
8. مدیر و حسابدار مجاز باید سوابق را ببینند.

ایراد گزارش‌شده:

- حسابدار متن را می‌نویسد، اما ممکن است ذخیره نشود.
- متن جایی دیده نمی‌شود.
- به فروشنده نمایش داده نمی‌شود.
- اعلان ماندگار و وضعیت «دیده شد» وجود ندارد یا ناقص است.

9. ساخت اعلان برای فروشنده صحیح

# 6. مورد 212 — اعتبار، معوق، تعهد و موجودی

## 6.1. 212-A کنترل پایه اعتبار

1. اعتبار مشتری خوانده شود.
2. اعتبار قابل استفاده با مبلغ پیش‌فاکتور مقایسه شود.
3. اگر مبلغ پیش‌فاکتور بیشتر از اعتبار قابل استفاده است، ثبت عادی متوقف شود.
4. اگر مشتری معوق دارد، ثبت عادی متوقف یا فقط از مسیر استثنای مجاز ادامه یابد.

6. مبلغ پیش‌فاکتور، اعتبار کل، مصرف‌شده، باقی‌مانده، کسری و معوق نمایش داده شود.
7. Backend نیز Validation را enforce کند.

توجه: عبارت اولیه «اگر اعتبار مشتری از مبلغ پیش‌فاکتور بیشتر باشد جلو ثبت را بگیرد» احتمالاً اشتباه نگارشی است. منطق صحیح ظاهراً این است که اگر مبلغ پیش‌فاکتور از اعتبار قابل استفاده بیشتر باشد، ثبت متوقف شود. هر تعارض را گزارش کنید و خودسرانه تغییر ندهید.

## 6.2. 212-B ثبت با مانده معوق و تعهد فروشنده

1. گزینه «ثبت با تعهد کارشناس فروش» وجود داشته باشد.
2. مدت `N دقیقه` تعیین و ذخیره شود.
3. Popup متن تعهد سیستمی را نمایش دهد.
4. بدون تأیید تعهد ثبت نشود.
5. متن/نسخه تعهد، زمان، کارشناس، مشتری، پیش‌فاکتور و Deadline ذخیره شود.
6. پس از Deadline، تسویه یا عدم تسویه قابل تشخیص باشد.
7. فیش واریزی به تعهد مربوط متصل شود.
8. عدم ایفای تعهد قابل پیگیری باشد.
9. مهلت ۱۰ روزه فروش کالا فقط متن نباشد و Workflow قابل رصد داشته باشد.
10. کسر خسارت بدون Approval و Audit انجام نشود.

متن مورد انتظار:

> اینجانب با توجه به شناختی که از مشتری خود دارم و بنا به تشخیص شخصی، متعهد می‌شوم که مشتری حداکثر تا N دقیقه دیگر مبلغ معوق خود را تسویه کرده و فیش واریزی را ارسال خواهد کرد. در صورتی که مشتری در مهلت مقرر بدهی قبلی خود را تسویه نکند، تمام مسئولیت خرید انجام‌شده و کالایی که بر اساس این پیش‌فاکتور توسط واحد خرید تهیه شده است، بر عهده اینجانب خواهد بود. همچنین در صورت کاهش قیمت کالا یا عدم فروش آن، موظف هستم حداکثر ظرف مدت ۱۰ روز کالا را به فروش برسانم و در غیر این صورت، خسارت و زیان وارده در پایان ماه از محل درآمد اینجانب کسر خواهد شد.

## 6.5. 212.8 کنترل موجودی

طبق متن فعلی:

هنگام ثبت توسط فروشنده:
1. کالای ناموجود قابل ثبت نباشد.
2. تعداد بیشتر از موجودی قابل ثبت نباشد.
3. موجودی انبار انتخاب‌شده خوانده شود.
4. Backend نیز کنترل کند.

هنگام قطعی‌سازی:
1. موجودی لحظه‌ای مجدداً بررسی شود.
2. موجودی صفر یا کمتر از مقدار درخواستی مانع قطعی‌سازی شود.
3. پیام خطا نام کالا، تعداد درخواستی، موجودی فعلی و انبار را نشان دهد.
4. کاهش موجودی Transactional باشد.
5. Race Condition و موجودی منفی کنترل شود.
6. Finalize دوباره دوباره موجودی را کم نکند.

اگر اسناد قبلی اجازه ثبت بدون موجودی و کنترل فقط هنگام قطعی‌سازی را می‌دهند، تعارض را با مسیر و مدرک گزارش کنید و خودسرانه سیاست را تغییر ندهید.

# 20. پاسخ‌های صریح نهایی

1. آیا دلیل رد پیش‌فاکتور ذخیره می‌شود؟
2. آیا برای فروشنده صحیح نمایش داده می‌شود؟
3. آیا اعلان تا «دیده شد» باقی می‌ماند؟

5. آیا کنترل اعتبار کار می‌کند؟
6. آیا تعهد معوق ذخیره و پیگیری می‌شود؟
7. آیا تعهد بیش از اعتبار ذخیره و پیگیری می‌شود؟
8. تأیید حسابداری واقعی است یا Self-attestation؟
9. موجودی هنگام ثبت کنترل می‌شود؟

# 21. پایان ممیزی

1. اصلاح اجرا نکنید.
2. Commit و Push نکنید.
3. سه گزارش را بسازید.
4. خلاصه وضعیت را در ترمینال نمایش دهید.
5. مسیر گزارش‌ها را اعلام کنید.
6. اگر امن بود، یک خط به PROGRESS اضافه کنید.
7. تأیید کنید Migration اجرا نشده، داده زنده تغییر نکرده، Runtime نامرتبط تغییر نکرده و فایل نامرتبط دست‌کاری نشده است.
