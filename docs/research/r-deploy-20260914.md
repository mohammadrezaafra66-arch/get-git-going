## What differed from the runbook

1. **Execution model.** The runbook assumes one interactive window with regions pasted one by one. This executor's
   PowerShell tool starts a new process per call, so the in-shell failed-gate record cannot span calls. Instead each
   phase ran as ONE script in ONE process, where a failing gate's `throw` halts everything after it (stricter than
   pasting). Where a later phase needed a new process, the read-only gates were re-run first, as the runbook says to
   do in a new window: D1a + L1 before TAR (attempt 3); D1a + L1 + D3 before deploy (attempt 4).
2. **GATE TAR copy step skipped** (attempt 3) — hand copy by the owner, executor re-verified; `.sha256` read locally.
3. **Deploy region instrumented** — exit code read and printed after `compose up` and after `docker restart`; throw on
   non-zero. No command changed.
4. **Block 5 got one added read-only query** (`docker ps -a --filter name=afrakala-lan-db-role-fix`) and a wait for
   web health before running.

## Release-line defects found

1. **GATE TAR has no fallback when the release share is unreachable from production.** The runbook assumes
   `\\192.168.170.8\dumps` is readable from `192.168.170.10`. On 2026-09-14 `Copy-Item` from the share threw
   `Invalid Signature.` (the Windows text for an SMB signing failure; not diagnosed — the share was not retried and no
   SMB setting was touched). The gate's catch merges "copy" and "hash" into one message, so the failing step is
   inferred from the empty target directory, not reported. The release line needs a documented, gated local-copy path
   (pre-staged tarball, both hashes checked locally) instead of an ad-hoc variant.
2. **Block 5's `docker ps` omits `-a`**, so it never lists the exited `afrakala-lan-db-role-fix`; its own Expect
   ("db-role-fix = Exited (0)") cannot be checked from its own output.
3. **Block 4 has no gate and no exit-code read**, and its Expect "afrakala-lan-rest Up X seconds" is not printed by the
   block (only by Block 5).
4. **`$env:GIT_SHA` in Block 4 is inert under `--no-build`** — harmless, but its Expect line implies it protects the
   label, which on this path only the image does.
5. **D6(i) IPv4 allowlist is at its ceiling** (4 of 4). Any new quoted `127.0.0.1`/`0.0.0.0` in the bundle fails the gate.
6. **Runbook LOAD Expect / brief** predicted a different image id on this laptop's store; it printed the build id.
7. **Pre-deploy `APP_GIT_SHA` was `d60232f5`** while the checkout was `9bc8d554` — the old container's label did not
   equal its checkout's HEAD. Recorded as measured; not investigated.
