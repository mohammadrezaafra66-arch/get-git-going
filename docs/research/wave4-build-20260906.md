## 2 · O-1 — how many OCR calls reached OpenAI

**The exact count is not knowable, and that is itself the finding.** `ai_provider_health` has
primary key `(provider_id, capability)` — one upserted row, no history — and the schema has no
per-call AI usage or audit table.

**Provable lower bound:**
- **At least one confirmed success**, `2026-08-31 12:56:59 UTC`, latency 4413 ms, against
  `https://api.openai.com/v1` with a live key (`key_prefix sk-pro`).
- **Exposure window:** 2026-08-28 06:48:04 → 2026-09-06 (closed by migration 460).
- **Nine receipt images** were uploaded inside that window (2026-08-28 ×1, 2026-08-29 ×5,
  2026-08-31 ×3). That bounds *distinct images*; it is **not** a call count.

**How the exposure was created.** Migration 397 set the local pin and 401 re-asserted it. No later
migration touches the table. Yet **all seven other routes still carry `updated_at = 2026-08-28
06:37:41` with `provider_id` NULL** — every route was cleared in one transaction, three minutes
after Ollama's vision endpoint first timed out, and eleven minutes before the keyed OpenAI provider
was created. Something outside the migration history did that.

**Durability.** Independently verified: the fix survives a second clearing through two locks.
`fallback_enabled=false` now makes `applyUsageRoute` return `[]`, and `listProvidersFor` filters on
`.eq("is_active", true)`, which excludes the OpenAI row before routing is consulted. An attacker
would have to change two rows in two tables.

🔴 **Unclaimed weakness, found by the verifier.** There is **no audit trigger on
`ai_usage_routes` or `ai_providers`** — only `updated_at` triggers. A search of `audit_logs` for
`receipt_ocr` or the provider id returns **0 rows**. The 2026-08-28 clearing left no audit trail,
and a repeat would be equally invisible. Detection currently rests on a human re-reading
`updated_at`. **This is the weakest link in the OCR fix and is not addressed by this wave.**

Also relevant: local Ollama vision is **not broken**. `EXTERNAL_API_TIMEOUT_MS` is unset and floors
at 15 000 ms while a cold model load takes ~170 s — both the original and current failures are
exactly 15001/15002 ms. Raising it is an owner decision that was deliberately not taken.

### 🔴 The inverted guard — the sharpest finding of the wave

Three system RPCs opened with:
```sql
IF auth.uid() IS NOT NULL THEN
  RAISE EXCEPTION 'system RPC: not callable by authenticated users';
```
`auth.uid()` is NULL for `service_role` **and for `anon`**. A guard written to admit only the system
therefore admitted precisely the callers with no identity. `record_…` inserts into
`market_rate_ticks`, which feeds `_par_latest_usd_rate()` and so product pricing, and wrote
`audit_logs` rows with `actor_id NULL`.

**Correction to Agent S's naming, from the verifier:** two of the three names as reported do not
exist. The real functions are `start_market_rate_ingestion_run_system`,
`finish_market_rate_ingestion_run_system`, and `record_external_market_rate_tick_system`. All three
are now `anon = f` and `authenticated = f`.

⚠️ **The inverted guard itself was never corrected — only made unreachable by revoking grants.** The
logic is still in the bodies verbatim. If EXECUTE were ever regranted, the anon-admitting behaviour
returns immediately. Six non-`_system` siblings remain `anon = t` / `authenticated = t`; they appear
to carry checks but the hardening did not extend to them.

### Anon reachability is genuine, not a grant artifact

**658 of 661** anon-executable functions carry an **explicit** `anon=X/supabase_admin` entry in
`proacl`. Only **3** receive it via the PUBLIC grant alone. These are deliberate grants that
PostgREST exposes over the API. Prior art's "0" was "0 after allowlist subtraction", and only
because the existing derived query filters out anything containing `RAISE EXCEPTION` — the naive
filter the brief warned about. Raw anon-reachable writers: **80**.

Eight anon-reachable SECDEF writers with no role check remain: four `bot_*` functions (which

## 4 · S-5 — the route-guard hole is worse than reported, and is only partly closed

**The brief called this a loading-window race. It is not.** `beforeLoad` runs **once, on the
server**, where `ensureAuthReady` cannot see a session held in `localStorage`, and it **never runs in
the browser at all**. Instrumenting the guard produced exactly one line, on the dev server's stdout
and never in the browser: `[GATEPROBE] requireAnyRole ran; isBrowser= false [ 'admin' ]`. The
exposure was **permanent for the page view**, not a window — a cold `viewer` sat on 93 person rows
for a full 20 seconds and never redirected.

Cold measurement (fresh `browser.newContext()`, no `storageState`, storage asserted empty before
login, real form login, full navigation):

| role | route | before | after |
|---|---|---|---|
| viewer | `/admin/persons-cleanup` | **93 rows rendered** | refused |
| viewer | `/api-keys`, `/presence` | refused | refused |
| viewer | `/admin/roles`, `/admin/audit` | rendered, no data | refused |
| sales | `/admin/persons-cleanup` | **12 rows rendered** | refused |
| sales | `/admin/roles` | **9 rows rendered** | refused |
| admin | all six | renders | renders — the open half holds |

Independently re-measured cold by the verifier: zero person rows on any route; every route showed
«در حال بررسی جلسه کاربری…» then a denial; the page component never painted.

### 🔴 `/bot-api-keys` is still open — confirmed twice

Both `viewer` and `sales` see the **full Bot API Keys management page**, including the «کلید جدید»
(New Key) button. No key data leaked only because the table is currently empty.

This is a genuine authorization hole, not intended access. `role_permissions` is explicit:

```
 role_name  |    module    | can_view | can_create
 accountant | bot-api-keys | f        | f
 sales      | bot-api-keys | f        | f
 viewer     | bot-api-keys | f        | f
```

Root cause: `_app.bot-api-keys.tsx` uses `requirePermission("bot-api-keys","view")` with no
`staticData.gate`, and `RouteRoleGate` declares only `{kind:"anyRole"} | {kind:"admin"}` — it has
**no `permission` kind**, deliberately and documented.

### The scale, corrected

Agent S reported **19 of 149** routes carrying `staticData.gate`. The verifier **refuted** that: the
real count is **23 of 148**.

```
guarded route files (beforeLoad + a require* guard): 148
of those carrying staticData `gate:`                : 23
guard kinds: requirePermission 73 | requireAnyRole 60 | requireAdmin 17 | requireAdminOrManager 2
```

**125 of 148 guarded route files still have no client-side gate**, and the **73 `requirePermission`
routes are structurally uncoverable** until `RouteRoleGate` grows a `permission` kind.
`/bot-api-keys` is one confirmed live instance of that class; there are likely more.
**This is an owner decision that was deliberately not taken.**

### W-3 · «آزمایشی ۸» — both numbers are right; they never measured the same thing

The customer is `مشتری آزمایشی 8` (`7e35520c-…`), `responsible_id IS NULL`.

- **5,000,000 is right, as prepaid credit on hand.** Not a default or fallback constant — that
  hypothesis is refuted: no `pg_proc` body contains `5000000`, no column default does, and
  `customers` has **no credit columns at all**. It is a real ledger entry: `increase_credit` posted
  `payment` +5,000,000 against approved receipt `4ecb0eff-…` on 2026-08-20.
- **0 is right, as the dynamic capital-allocation ceiling.** `calculate_customer_realtime_credit`
  reads `customers.responsible_id`, finds NULL, and short-circuits to
  `{final_limit: 0, binding_constraint: 'no_salesperson'}`. A customer with no salesperson has no
  capital pool to take a share of.
- **The mechanism:** the two share no data source but `customers` itself. One is the live prepaid
  ledger (D-13's world); the other belongs to the capital-allocation cycle retired by 447. Neither
  can flow into the other. `customer_credit_profile` is **empty — 0 rows table-wide** — so the
  `COALESCE(ccp.credit_limit − ccp.outstanding_balance, …)` branch is dead code for all 91 customers.

🔴 **The real hazard is not the discrepancy.** The page labels the 5,000,000 as «سقف مجاز حساب‌باز»
(open-account credit ceiling) and stamps the customer «معتبر». That is **a prepaid balance the
customer has already paid, presented as extendable credit.** Both rows on the default page are
prepaid balances. **Owner decision required.**
