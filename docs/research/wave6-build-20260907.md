## X-1's replacement guard — mechanism and predicate

The old guard counted rows in `capital_allocation_ledger` and skipped the whole recompute if any
existed. It protected against a recompute dropping a ceiling **below what is already held**, leaving
a customer over-committed. **It had never once fired, because the table was empty** — the failure
mode that looks like success.

Retiring is a **rename**, so the original predicate still works verbatim, and a live source is added
on top. `_capital_setting_reservation_count(p_setting_id)` returns:

1. rows in `zz_retired_capital_allocation_ledger` belonging to this setting (customer or
   salesperson) — the original predicate, unchanged but for the name; **plus**
2. customers of this setting whose **net** `hold` in `customer_credit_ledger` is `> 0`
   (`SUM(hold) − SUM(release) > 0`, so a fully released hold no longer locks).

**Strictly stronger than what it replaced, never weaker.** Reproduced by the orchestrator:

```
0 reservations     -> {"skipped": false}                                  recompute proceeds
1 live 'hold' row  -> {"skipped": true, "reason": "ledger_exists", ...}   ceilings UNCHANGED
```

The concrete harm it prevents, measured by Agent X on setting `c977b3f9` by halving capital: without
the guard, customer `869e7514` would hold 900,000,000 against a ceiling that had just become
623,574,797 — **over-committed by 276,425,203**.

`is_valid_audit_entity_type` was confirmed **not** a reader: it contains the string literal only, and
has zero callers.

## `call_logs` — final schema

```
id uuid PK            extension    text NULL
employee_id uuid NOT NULL          is_missed    boolean NULL
direction text NOT NULL            is_internal  boolean NULL
duration_seconds integer NOT NULL  disposition  text NULL
started_at / ended_at timestamptz
customer_id / external_id / source / metadata jsonb / created_at

CHECK (direction = ANY (ARRAY['inbound','outbound','internal']))
UNIQUE INDEX call_logs_external_id_unique_idx (external_id) WHERE external_id IS NOT NULL
INDEX idx_call_logs_extension (extension) WHERE extension IS NOT NULL
INDEX idx_call_logs_employee_time (employee_id, started_at DESC)
0 user triggers · 0 foreign keys · anon holds nothing · 0 rows
```

Two design notes that consumers must respect:

- **`is_missed` and `is_internal` are nullable with no default, on purpose.** `DEFAULT false` would
  assert "not missed" about rows nobody has classified. **Write `is_missed IS TRUE`, never
  `NOT is_missed`.**
- **`employee_id` is `NOT NULL` and the table has zero FKs.** A CDR row for an unmapped extension
  **cannot be inserted at all**, which makes C-3's extension table a hard prerequisite for C-4.

## 🔴 A security regression this wave caused, and fixed — migration 507

**`og61` caught it after the merge**, and neither the build agents nor Agent V's brief covered it:

```
Error: SECURITY DEFINER writer(s) reachable by every authenticated user - a 'viewer'
included - with no check that refuses a CALLER:
  notify_accountants_daily_accrual_summary, roll_employee_daily_streaks.
```

`CREATE FUNCTION` leaves `EXECUTE` granted to `authenticated`, so any signed-in user — a `viewer`
included — could post notifications into three accountants' queues and advance or reset every
employee's streak, minting the XP events with it. `anon` was already closed (migration 477 held), so
the exposure was to logged-in users only.

**The orchestrator's own correction contributed to this.** Both agents were told that cron carries no
JWT and that a role assertion would raise `42501` and fail silently — so both correctly wrote
guard-free SECURITY DEFINER functions. Neither was told to close the grant.

The fix is the grant, not the body: a `has_any_role` check would refuse the scheduler itself.

```
before   authenticated = t  on both                 og61: 1 failed
after    permission denied for function roll_employee_daily_streaks
         permission denied for function notify_accountants_daily_accrual_summary
         og61: 23 passed
```

Both cron owners (`postgres` jobid 23, `supabase_admin` jobid 25) keep EXECUTE, and both functions
were re-invoked from the scheduler's own path afterwards and still work. `grep` over `src/` and
`server/` finds zero callers.

**The migration asserts its own outcome, and that mattered.** The first attempt was applied as
`postgres` rather than the owning role, where `REVOKE` emits only a `WARNING` and silently does
nothing. The assertion raised and the whole migration rolled back rather than recording a fix that
had not happened.

**Standing lesson: any cron-only SECURITY DEFINER function must carry its `REVOKE` in the same
migration that creates it.**
