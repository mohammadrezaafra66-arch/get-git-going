### ۵) کاربر غیرفعال نمی‌تواند خرید ثبت کند

`tg_purchase_actor_active` به هیچ triggerی وصل نبود. حالا:

```
purchases          | trg_purchases_actor_active          | tgtype=7  (BEFORE INSERT FOR EACH ROW)
purchase_requests  | trg_purchase_requests_actor_active  | tgtype=7
```

رفتار، داخل `BEGIN … ROLLBACK`:

```
CASE 1 purchase_requests / INACTIVE -> REFUSED  42501  حساب کاربری شما فعال نیست.
CASE 2 purchase_requests / ACTIVE   -> ACCEPTED             (کنترل: رد فراگیر نیست)
CASE 3 purchases / INACTIVE         -> REFUSED  42501
rows after rollback: purchase_requests=1210 purchases=303   (بدون تغییر)
```

**فقط BEFORE INSERT، عمداً:** تابع نویسندهٔ ردیف را قضاوت می‌کند نه نشست را، پس شلیک روی UPDATE
هر ردیفی را که نویسنده‌اش بعداً غیرفعال شده برای همیشه قفل می‌کرد — از جمله ویرایش‌های ادمین فعال.

## دو یافته که از ردیف‌هایشان مهم‌ترند

### الف) یک زمان‌بند ۵۶ روز است که «با موفقیت» هیچ کاری نمی‌کند

نقشه فرض کرده بود `pg_cron` نصب نیست. آن قرائت — که **مال من بود** — علیه `afrakala` گرفته شده

هستند. علیه `postgres`: **pg_cron 1.6 نصب است و از ۲۰۲۶-۰۷-۱۱ چهار job فعال دارد.**

11|succeeded| 15947    capture-score-snapshots-5min
12|succeeded|    56    cleanup-stale-auto-suppliers

| 22 | `afrakala-sync-price-observatory-daily` | `0 23 * * *` | ۰۲:۳۰ |

> ⚠️ **`cron.database_name` را سرسری «درست» نکنید.** هنوز `postgres` است. تغییرش به `afrakala`
> و restart باعث می‌شود job 11 هر ۵ دقیقه روی دادهٔ واقعی snapshot بگیرد (~۲٬۶۰۰ ردیف در روز)

## C-12 — موکول‌شده به‌تصمیم، با شواهدی که brief آینده به ارث می‌برد

**تصمیم مالک (۲۰۲۶-۰۹-۰۵): در این موج وصل نشود. بعداً درست ساخته شود، با کنترل دسترسی
به‌ازای هر کلید، هم‌ارز `bot_api_key_table_access(can_read, can_update)`.**

شواهدی که هر brief آینده باید با آن شروع کند — چرا شکل فعلی نمی‌تواند کار کند:

**۱) دو تابع هویت کاربر واقعی می‌خواهند؛ مسیر bot هویت کاربر ندارد.** هر دو با این شروع می‌شوند:

```sql
_uid uuid := auth.uid();
IF _uid IS NULL THEN RAISE EXCEPTION 'احراز هویت لازم است.' USING ERRCODE = '42501';
IF NOT public.has_any_role(_uid, ARRAY['admin','manager']::text[]) THEN ...
```

اندازه‌گیری از راه Kong، همان مسیری که endpointهای bot می‌روند:

```
service_role -> HTTP 403  {"code":"42501","message":"احراز هویت لازم است."}
anon         -> HTTP 401  {"code":"42501","message":"احراز هویت لازم است."}
```

`BotAuthContext` برابر `{ keyId, name }` است (`src/server/bot-api.ts:8-11`) — هیچ هویت کاربری
برای تحویل دادن وجود ندارد، و `api_dynamic_table_update_cell` مقدار
`audit_logs.actor_id = _uid` می‌نویسد، پس یک ربات actor معتبری ندارد.

**۲) وصل کردنش با شکل فعلی یک عقب‌گرد امنیتی بود.** مسیرهای bot موجود
(`api.public.bot.dynamic-tables.by-slug.$slug.ts`، `.rows.ts`، `.rows.$rowId.ts`) از راه
`bot_query_table_rows`/`bot_update_table_row` می‌روند و **ACL هر کلید** را روی
`bot_api_key_table_access(can_read, can_update, allowed_update_columns)` اعمال می‌کنند،
به‌علاوهٔ rate limit و ثبت مصرف. جفت `api_*` هیچ مفهومی از ACL هر کلید ندارد — هر کلید ربات
به هر جدول پویای فعال می‌رسید.

**۳) قابلیت از قبل به‌شکل bot-key-native وجود دارد.** تفاوت واقعی جفت `api_*` فقط این است که
با **slug** کار می‌کند نه با id.

**بنابراین کار آینده «وصل کردن» نیست؛ یا باید ACL هر کلید به جفت `api_*` اضافه شود، یا به
مسیرهای موجود یک ورودی مبتنی بر slug داده شود.** دومی احتمالاً کوچک‌تر است.
