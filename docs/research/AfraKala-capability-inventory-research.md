## بخش ۰ — قواعد

### ۰.۱ ممنوعیت‌ها
- فقط خواندن: `rg`، خواندن فایل، و `SELECT`/introspection روی DB. هیچ نوشتنی، هیچ build/up/down.
- برنچ کاری: `feature/navigation-modernization` (تأیید کن). دیتابیس: `afrakala`.
- الگوی اتصال DB:
  ```powershell
  $pw = (docker exec afrakala-lan-db printenv POSTGRES_PASSWORD).Trim()
  @"
  SET client_encoding='UTF8';
  <SQL>
  "@ | docker exec -i -e PGPASSWORD=$pw afrakala-lan-db psql -U supabase_admin -d afrakala -A -F '|'
  ```
- هیچ کلید/رمز چاپ نشود.

### ۰.۲ استاندارد شواهد + ضدخوش‌بینی
هر ادعا با شاهد (فایل:خط، نام تابع، خروجی SQL). و این چهار قانون را اعمال کن:
1. **کامپوننت mount‌نشده = وجود ندارد.** برای هر UI با `rg` تأیید کن که واقعاً رندر/استفاده می‌شود، نه صرفِ وجود فایل.
2. **UI بدون اتصال داده = نیمه.** اگر صفحه هست ولی hook/کوئری‌اش کار نمی‌کند یا mock است، «نیمه».
3. **قابلیت روی برنچ سروری (`feature/navigation-modernization`) باشد**، نه فقط جایی در کد.
4. **«هست» یعنی واقعاً از سایدبار قابل رسیدن و کارکردنی است.** اگر فقط route وجود دارد ولی در منو نیست یا گارد اجازه نمی‌دهد، این را دقیق بنویس.

### ۰.۳ برچسب وضعیت
برای هر قابلیت دقیقاً یکی: **✅ هست و کارکردنی** / **🔶 نیمه‌ساخته** (بگو کدام بخش هست، کدام نیست) / **❌ نیست** (با ذکر روش جستجو) / **❓ نامشخص** (با ذکر مانع).

## بخش ۱ — اول: درخت کامل سایدبار با نام‌های فارسی دقیق (حیاتی)

قبل از هر قابلیتی، ساختار ناوبری واقعی را بیرون بکش. این پایهٔ کل آموزش تست است.

```powershell
Get-Content src/lib/navigation/registry.ts
rg -n "label|title|group|icon|path|to:" src/lib/navigation/registry.ts
```
- **درخت کامل سایدبار را بازتولید کن**: گروه‌ها و زیرآیتم‌ها، با **رشتهٔ فارسی دقیق هر برچسب** + مسیر (route) + نقش/گاردی که نمایش آن را کنترل می‌کند.
- خروجی را به‌صورت یک درخت مرتب در گزارش بگذار، مثل:
  ```
  گروه «فروش»
    - «جستجوی سریع فروش» → /sales/search (نقش: sales, manager, admin)
    - «پیش‌فاکتورها» → /sales/quotes (...)
  گروه «حسابداری»
    - ...
  ```
- اگر بعضی صفحات route دارند ولی در سایدبار نیستند (فقط از هاب/لینک مستقیم قابل دسترسی)، جدا فهرست کن.

## بخش ۲ — قابلیت‌ها (برای هرکدام: وضعیت + کارت ناوبری)

برای **هر** قابلیت زیر، دو چیز بده:
- **الف) وضعیت** (✅/🔶/❌/❓) + شاهد در چهار لایه (UI / منطق فرانت / بک‌اند / دسترسی).
- **ب) کارت ناوبری** (فقط اگر ✅ یا 🔶): جدول زیر را پر کن:

  | فیلد | مقدار |
  |---|---|
  | نام فارسی در سایدبار | (رشتهٔ دقیق) |
  | مسیر URL | /... |
  | نقش لازم | admin / accountant / sales / manager / purchase_specialist |
  | پیش‌نیاز | (مثلاً: اول باید انبار ساخته شود) |
  | مراحل استفاده | ۱. ... ۲. ... ۳. ... (کلیک‌ها، فیلدها، دکمهٔ نهایی) |
  | نکتهٔ خاص | (هر gotcha) |

### پکیج ۱ — محصولات
1. **تعریف محصول در سیستم** — route ساخت محصول، فرم، فیلدهای اجباری.
2. **گذاشتن عکس برای محصول** — آیا آپلود تصویر محصول وجود دارد؟ کدام فیلد/جدول/storage bucket؟ در فرم محصول کجاست؟ (توجه: عکس **محصول**، نه عکس فیش.)
3. **تعریف ویژگی/مشخصات برای محصول** — سیستم برچسب/تگ/spec. آیا از UI قابل تعریف است؟ کدام صفحه؟
4. **🔴 ثبت قیمت دلار برای اجناس دلاری** — (حدس: شکاف) آیا مفهوم قیمت ارزی/دلاری روی محصول وجود دارد؟ ستون `usd_price`/`currency` روی products؟ نرخ دلار جایی تعریف می‌شود؟ با `rg` روی `dollar|usd|دلار|ارز|exchange_rate` در کد و introspection جداول بگرد. اگر نیست، صریح بنویس چه جستجو کردی.

### پکیج ۲ — خرید
5. **ثبت سند خرید** — route، فرم، اتصال به تأمین‌کننده و محصول.
6. **ثبت خرید با کاربرهای مختلف (انتساب کاربر)** — آیا سند خرید `created_by`/کاربر ثبت‌کننده را نگه می‌دارد؟ آیا در UI قابل تفکیک است؟
7. **گزارش خرید به تفکیک کاربرهای مختلف** — آیا گزارشی هست که خریدها را per کاربر فیلتر/گروه کند؟ کدام route؟
8. **🔴 دستور خرید (به‌عنوان یک workflow رسمی)** — آیا «دستور خرید» یک سند/وضعیت رسمی در سیستم است، یا فقط در پیام‌رسان؟ (پکیج ۴ هم این را از سمت پیام‌رسان می‌بیند.)
9. **🔴 متریک فاصلهٔ زمانی «دستور خرید تا قطعی‌شدن خرید»** — (حدس: شکاف) این خیلی خاص است: آیا سیستم زمان لحظه‌ای که کارشناس «دستور خرید» می‌دهد و زمان لحظه‌ای که مسئول خرید «خرید را قطعی» اعلام می‌کند را جدا ثبت می‌کند و فاصله‌شان را محاسبه می‌کند؟ با `rg` روی `order.*confirm|purchase_order|قطعی|dispatch|فاصله زمانی|duration|elapsed` بگرد. اگر ثبت دو timestamp و محاسبهٔ فاصله وجود ندارد، صریح بنویس نیست.

### پکیج ۳ — پیش‌فاکتور و تأیید
10. **ثبت پیش‌فاکتور برای محصول** — route، فرم (احتمالاً `sales_quotes`).
11. **تأیید پیش‌فاکتور توسط حسابدار** — آیا workflow تأیید وجود دارد؟ چه وضعیت‌هایی (`draft/approved/...`)؟ کدام نقش تأیید می‌کند؟ حسابدار از کدام صفحه تأیید می‌کند؟ دکمهٔ تأیید کجاست؟
12. **ثبت پیش‌فاکتور با کاربرهای مختلف (انتساب)** — آیا `salesperson_id`/created_by ثبت می‌شود؟
13. **گزارش پیش‌فاکتور به تفکیک کاربرهای مختلف** — آیا گزارش per کاربر هست؟

### پکیج ۴ — پیام‌رسان (استعلام/اعلام/دستور خرید و متریک‌ها)
> اول مشخص کن این قابلیت‌ها در **همین ریپو** (`D:\AfraKalaTest\app`) هستند یا در ریپو/سرویس جدا. با `rg` روی `messenger|پیام‌رسان|استعلام|اعلام قیمت|rubika|روبیکا` در کد بگرد. اگر جای دیگری‌اند، صریح بگو.
14. **استعلام قیمت** — آیا کاربر می‌تواند استعلام قیمت ثبت/ارسال کند؟ کدام صفحه/جریان؟
15. **اعلام قیمت** — آیا اعلام/پاسخ قیمت وجود دارد؟ کجا؟
16. **دستور خرید (از طریق پیام‌رسان)** — جریان دستور خرید در پیام‌رسان.
17. **🔴 ثبت لحظه‌ای تعداد استعلام‌ها** — آیا شمارندهٔ لحظه‌ای/real-time برای تعداد استعلام‌ها هست؟ مکانیزمش چیست (Realtime/polling)؟ کجا نمایش داده می‌شود؟
18. **🔴 دیدن سرعت اعلام قیمت‌ها** — آیا متریک «سرعت پاسخ‌گویی به استعلام» (فاصلهٔ استعلام تا اعلام) ثبت/نمایش می‌شود؟
> برای موارد ۹، ۱۷، ۱۸ (همه متریک زمانی/لحظه‌ای‌اند) با هم بررسی کن آیا اصلاً زیرساخت ثبت timestamp دو رویداد و محاسبهٔ فاصله وجود دارد یا نه.

### پکیج ۵ — اشخاص و انبار
19. **ساخت اشخاص** — route، فرم ساخت شخص (`persons`).
20. **ساخت انبارها** — route مدیریت انبار (فاز ۸؛ احتمالاً `/warehouses`). ساخت/ویرایش/حذف.

### پکیج ۶ — تخصیص سرمایه (سه‌لایه)
21. **تخصیص سرمایه کل** — حسابدار سرمایه روز را وارد می‌کند؛ کدام صفحه؟
22. **تخصیص سرمایه کارشناس بر اساس امتیازاتش** — صفحهٔ ورود امتیاز کارشناس + اجرای تخصیص. کدام route؟ کدام نقش؟
23. **تخصیص سرمایه مشتری بر اساس امتیاز خود و کارشناسش** — صفحهٔ تخصیص مشتری + اجرا.
> برای این سه، **پیش‌نیاز داده** را صریح بنویس: طبق یافته‌های قبلی، تا امتیاز کارشناس در `dynamic_entity_scores` وارد نشود، سقف اعتبار صفر می‌ماند. در کارت ناوبری این را به‌عنوان پیش‌نیاز ذکر کن.

### پکیج ۷ — دکمه‌های آموزش
24. **آموزش دقیق روی همهٔ صفحات** — کدام صفحات دکمه/لینک «راهنما/آموزش» دارند و کدام ندارند؟ با `rg` روی `راهنما|guide|آموزش|help|Onboarding` بگرد. یک **جدول** بساز: هر صفحهٔ مرتبط با قابلیت‌های بالا | آیا دکمهٔ آموزش دارد؟ (✅/❌). (طبق یافته‌های قبلی، احتمالاً فقط چند صفحه راهنما دارند.)

## بخش ۴ — یادآوری
- **فقط بررسی و ثبت.** هیچ ساختی، هیچ buildی.
- **رشته‌های فارسی سایدبار را عیناً ثبت کن** — تقریبی ننویس؛ آموزش تست به این وابسته است.
- **کارت ناوبری = مهم‌ترین خروجی.** برای هر قابلیت موجود، مراحل استفاده را طوری بنویس که یک کاربر تازه‌کار بتواند دنبال کند.
- ضدخوش‌بینی را جدی بگیر: «هست» یعنی واقعاً از سایدبار قابل رسیدن و کارکردنی، نه صرفِ وجود فایل.
- گزارش: فارسی، مستقیم، جدول‌محور، با شواهد.
