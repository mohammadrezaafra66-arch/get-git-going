### ساختار مخزن

**Monolith تک‌بسته‌ای** — نه workspace، نه monorepo. یک `package.json` در ریشه.

```
src/routes/          ← مسیرهای فایل‌محور TanStack؛ «_app.*» = داخل shell احراز هویت‌شده،
                       «api.*» = HTTP endpoint، «_app.x_.y» = مسیر تودرتوی flat
src/components/      ← کامپوننت‌های دامنه‌ای (۳۱ پوشه)
src/shared/components/ ← فرم‌های مشترک بین چند مسیر (PurchaseForm, PaymentReceiptForm, …)
src/hooks/           ← React Query hookها به تفکیک دامنه
src/lib/<domain>/    ← منطق دامنه؛ الگوی نام‌گذاری معنادار:
                         *.functions.ts → createServerFn (روی سرور اجرا می‌شود)
                         *.server.ts    → فقط سرور، بدون قرارداد RPC
                         *.ts           → منطق ایزومورفیک/کلاینت
src/integrations/supabase/ ← client مرورگر، client.server (service-role)، middlewareهای auth
src/server/bot-api.ts ← لایهٔ API عمومی بات
supabase/migrations/ ← اسکیمای پایگاه‌داده (۴۵۳ فایل)
deploy/lan/          ← استقرار محیط کار (این محیط)
deploy/local/        ← استقرار Cursor Cloud (محیط دیگر — قاطی نشود)
e2e/                 ← Playwright
```

```

  │
  ├─(الف) supabase-js مستقیم ──► Kong :8000 ──► PostgREST ──► Postgres (RLS اعمال می‌شود)
```

و یک لنگرگاه سوم هم هست: `salesperson_capital_allocations_dynamic.salesperson_id` و
`customer_capital_allocations_dynamic.salesperson_id` مستقیم به **`auth.users(id)`** اشاره می‌کنند.

⇒ پروژه امروز **سه لنگرگاه هویتی** دارد: `persons` (بیرونی)، `profiles` (کارمند)، `auth.users` (تخصیص سرمایه).

#### چند نقشی بودن — ردشده با شواهد

`person_context_links.context_kind` هجده مقدار مجاز دارد
(`customer, supplier, driver, sender, receiver, referrer, marketer, representative, complainant,
returner, staff_link, credit_party, accounting_party, delivery_party, purchase_owner,
sales_expert, warehouse_owner, other`) — یعنی **طرح** چندنقشی بودن از قبل ریخته شده،
از جمله `staff_link` برای کارمند.

ولی دادهٔ زنده:

| context_kind | تعداد | فعال |
|---|---|---|
| `customer` | ۱۴ | ۱۴ |
| `supplier` | ۱۵ | ۱۵ |
| `accounting_party` | ۱ | ۱ |

و پرس‌وجوی «تعداد نوع نقش فعال به ازای هر شخص»: **هر ۳۰ شخص دقیقاً ۱ نقش دارند.**
`staff_link` صفر ردیف دارد.

⇒ **تصمیم ۹ مالک** («یک شخص می‌تواند هم‌زمان کارمند، فروشنده، مشتری، تأمین‌کننده، حسابدار،
کارشناس خرید و تیم بازاریابی باشد») امروز: **مدل داده بدون گردش کامل** — ساختار هست، مسیر
نوشتن و رابط کاربری نیست، و کارمند اصلاً به این ساختار وصل نیست.

#### دوگانگی باقی‌ماندهٔ Person/Customer — ریسک‌ها

از `pg_constraint`، **هر کلید خارجی قدیمی هنوز کنار کلید شخص زنده است**:

| جدول | کلید قدیمی | کلید شخص |
|---|---|---|
| `invoices` | `customer_id → customers` | `customer_person_id → persons` |
| `sales_quotes` | `customer_id → customers` | `customer_person_id → persons` |
| `payment_receipts` | `customer_id → customers` | `customer_person_id → persons` |
| `delivery_receipts` | `customer_id → customers` | `customer_person_id → persons` |
| `didar_activities` | `customer_id → customers` | `customer_person_id → persons` |
| `credit_requests`، `credit_score_snapshots`، `customer_credit_*`، `customer_capital_allocations(_dynamic)` | `customer_id → customers` | `customer_person_id → persons` |
| `purchases`، `purchase_prices`، `product_suppliers` | `supplier_id → suppliers` | `supplier_person_id → persons` |
| `payment_vouchers` | `payee_customer_id`، `payee_supplier_id`، `payee_party_id` | `payee_person_id` |

ستون‌های شخص **مشتق** هستند (تریگر از کلید قدیمی بازشان می‌سازد — PROGRESS.md فازهای ۵ و ۷).

**ریسک‌ها:**

1. **جهت اشتقاق وارونه است.** دیتابیس می‌گوید «مشتری مرجع است، شخص مشتق». مالک می‌گوید
   «شخص مرجع است». تا وقتی این وارونه است، هر مسیر نوشتنِ جدیدِ شخص‌محور باید اول یک ردیف
   `customers` بسازد.
2. **نوشتن مستقیم روی ستون قدیمی، ستون شخص را بی‌صدا عوض می‌کند** — چون تریگر است، نه رابطهٔ دوطرفه.
3. **`external_parties.person_id` یکتا نیست** ⇒ یک شخص می‌تواند چند ردیف طرف‌حساب داشته باشد.
   برای اعتبار/مانده این یعنی احتمال جمع دوباره (به C2.13 وصل است).
4. **ستون‌های هویتی قدیمی حذف‌نشدنی‌اند** (PROGRESS.md ۸.۷: ۱۹ تریگر مشتق، ۸ CHECK، ۴ view،
   ۱۴۵ ارجاع کد). یعنی هر گزارش شخص‌محور باید هر دو دنیا را بشناسد.
5. **موتور امتیاز روی شخص کار نمی‌کند** — جزئیات در B1.4.

#### آیا ماژولی هنوز مستقیم `customer_id` می‌زند؟

بله — تقریباً همه. نمونهٔ قطعی از کد: `DynamicScoringSection` با
`entityId={customerId}` صدا زده می‌شود (`src/routes/_app.sales_.customers_.$customerId.credit.tsx:160`)،
یعنی **`customers.id`** نه `persons.id`. هم‌چنین `useCustomerLatestAllocation` روی
`customer_capital_allocations_dynamic.customer_id` فیلتر می‌کند
(`src/hooks/credit/useDynamicScoring.ts`).

یکی‌کردنشان یعنی یا باید برای هر مشتری یک `auth.users` ساخت (نامناسب و پرخطر)،
یا Role را از `persons` آویزان کرد و کل RBAC موجود را بازنویسی کرد.

**مسیر درست برای تصمیم‌های ۹ و ۱۰ مالک:**
1. `profiles` را به `persons` وصل کنید (یک ستون `person_id` روی `profiles` + پرکردن + `staff_link`).
   بدون این، «یک شخص هم کارمند و هم مشتری» **از نظر داده‌ای ناممکن** است.
2. `context_kind` را از CHECK ثابت به یک **جدول مرجع** تبدیل کنید تا مدیر بتواند گروه تعریف
   کند (تصمیم ۱۱). این گسترش همان جدول است، نه ساخت موازی.

#### تصمیم ۱۲ («تغییر وزن نباید امتیاز تاریخی را عوض کند») — موجود ولی ناقص

**بخش درست:** `calculate_dynamic_score` وزن را **به تفکیک دوره** انتخاب می‌کند:

```sql
JOIN dynamic_parameter_weights w
  ON w.parameter_id = p.id
  AND w.valid_from <= v_period
  AND (w.valid_to IS NULL OR w.valid_to >= v_period)
```

**بخش شکسته:** `upsert_dynamic_parameter_weight` (تعریف زنده) وقتی وزن فعلی از **همین ماه**
شروع شده باشد، به‌جای بستن نسخه و باز کردن نسخهٔ جدید، **در جا UPDATE می‌کند**:

```sql
IF v_cur_valid_from = v_month THEN
  UPDATE public.dynamic_parameter_weights
     SET weight = _new_weight, created_by = v_uid
   WHERE id = v_cur_row_id;
ELSE
  UPDATE public.dynamic_parameter_weights SET valid_to = v_month - 1 WHERE id = v_cur_row_id;
  INSERT INTO public.dynamic_parameter_weights(parameter_id, weight, valid_from, created_by)
  VALUES (_parameter_id, _new_weight, v_month, v_uid);
END IF;
```

و چون **هیچ snapshot امتیازی ذخیره نمی‌شود** (`score_snapshots` صفر ردیف دارد و ضمناً
کارمندمحور است، نه خروجی این موتور) و امتیاز **on-demand** محاسبه می‌شود، نتیجه این است:

> **تغییر وزن در همان ماه، امتیاز آن ماه را برای همه‌کس بی‌صدا و بازگشت‌ناپذیر عوض می‌کند.**

ماه‌های گذشته امن‌اند (نسخه‌بندی کار می‌کند). ماه جاری امن نیست.
مضاعف بر آن، همان تابع بلافاصله `run_daily_capital_allocation` را دوباره اجرا می‌کند، پس
اثر مالی هم فوری است.

**ارزیابی رویکردها برای «تغییر وزن، تاریخ را عوض نکند»:**

| رویکرد | تناسب با این کدبیس |
|---|---|
| **snapshot ذخیره‌شده** | **توصیه‌شده.** جدول `score_snapshots` از قبل هست (خالی)؛ الگویش هم از قبل در `credit_score_snapshots` (با `params_used jsonb`) اجرا شده. کمترین کار، بیشترین اثر. |
| رویدادمحوری امتیاز | تا حدی از قبل هست (`employee_score_events`) ولی برای این هدف لازم نیست |
| ذخیرهٔ نسخهٔ فرمول | تا حدی هست (`credit_score_snapshots.params_used`) — الگوی قابل تکرار |
| event sourcing محدود | بیش از نیاز |
| محاسبهٔ دوره‌ای | با `period_month` سازگار است |
| محاسبهٔ on-demand | همین امروز است — و دقیقاً همان چیزی است که مشکل را می‌سازد |

**بهترین ترکیب:** بستن نسخهٔ وزن *همیشه* (حذف شاخهٔ UPDATE در ماه جاری) +
نوشتن یک snapshot در پایان هر دوره با `params_used` به سبک `credit_score_snapshots`.

| مدرک اجباری نباشد (تصمیم ۱۴) | ✔ — هیچ الزام پیوستی نیست | — |
| منقضی نشدن (تصمیم ۱۵) | **نقض شده** — پایین ببینید | `calculate_dynamic_score` روی `s.period_month = v_period` |

**تصمیم ۱۵ نقض شده است:** «امتیاز مثبت/منفی دستی منقضی نمی‌شود» — ولی مدل داده هر امتیاز را
به یک `period_month` می‌بندد و تابع فقط همان ماه را می‌خواند. یعنی یک امتیاز منفی دستی که
در یک ماه ثبت شود، ماه بعد **به‌طور کامل از محاسبه خارج می‌شود** — عملاً همان انقضایی که
مالک صریحاً رد کرده.

**آیا مکانیزم Note یا رویداد گیمیفیکیشن قابل استفادهٔ مجدد است؟**
- `persons.notes` یک فیلد متنی تکی است — نه.
- `employee_score_events` (`employee_id، event_type، source_table، source_id، triggered_at، payload jsonb`)
  **دقیقاً شکل درست یک رویداد امتیاز است** و ۱۶۶ ردیف واقعی دارد. اگر ستون کلیدش از
  `employee_id` به یک ارجاع شخص تعمیم یابد، همین جدول می‌تواند امتیاز دستی ماندگار
  (بدون قفل ماهانه) را نگه دارد. **ساخت جدول رویداد امتیاز جدید توجیه ندارد.**

### B1.6 — تاریخچه و توضیح‌پذیری

| پرسش مالک | امروز قابل پاسخ است؟ |
|---|---|
| امتیاز امروز این شخص چند است؟ | **بله** برای مشتری/فروشنده (`calculate_dynamic_score`) — **نه** برای شخص |
| ماه گذشته چند بود؟ | **بله** — `p_period_month` را عوض کنید؛ وزن‌های همان دوره اعمال می‌شوند |
| کدام عوامل بالا/پایینش بردند؟ | **بله** — `breakdown` هر معیار را با `contribution` می‌دهد |
| چه وزن‌هایی در آن زمان برقرار بودند؟ | **بله** — `raw_weight` و `normalized_weight` در `breakdown` |
| کدام نسخهٔ فرمول اعمال شده بود؟ | **نه** — فرمول نسخه ندارد؛ فقط وزن نسخه دارد |
| کدام رویدادها اثر گذاشتند؟ | **نه** — رابطهٔ امتیاز با سند/رویداد منبع ثبت نمی‌شود |

**«امتیاز سیستمی نباید مستقیم دستکاری شود» — ردشده با شواهد.**
امروز **همهٔ** امتیازها از یک مسیر واحد نوشته می‌شوند (`useUpsertEntityScore` → INSERT/UPDATE
مستقیم روی `dynamic_entity_scores` از کلاینت)، و **هیچ تمایزی بین امتیاز سیستمی و دستی وجود ندارد**
— نه ستونی، نه CHECKای، نه RPC جداگانه‌ای. یعنی هر کاربر مجاز می‌تواند هر امتیازی را
مستقیماً بازنویسی کند و مقدار قبلی هم باقی نمی‌ماند.

### B1.7 — کنترل دسترسی پروفایل

**وضعیت: موجود ولی ناقص — و یک حفرهٔ واقعی دارد.**

سیاست‌های RLS زندهٔ `persons` (از `pg_policies`، عیناً):

```
persons_select_by_visibility_scope | SELECT | authenticated |
   ((visibility_scope = 'internal_general'     AND has_any_role(uid(), ARRAY['admin','manager','accountant','sales','viewer']))
 OR (visibility_scope = 'restricted_finance'   AND has_any_role(uid(), ARRAY['admin','manager','accountant']))
 OR (visibility_scope = 'restricted_executive' AND has_any_role(uid(), ARRAY['admin','manager'])))

persons_update_admin_manager    | UPDATE | authenticated | has_any_role(uid(), ARRAY['admin','manager'])
persons_insert_identity_authors | INSERT | authenticated
```

`person_identifiers` و `person_context_links` همین منطق را از طریق `EXISTS (... persons p ...)`
به ارث می‌برند — یعنی سطح دسترسی **از شخص** می‌آید. طراحی تمیزی است.

سیاست‌های `customers`:

```
read customers by role   | SELECT |
  (has_any_role(uid(), ARRAY['admin','manager','accountant','viewer'])
   OR (has_role(uid(),'sales') AND (responsible_id = uid() OR responsible_id IS NULL)))
manage customers by role | ALL |
  (has_any_role(uid(), ARRAY['admin','manager'])
   OR (has_role(uid(),'sales') AND (responsible_id = uid() OR responsible_id IS NULL)))
```

**مقایسه با تصمیم ۱۷ مالک:**

| قاعدهٔ مالک | وضعیت واقعی | حکم |
|---|---|---|
| پروفایل کارمند ← خود شخص، مدیرعامل، حسابدار | کارمند اصلاً پروفایل شخص ندارد؛ `/users/$userId` گارد نقش دارد ولی «خود شخص» به‌عنوان قاعده در RLS نیست | **ردشده با شواهد** |
| پروفایل مشتری ← مدیرعامل (همه) | ✔ | تأییدشده با شواهد |
| پروفایل مشتری ← حسابدار (همه) | ✔ | تأییدشده با شواهد |
| پروفایل مشتری ← فروشنده (فقط مشتریان خودش) | **نقض شده** | **ردشده با شواهد** |

**حفرهٔ اصلی، با شاهد:**
سیاست `customers` مالکیت‌محور است (`responsible_id = uid()`)، ولی سیاست `persons`
**فقط نقش‌محور** است. یک کاربر با نقش `sales`:

- ردیف `customers` مشتریِ همکارش را **نمی‌بیند** ✔
- ولی ردیف `persons` همان مشتری را **می‌بیند** (چون `visibility_scope='internal_general'` و
  `sales` در فهرست مجاز است) — به‌همراه `display_name`، `legal_name` و `notes`
- و ردیف‌های `person_identifiers` او را هم **می‌بیند** — یعنی **شمارهٔ موبایل، ایمیل، کد ملی
  و شبا** — چون سیاست `person_identifiers_select_via_person` فقط `visibility_scope` را چک می‌کند.

⇒ **محدودیت مالکیتی روی `customers` از مسیر `persons` قابل دور زدن است.**
و دقیقاً به‌خاطر همان یکپارچه‌سازی هویت که در فازهای ۶ تا ۸ انجام شد، حالا اطلاعات تماس
همهٔ مشتریان در یک جدول است که همهٔ فروشنده‌ها می‌بینند.

نکتهٔ دوم: `OR responsible_id IS NULL` یعنی **هر مشتری بدون مسئول، برای همهٔ فروشنده‌ها
قابل خواندن و (چون سیاست `ALL` است) قابل ویرایش است**.

**نتیجه‌گیری صریح:** موضوع اصلاً پنهان‌کردن در UI نیست — Backend و دیتابیس قاعدهٔ مالک را
**اجرا نمی‌کنند**. برای تصمیم ۱۷ باید سیاست `persons` مالکیت‌آگاه شود (مثلاً: `sales` فقط
اشخاصی را ببیند که یک `person_context_links` فعال به یک ردیف `customers` با
`responsible_id = uid()` دارند).

### B1.8 — یادداشت‌های حساس

**وضعیت: موجود ولی ناقص — زیرساخت سطح‌بندی هست، ولی روی یادداشت اعمال نمی‌شود.**

- `persons.notes` یک ستون `text` تکی است (`information_schema.columns`).
- **هیچ بُعد محرمانگی روی خود یادداشت وجود ندارد** — نه سطح، نه مخاطب، نه تاریخچه.
- محافظت فقط از `visibility_scope` **کل شخص** می‌آید.

نکتهٔ مهم: سه سطح `visibility_scope` که از قبل در دیتابیس‌اند
(`internal_general` / `restricted_finance` / `restricted_executive`)
**تقریباً دقیقاً همان سه سطحی هستند که مالک برای یادداشت خواسته**
(«همه‌کسِ مجاز روی پروفایل» / «مدیرعامل و حسابدار» / «فقط مدیرعامل»).

⇒ معماری پیشنهادی: یک جدول یادداشت شخص با ستون `visibility_scope` که **همان CHECK
موجود را تکرار کند** و RLSاش دقیقاً از الگوی `persons_select_by_visibility_scope` پیروی کند.
این گسترش الگوی موجود است، نه اختراع تازه. مزیت جانبی: بالا بردن سطح یک یادداشت دیگر لازم
نمی‌کند کل شخص را از دید فروشنده پنهان کنیم.

**سوءاستفاده و ممیزی:** `persons_update_admin_manager` یعنی فقط admin/manager می‌توانند
`notes` را عوض کنند — که برای موارد «اتهام تخلف» و «بررسی محرمانهٔ مالی» زیادی محدود است
(حسابدار نمی‌تواند یادداشت بگذارد) و هم‌زمان زیادی باز است: **هیچ تاریخچه‌ای از تغییر
یادداشت نگه داشته نمی‌شود** و مسیر عمومی UPDATE روی `persons` در `audit_logs` ثبت نمی‌شود.

### دستهٔ تلویزیون — با شناسهٔ پایدار، نه با نام

**خبر خوب:** دسته با **شناسهٔ پایدار** مشخص می‌شود، نه با جست‌وجوی متنی نام.

| واقعیت | مقدار |
|---|---|
| ردیف دستهٔ تلویزیون | `1a738b6c-7188-4eb1-a3b7-1cb0881cf224` — «تلویزیون» |
| `products.category_id` | UUID، کلید خارجی به `categories` |
| `products.category` (متن) | **ستون مرده** — از ۳۵۵ محصول، **صفر تا** مقدار دارند |
| محصولات با `category_id` | ۳۵۰ از ۳۵۵ (۵ محصول بدون دسته) |
| محصولات دستهٔ تلویزیون | **۱۶** |
| سلسله‌مراتب دسته | `categories.parent_id` وجود دارد ولی **هر ۱۲ دسته `parent_id = NULL`** ⇒ ساختار امروز مسطح است |

⇒ **قاعده باید روی `category_id` نوشته شود.** استفاده از نام فارسی به‌عنوان قاعدهٔ اصلی

شود قاعده باید بازگشتی (`WITH RECURSIVE`) باشد. و ۵ محصول بدون `category_id` هیچ قاعده‌ای
نمی‌گیرند — باید تصمیم گرفت.

#### نکتهٔ حیاتی: کد فعلی Service Workerها را پاک می‌کند

`src/lib/cache-buster.ts:65-84`:

```ts
async function clearAllCaches() {
  if (typeof caches !== "undefined") {
    const keys = await caches.keys();
    await Promise.all(keys.map((k) => caches.delete(k)));   // کل Cache Storage
  }
  if (typeof navigator !== "undefined" && navigator.serviceWorker) {
    const regs = await navigator.serviceWorker.getRegistrations();
    await Promise.all(regs.map((r) => r.unregister()));      // لغو ثبت همهٔ SWها
  }
}
```

این کد عمداً نوشته شده تا مشکل «chunk کهنه» بعد از deploy را حل کند — و کارش را هم
درست انجام می‌دهد. ولی معنایش این است که **هر Service Workerی که فردا اضافه شود، توسط
همین مکانیزم پاک خواهد شد** مگر اینکه هم‌زمان بازطراحی شود.

**پاسخ صریح به پرسش «آیا Service Worker می‌تواند نسخهٔ کهنه سرو کند؟»**
امروز **خیر** — چون اصلاً Service Workerی وجود ندارد.
اگر فردا اضافه شود، **بله، و این ریسک اصلی است.** استراتژی به‌روزرسانی درست برای این پروژه
از قبل نیمه‌ساخته است: `api.version.ts` نسخه را برمی‌گرداند و `cache-buster.ts` منطق
تشخیص کهنگی را دارد. ترکیب درست: SW با استراتژی
**`network-first` برای HTML/ناوبری و `stale-while-revalidate` برای دارایی‌های hash‌دار**،
به‌علاوهٔ نظرسنجی نسخه از `/api/version` و پیام «نسخهٔ جدید موجود است — بارگذاری مجدد».

**توصیهٔ متمرکز بر خواستهٔ مالک (نصب روی صفحهٔ اصلی، اجرای اپ‌گونه، ورود سریع، بدون آفلاین کامل):**

| هدف | حداقل کار لازم | مانع |
|---|---|---|
| نصب روی صفحهٔ اصلی | manifest + آیکون‌ها + `display: standalone` | **HTTPS** |
| اجرای اپ‌گونه | همان manifest | همان |
| ورود سریع | امروز هم کار می‌کند (نشست Supabase پایدار است) | — |
| رابط مناسب موبایل | بخش C3.1 | — |

| آپلود مستقیم از دوربین | C3.4 — **بدون PWA هم ممکن است** | — |
| دسترسی سریع به وظایف/همکاری | افزودن `purchase_specialist` به `SHORTCUTS_BY_ROLE` | — |

⇒ **بزرگ‌ترین مانع PWA در این پروژه فنی نیست، زیرساختی است: نبود HTTPS.**

افراکالا یک monolith بالغ و پرحجم است: ۲۱۳ جدول، ۴۵۳ مهاجرت، بیش از ۱۸۰ مسیر صفحه،
۴۶ فایل تست Playwright با ۱۲۸ تست. زیرساخت‌های سختِ کار — RLS سراسری، RPCهای اتمیک،
ممیزی، نرمال‌سازی فارسی در دیتابیس، Realtime، Storage خصوصی — **ساخته شده‌اند و کیفیت
بالایی دارند**.

الگوی غالبِ یافته‌های این ممیزی یک الگوی تکرارشونده است و باید صریح گفته شود:

> **مشکل اصلی این پروژه «نبودِ قابلیت» نیست؛ «وصل‌نبودنِ قابلیت‌های ساخته‌شده» است.**

سه نمونهٔ گویا:
- موتور معیار/وزن/امتیاز کامل ساخته شده — ولی به `persons` وصل نیست و فقط دو `entity_type` می‌شناسد.
- سیستم وظیفه با شاخص‌های عملکرد ساخته شده — ولی **صفر ردیف** دارد.
- سیستم تطبیق محصول خارجی با امتیاز اطمینان و گردش بررسی ساخته شده — ولی واتساپ به آن وصل نیست.

### مهم‌ترین قابلیت‌هایی که وجود دارند

1. **هستهٔ هویت یکپارچه** — `persons` + شناسه‌های نرمال‌شده + `person_context_links` +
   ادغام با RPC و رابط بررسی. برای مشتری/تأمین‌کننده/طرف‌حساب کامل است.
2. **موتور امتیازدهی پویا با وزن نسخه‌دار** — `dynamic_*` + `calculate_dynamic_score` با
   `breakdown` کامل.
3. **تخصیص روزانهٔ سرمایه با snapshot و `formula_version`** — کامل و در حال کار (۱۸۲ ردیف).
4. **زنجیرهٔ دریافت پول** — فیش، OCR، تخصیص جزئی به چند فاکتور، وضعیت ثبت سند، خروجی اکسل.
5. **ماژول همکاری** — گروه، پیوست ویدیو، Realtime، رسید خواندن، جست‌وجوی معنایی، بورد استعلام.
6. **پل واتساپ (AfraPayam)** — proxy سمت سرور با گارد نقش دولایه، timeout و adapter سازگار با گذشته.
7. **ورود دسته‌ای اشخاص** با تشخیص تکراری و **رد ادغام خودکار** — دقیقاً مطابق خواستهٔ مالک.

### مهم‌ترین ریسک‌ها

۱. **تغییر وزن در ماه جاری، امتیاز همان ماه را بازگشت‌ناپذیر عوض می‌کند** — و بلافاصله
   تخصیص سرمایه را هم بازمحاسبه می‌کند. اثر مالی مستقیم.
۲. **`VITE_SUPABASE_URL` build-time است** ⇒ جابه‌جایی به سرور تولید بدون rebuild ممکن نیست،
   و اگر env در زمان build ست نباشد، اپ **بی‌صدا به یک پروژهٔ Supabase ابری** وصل می‌شود.
۳. **دو موتور امتیاز مشتری هم‌زمان زنده‌اند** (`dynamic_*` روی `customers.id` و
   `credit_*` روی `customer_person_id`).
۴. **سه لنگرگاه هویتی** (`persons` / `profiles` / `auth.users`) ⇒ خطر شمارش دوباره در هر
   گزارش مالی شخص‌محور.
۵. **`/api/healthz` ثابت `{ok:true}` برمی‌گرداند** ⇒ پایش، قطعی دیتابیس یا افراپیام را نمی‌بیند.

### مهم‌ترین وابستگی‌ها

```
[۱] profiles ↔ persons ──┬──► نیاز ۲۲۱ (گروه، پروفایل جامع، امتیاز شخص‌محور)
                          ├──► C2.12 امتیاز دستی روی شخص
                          └──► C2.13 اعتبار بدون شمارش دوباره

[۲] سرویس محصول در سطح ردیف ──┬──► نیاز ۲۲۲ (رسانه، وظیفه، ارسال به مشتری)
                                └──► نیاز ۲۲۳ (بسته‌بندی اجباری تلویزیون)

[۳] HTTPS / زیردامنه ──┬──► نیاز ۲۲۶ (PWA، نصب روی صفحهٔ اصلی)
                        └──► نیاز ۲۲۰.۲ (جابه‌جایی سرور بدون rebuild)

[۴] snapshot + زمان‌بند سمت سرور ──► نیاز ۲۲۰ (تصمیم‌های ۲ و ۳ مالک)
```

### ترتیب توسعهٔ پیشنهادی (خلاصه — جزئیات در D9)

**اول کارهای کوچک با اثر بزرگ و ریسک نزدیک صفر**، بعد پیش‌نیازهای ساختاری، بعد قابلیت‌های نو:

1. رفع سقف ۱۵۰ و افزودن جست‌وجو (چند ده خط، ریسک نزدیک صفر، اثر فوری روی نیاز ۲۲۰).
2. رفع تناقض ویدیوی رسید تحویل + افزودن `capture` + افزودن `purchase_specialist` به ناوبری موبایل.
3. بستن حفرهٔ دسترسی `persons` و اصلاح شاخهٔ UPDATE وزن.
4. اتصال `profiles ↔ persons` (پیش‌نیاز بزرگ).
5. مفهوم سرویس محصول در سطح ردیف (پیش‌نیاز بزرگ دوم).
6. snapshot و زمان‌بند واتساپ.
7. PWA (وابسته به HTTPS).

### موجودیت‌های جدیدی که این ممیزی لازم می‌داند — و اثبات پنج‌گانه

طبق قاعدهٔ پرامپت، برای هر موجودیت جدید باید هر پنج شرط ثابت شود.
**فقط دو موجودیت از این آزمون عبور می‌کنند:**

#### الف) «سرویس محصول در سطح ردیف»

| شرط | اثبات |
|---|---|
| ۱. مدل مشابهی وجود ندارد | grep روی ۴۵۳ مهاجرت برای `service|instruction|checklist|packaging|بسته‌بندی` صفر نتیجه؛ `sales_quote_items` و `invoice_items` هیچ ستون سرویس ندارند |
| ۲. مدل موجود قابل گسترش نیست | `tasks` یک وظیفه است نه یک الزام سند؛ نمی‌تواند «این ردیف باید بسته‌بندی شود» را به‌عنوان بخشی از سند نگه دارد و در PDF چاپ شود. `documents` فایل است نه الزام. |
| ۳. گسترش، coupling خطرناک می‌سازد | افزودن ستون سرویس به `sales_quote_items` یعنی هر سرویس جدید = یک مهاجرت ستونی؛ و «چند سرویس روی یک ردیف» با ستون ممکن نیست |
| ۴. مرز مسئولیت روشن است | «چه کاری روی چه ردیفی از چه سندی باید انجام شود، اجباری است یا اختیاری، و چه کسی مسئول است» — متمایز از `tasks` (اجرا) و `documents` (نتیجه) |
| ۵. مسیر مهاجرت روشن است | جدول نو، بدون دادهٔ تاریخی؛ `tasks` صفر ردیف دارد؛ اتصال از طریق `tasks.reference_type='product_service'` و `documents.reference_type='product_service'` |

#### ب) «قالب وظیفهٔ تکرارشونده»

| شرط | اثبات |
|---|---|
| ۱. مدل مشابهی وجود ندارد | `tasks` هیچ ستون `recurrence`/`rrule` ندارد؛ هیچ جدول قالب در ۲۱۳ جدول نیست |
| ۲. مدل موجود قابل گسترش نیست | افزودن `recurrence` به `tasks` یعنی هر نمونهٔ روزانه، قاعدهٔ تکرار را کپی می‌کند و ویرایش قاعده روی نمونه‌های گذشته اثر می‌گذارد |
| ۳. گسترش، coupling خطرناک می‌سازد | همان — قاعده و نمونه دو چرخهٔ عمر متفاوت دارند |
| ۴. مرز مسئولیت روشن است | قالب = «چه چیزی هر روز باید ساخته شود»؛ `tasks` = «نمونهٔ امروز» |
| ۵. مسیر مهاجرت روشن است | `tasks` صفر ردیف؛ کانال از `marketing_channels` می‌آید؛ job از `automation_jobs` |

**هر موجودیت جدید دیگری در این گزارش رد شد** — همه از طریق گسترش ماژول موجود قابل تأمین‌اند.

## D8 — تصمیم‌های باقی‌ماندهٔ مالک

فقط پرسش‌هایی که (الف) از کد قابل پاسخ نیستند، (ب) تصمیم کسب‌وکاری واقعی‌اند،
و (ج) بدون آن‌ها سند اجرا ناقص می‌ماند.

### ۱. «مدیر نباید سقف را override کند» دقیقاً در چه سطحی؟

- **چرا لازم است:** `daily_capital_snapshots` امروز سه ستون `system_suggested_capital`،
  `final_capital` و `override_reason` دارد — یعنی override **عمداً ساخته شده و ممیزی می‌شود**.
- **کدام تصمیم معماری را عوض می‌کند:** اگر منع در سطح «سرمایهٔ کل روز» باشد، باید این سه
  ستون بازنشسته یا قفل شوند و یک شکست عقب‌گرد در چرخهٔ مالی رخ می‌دهد. اگر منع فقط در
  سطح «سقف یک فروشنده/مشتری» باشد، هیچ تغییری لازم نیست.
- **توصیهٔ کارشناسی:** override در سطح **سرمایهٔ کل روز** باقی بماند (چون یک ورودی
  کسب‌وکاری است، نه دور زدن فرمول) و منع در سطح **سقف فردی** اعمال شود.

### ۲. آیا یک شخص می‌تواند بیش از یک «طرف حساب خارجی» باشد؟

- **چرا لازم است:** `external_parties.person_id` عمداً UNIQUE نشد (PROGRESS.md).
- **کدام تصمیم را عوض می‌کند:** بدون UNIQUE، هر تجمیع مالی روی `person_id` در معرض
  شمارش دوباره است (D6 ریسک ۵).
- **توصیه:** UNIQUE شود، مگر اینکه مالک نمونهٔ واقعی «یک شخص، دو طرف‌حساب مستقل» داشته باشد.

### ۳. آیا کارمند باید یک `persons` هم داشته باشد؟

- **چرا لازم است:** تصمیم ۹ مالک بدون این از نظر داده‌ای ناممکن است. ولی این یک
  مهاجرت هویتی است که ۱۲ جدول `employee_*`/`tasks`/`profiles` را لمس می‌کند.
- **کدام تصمیم را عوض می‌کند:** کل ترتیب فازها. اگر «نه»، نیاز ۲۲۱ باید به دو سیستم
  پروفایل جدا تقسیم شود (داخلی و بیرونی) که خلاف روح نیاز است.
- **توصیه:** **بله** — ولی به‌صورت **افزایشی**: فقط `profiles.person_id` اضافه و پر شود
  و `staff_link` ساخته شود؛ هیچ ستون یا کلید موجودی جابه‌جا نشود.

### ۴. سطح توصیفی امتیاز چه آستانه‌هایی دارد؟

- **چرا لازم است:** تصمیم ۱۳ مالک «عالی / قابل اعتماد / متوسط / پرریسک» را نام برده،
  ولی مرزهای عددی مشخص نیست و `calculate_dynamic_score` فقط عدد برمی‌گرداند.
- **کدام تصمیم را عوض می‌کند:** آستانه‌ها باید **داده** باشند (جدول قابل ویرایش) یا
  **کد** (ثابت). اگر داده باشند، باید نسخه‌دار شوند وگرنه همان مشکل تصمیم ۱۲ تکرار می‌شود.
- **توصیه:** جدول آستانه با `valid_from`/`valid_to`، دقیقاً مثل `dynamic_parameter_weights`.

### ۵. امتیاز دستی «منقضی نمی‌شود» یعنی در محاسبهٔ هر ماه بیاید یا فقط در تاریخچه بماند؟

- **چرا لازم است:** امروز امتیاز به `period_month` قفل است (تناقض ۷ در D4).
- **کدام تصمیم را عوض می‌کند:** اگر «در محاسبهٔ هر ماه بیاید»، مدل داده باید از
  «امتیاز ماهانه» به «رویداد ماندگار با اثر تجمعی» تغییر کند — یک بازطراحی واقعی.
  اگر «فقط در تاریخچه بماند»، تغییر کوچک است.
- **توصیه:** رویداد ماندگار با **اثر میرا** (مثلاً وزن کامل در ۳ ماه اول، کاهنده پس از آن)
  تا یک اشتباه قدیمی برای همیشه شخص را تنبیه نکند — ولی این خودش نیازمند تأیید مالک است.

### ۶. آیا خروجی اکسل باید با قالب ورودی آسان دقیقاً منطبق شود؟

- **چرا لازم است:** طبق دستور پرامپت، تصمیم نهایی گرفته نشد. مالک گفته نمونهٔ واقعی خروجی
  آسان را دارد.
- **کدام تصمیم را عوض می‌کند:** یک «حالت خروجی آسان» جدا از «حالت خروجی انسانی»،
  یا جایگزینی کامل خروجی فعلی.
- **توصیه:** **حالت جدا**. خروجی فعلی برای انسان بهینه است و نباید خراب شود.
  پیش‌نیاز: دریافت فایل نمونهٔ آسان.

### ۷. HTTPS برای PWA — آیا سازمان حاضر به دامنه/گواهی داخلی است؟

- **چرا لازم است:** بدون HTTPS، **Service Worker ثبت نمی‌شود و گزینهٔ نصب ظاهر نمی‌شود**.
  این یک محدودیت مرورگر است، نه انتخاب پیاده‌سازی.
- **کدام تصمیم را عوض می‌کند:** اگر «نه»، نیاز ۲۲۶ به «موبایل‌پسند کردن» تقلیل می‌یابد و
  بخش PWA باید تا زمان دامنهٔ واقعی معلق بماند.
- **توصیه:** یک زیردامنهٔ داخلی + گواهی (حتی داخلی) — که هم‌زمان مسئلهٔ نیاز ۲۲۰.۲ را هم حل می‌کند.

### ۸. آیا انبار باید در سطح ردیف انتخاب شود؟

- **چرا لازم است:** «ساخت پیش‌فاکتور از انبارهای مختلف» دو تفسیر دارد: (الف) کاربر بتواند
  انبار سند را انتخاب کند (امروز هست)، (ب) هر ردیف انبار خودش را داشته باشد (نیست).
- **کدام تصمیم را عوض می‌کند:** تفسیر (ب) یعنی تغییر `sales_quote_items` و `purchase_items`
  و بازنویسی منطق کنترل موجودی در قطعی‌سازی.
- **توصیه:** تفسیر (ب) — چون بدون آن، سفارشی که کالاهایش در دو انبار است باید شکسته شود.
