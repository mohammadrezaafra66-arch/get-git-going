## The partial-payment model, and why

**[U] The owner's instruction was explicit:** reuse `payment_vouchers.purchase_id` + `amount` unless
they provably cannot carry the semantics — *"A new table when an existing column fits is the failure
this programme exists to prevent."* The bar set was to read **every** caller first.

**Path taken: reuse. No new table.** [E] The column already had an FK to `purchases`, a partial index,
and **no unique constraint**; and the newer of its two writers, `create_payment`, already inserted it
with no duplicate guard and without stamping `paid_at` — i.e. the schema had already stopped treating
the link as all-or-nothing. All 12 existing vouchers carry `purchase_id IS NULL`, so **no data
migration was required either way.**

```sql
LEFT JOIN LATERAL (
  SELECT COALESCE(sum(pv.amount) FILTER (
           WHERE pv.status = 'approved' AND pv.reversed_at IS NULL), 0) AS confirmed_paid_amount, ...
) vp ON true
-- outstanding:
WHEN vp.voucher_linked THEN GREATEST(COALESCE(p.total_amount,0) - vp.confirmed_paid_amount, 0)
```

The `reversed_at IS NULL` filter matters: a **reversed** voucher correctly stops counting as paid.
`is_paid` was re-keyed from `paid_at IS NOT NULL` to `outstanding_amount <= 0`, which is why a reversal
reopens the debt even though `paid_at` remains stamped.

## Deviations from the brief — each deliberate, each flagged

1. **`group: "finance"`, not `"accounting"`.** The brief specified `accounting` for the registry row.
   `"accounting"` is **not a member of `NavigationGroupKey` at all**, and every live neighbour uses
   `finance`. Live code won.
2. **No migration 485, and no `role_permissions` seed.** The brief anticipated one ("`has_dynamic_permission`
   fails open without one"). Measured: the `accounting` module already grants `can_view` to exactly
   `admin, manager, accountant` and denies the other four roles; the registry keys off `module`, so the
   new entry inherits the right three. A seed would have been a duplicate.
3. **`has_any_role(uuid, text[])` rather than `::app_role[]`.** `compute_daily_capital` and
   `dual_documents` use the enum-array overload; `user_roles.role` is TEXT and the `app_role[]` overload
   casts straight back to `text[]`. The text form cannot raise on a role string that is not an enum
   label — one fewer failure mode.
4. **The demonstration ran on today's date, not `2026-07-22`.** The brief expected the headline to be
   silent for any date lacking a `daily_capital_inputs` row. Measured: `compute_daily_capital` returns
   real figures for today (`overdue_receivables 1,616,300,000`, `overdue_payables 37,091,243,925`); the
   2-row limitation only silences the *suggestion card* on `/accounting/dynamic-capital`, a different page.
5. **`pw.auth.config.ts` is tracked in git** despite its own comment saying "Not committed", and its
   `testMatch` sweeps in `save-admin-session.spec.ts`, which calls `page.pause()` and writes an **empty**
   session. Left untouched; the generator was invoked with an explicit file path instead.

## A behaviour change the owner should see

The default payment amount remains `COALESCE(_amount, cash_price, total_amount)`, because migration 457
explicitly considered that expression and declined to change it [P]. Consequence: for the single
purchase carrying a `cash_price` — `ba1c75a0-d406-4389-ac4f-e1501dbbe915`, `cash_price` 10bn against a
`total_amount` of 12bn — the purchase-payments page, which sends no amount, now pays 10bn and leaves
**2,000,000,000 outstanding with `paid_at` NULL**, where previously it marked the purchase fully paid.

[E] That is **1 of 317** purchases, and all 317 are test data, so live impact is nil. The semantics did
change, and whether that default is right is the owner's call.

Separately, `is_paid` re-keyed to `outstanding_amount <= 0` is a no-op on today's data (0 of 317 have
`paid_at`; none has `total_amount <= 0`), but a future purchase with `total_amount = 0` would newly
report as paid.

## Session harness — a fault found and repaired

All four `e2e/auth/*.storage.json` were **expired by ~14.4 hours** at dispatch. Regenerating them
exposed a hole in the generator: it calls `setPasswordViaAuthAdmin` **only when `usingProvidedPasswords`
is false** (`generate-role-sessions.spec.ts:383-385`). With `E2E_*_PASSWORD` set it skips the reset and
merely logs in — so `test.sales2@afrakala.local`, still carrying a random ephemeral password from a
wave-4 run, returned **400 invalid_grant**, and its storage file had already been deleted (all four are
unlinked up-front, line 363).

Repaired by resetting that one account through the Auth Admin API. **All six documented accounts now
return HTTP 200 on the documented password.** This is the same class of breakage wave 4 left on
`test.accountant`; it will recur until the generator resets passwords unconditionally.

inside `BEGIN … ROLLBACK`:

```
before:  outstanding 12,000,000,000 | paid_at NULL

CLICK 1 — exactly what the page sends (purchaseId + bank account, no amount)
  -> confirmed_paid 10,000,000,000 | outstanding 2,000,000,000 | paid_at NULL
     is_paid f | is_overdue t | aging_bucket d1_30

CLICK 2 — the identical call, the only thing the UI can do
  REFUSED: مبلغ پرداخت از ماندهٔ بدهی این خرید بیشتر است؛ ماندهٔ بدهی 2000000000.00 است.

final:   outstanding 2,000,000,000 | paid_at NULL | is_overdue t
```

**Why it is a regression, not a quirk.** Pre-478 the RPC ran
`UPDATE purchases SET paid_at = COALESCE(paid_at, now())` **unconditionally**, so that same click
closed the purchase. Post-478 it is conditional on reaching zero. `_amt` is always `cash_price` (10bn)
while the remainder is 2bn, so `_amt > _outstanding` **forever** — the purchase can never be brought to
zero from the UI, and it now accrues an overdue bucket.

**Consequence:** the accountant pays, the purchase does not leave the payables list, and every retry
throws a Persian error. It also means **478's partial-payment capability has no UI at all** — it is
reachable only by hand-crafting an RPC call.

**Why P-3's `EXCEPT` could not catch it:** that check compares *current state* before and after the
migration. This defect is in *what the next write does*. Both build agents' proofs passed an amount
explicitly; neither exercised the no-amount path the page actually uses.

**Scope, measured:** exactly **1 of 317** purchases carries a `cash_price` differing from
`total_amount`, and all 317 are test data — so nothing is broken for a real user *today*. The defect
lives in the code path, and it will bite the first real purchase that has a `cash_price`.

🔴 **This is a halt condition** under the mission brief ("a `pay_purchase_with_voucher` caller
breaking"). **No fix was improvised.** Options, for the owner to choose:

1. **Clamp the implicit amount** — `_amt := LEAST(_amt, _outstanding)` when `_amount IS NULL`. Restores
   the old "pay it off" click while keeping an explicit over-payment an error. Smallest change; still a
   behaviour decision, because migration 457 deliberately kept the `COALESCE` (lines 65–69).
2. **Give the page an amount field** — the honest fix, and the thing that makes 478 usable at all.
   Larger, and already on the handed-forward list.
3. **Both.** (1) stops the bleeding now; (2) delivers the feature.

## 🔴 REFUTED · A-3 — "every change logged" is not enforced where writes are actually allowed

**Claim:** migration 481 grants `authenticated` full DML and adds RLS letting `admin`/`accountant`
INSERT and UPDATE directly, but **only DELETE has an audit trigger**. INSERT and UPDATE are audited
inside the RPC bodies only, and nothing forces callers through them.

**Reproduced by the orchestrator.** Triggers on `allocation_rows`:

```
trg_allocation_rows_updated_at           UPDATE          (not audit)
trg_allocation_rows_derive_payer_person  INSERT, UPDATE  (not audit)
trg_allocation_rows_audit_delete         DELETE          <- the ONLY audit trigger
```

As `test.accountant`, writing directly to the table inside `BEGIN … ROLLBACK`:

```
UPDATE 1     -- amount -> 999999999, status -> 'جواب نمی‌ده'
INSERT 0 1   -- a whole new allocation row
NEW AUDIT ROWS: 0

control DELETE -> NEW AUDIT ROWS: 1     (so the counting method is sound)
```

Agent V additionally proved it over the real network with a genuine `test.accountant` bearer token
through Kong (`PATCH … -> 200`, audit rows unchanged at 4).

**Consequence:** that token sits in every accountant's `localStorage`. Anyone holding one can rewrite an
allocation's amount, status, priority, promise date or account number — or fabricate rows — and leave no
trace. CLAUDE.md rule 6 says frontend-only authorization is unacceptable; here the **audit trail** is
effectively frontend-only, holding only because `src/lib/allocation/queries.ts` happens to use `.rpc()`
and never `.from("allocation_rows")`. Spec 217 exercises only the RPC path, so it cannot see this.

**[U] This matters more than a typical gap** because "every change is logged" is a *standing* owner
requirement, not a wave-5 nicety.

**Not fixed** — same halt discipline. The shape of a fix is an `AFTER INSERT OR UPDATE` audit trigger
mirroring the existing DELETE one, so the trail holds regardless of path, and/or narrowing the
`authenticated` grant so the RPCs become the only write path.

## ⚠️ V's own protocol breach, disclosed by V

While probing A-3 over PostgREST, V sent a `PATCH` as `test.accountant`. **PostgREST commits** — unlike
its psql work, this was not in a transaction — changing the residue row to `amount=424242,
status='جواب نمی‌ده'`. It reverted through the same channel within ~60 seconds and verified every field
restored. Orchestrator-confirmed: the row now reads `amount=1000`, `status='شنبه واریز می‌کنه'`,
`promised_at=2026-09-05`, `IR-UI-DRIVE`, `priority='urgent'`.

**One field could not be restored:** `updated_at` now reads `2026-09-06 14:18:55+00` instead of
`~13:40:34+00`. Restoring it would need `ALTER TABLE … DISABLE TRIGGER`, which V correctly refused to do.

V disclosed this unprompted, at the top of its report. That is the behaviour you want from a verifier —
but the lesson is worth recording: **a verification brief must state that PostgREST commits, and that
write-probes belong inside psql transactions.** No other application data was written.

## A methodological note worth keeping

V's first anon RPC sweep sent `{}` and got **404 PGRST202** for five of six functions. That is a
*signature-resolution miss*, not a refusal — and a lazy reviewer would have banked it as "closed". V
re-sent with resolvable named parameters and got true `401`s. Any future anon sweep should assert on
**401**, never merely on "not 200".
