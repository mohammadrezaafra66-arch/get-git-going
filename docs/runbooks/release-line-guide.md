## ۰ · چرا این خط انتقال وجود دارد

روز ۲۲ شهریور ۱۴۰۵ یک image که روی **کامپیوتر تست** ساخته شده بود روی **لپ‌تاپ production** مستقر شد. آدرس Supabase در زمان build داخل باندل جاوااسکریپت پخته شده بود، پس مرورگر هر کارمند به `http://192.168.170.8:9000` — یعنی Kong ماشین **تست** — وصل شد.

حدود ۹۰ دقیقه، پرسنل روی دیتابیس تست **می‌خواندند و می‌نوشتند**.

فایل `.env.lan` روی production تمام مدت **درست** بود. مقادیرش build arg بودند و deploy با `--no-build` انجام شد، پس هرگز اعمال نشدند. هیچ چکی به **داخل image** نگاه نکرد.

### سه درس

**۱. هر ادعا باید روی همان سطحی سنجیده شود که کاربر تجربه می‌کند.** یک فایل env درست، یک باندل غلط را نجات نمی‌دهد.

**۲. یک probe که هرگز شکست نخورده، هیچ‌چیز را اثبات نمی‌کند.** چهار دور بازبینی مستقل روی همین کد **نُه probe شکسته** پیدا کرد — کدی که در نگاه اول کاملاً درست به نظر می‌رسید.

**۳. چیزی که خودش خودش را نمره می‌دهد، قابل اعتماد نیست.** سازنده نوشت «رفع شد» و بازبین ثابت کرد نشده. ابزار `apply-release.ps1` نوشت `PASSED` در حالی که یک دروازه شکست خورده بود.

## ۳ · قاعده‌های غیرقابل مذاکره

۱. **توسعه هرگز روی `C:\afrakala`.** آن checkout تولید است.
۲. **هرگز `--squash` برای رفتن به `main`.** مسیر: `feature/*` → `staging` → fast-forward به `main`.
۳. **`--no-deps` در هر `docker compose up`.** بدون آن کل استک پایین می‌آید.
۴. **`git pull` قبل از `up -d`.** compose قدیمی مقادیر runtime را پاس نمی‌دهد.
۵. **بعد از هر مهاجرت: `docker restart afrakala-lan-rest`.** PostgREST فقط در startup schema را می‌خواند.
۶. **SQL فارسی فقط با `docker cp` + `psql -f`.** هرگز از pipe پاورشل.
۷. **خروجی ترمینال فقط انگلیسی.** فارسی در ترمینال برعکس می‌شود.
۸. **هر exit code روی خط خودش از `$LASTEXITCODE`.** هرگز از `$?`، هرگز از داخل pipe. (`cmd | head` کد خروجی `head` را می‌دهد — این اشتباه سه بار در سه روز تکرار شد.)
۹. **بدون `&&`، `||`، ternary و `??`.** PowerShell 5.1 هیچ‌کدام را ندارد.
۱۰. **بدون double quote داخل رشتهٔ single-quoted `sh -c`.** پاورشل ۵٫۱ آن را می‌بُرد و متغیر `$null` برمی‌گردد — و `$null -notmatch` مقدار False می‌دهد، یعنی چک بدون سنجیدن چیزی OK چاپ می‌کند.
۱۱. **رول‌بک image از پیش مجاز است. رول‌بک دیتابیس هرگز.**
۱۲. **هرگز ردیف لجر برای مهاجرتی که اجرا نشده.** این دقیقاً باگ ۵۲۶ بود: ردیف نوشته شد، SQL اجرا نشد، و نُه ترمیم ماه‌ها غایب ماندند در حالی که همه فکر می‌کردند اعمال شده‌اند.
۱۳. **درخت کاری باید تمیز باشد.** `GATE PULL` روی هر فایل untracked می‌ایستد. قبل از release، فایل‌های سرگردان را روی یک شاخهٔ جدا commit کن — پاک نکن.

## ۴ · مکانیزم runtime config

### مشکل

`vite.config.ts` با `define` مقدار `import.meta.env.VITE_SUPABASE_URL` را در زمان build با یک رشتهٔ ثابت جایگزین می‌کرد. یعنی آدرس ماشین سازنده داخل باندل می‌پخت. این از commit `1adbfbc9` (۱۱ اردیبهشت) بود — چهار ماه قبل از حادثه.

### راه‌حل

`src/lib/runtime-config.ts` مقادیر را در زمان اجرا از محیط کانتینر می‌خواند. `src/routes/__root.tsx` آن‌ها را به‌صورت `window.__APP_RUNTIME_CONFIG__` داخل `<head>` تزریق می‌کند، **پیش از هر chunk جاوااسکریپت**.

ترتیب خواندن آدرس:
```
APP_SUPABASE_PUBLIC_URL  →  VITE_SUPABASE_URL  →  SUPABASE_URL
```

### چهار مقدار runtime

| کلید | معنی |
|---|---|
| `APP_SUPABASE_PUBLIC_URL` | آدرسی که **مرورگر** به آن می‌رسد |
| `SUPABASE_PUBLISHABLE_KEY` | کلید anon |
| `VITE_APP_ENV` | `production` یا `test` — بنر را کنترل می‌کند |
| `VITE_TRUSTED_HOSTS` | میزبان‌های مورد اعتماد — بنر قرمز را کنترل می‌کند |

### اثبات — ۲۳ شهریور، اندازه‌گیری‌شده

همان image `b67d27106ce4` روی هر دو ماشین:

| | production | تست |
|---|---|---|
| `supabaseUrl` | `http://192.168.170.10:8000` | `http://192.168.170.8:9000` |
| `appEnv` | `production` | `test` |
| بنر زرد | **نیست** | **هست** |

**یک باندل، دو رفتار.** این کل هدف کار بود.

### دام

`SUPABASE_URL` روی هر دو ماشین `http://kong:8000` است — نام داخلی شبکهٔ Docker. **هیچ مرورگری آن را resolve نمی‌کند.** اگر `APP_SUPABASE_PUBLIC_URL` خالی باشد، کد به آن می‌افتد و همهٔ صفحه‌ها خالی بالا می‌آیند، در حالی که `healthz` سبز است.

`GATE D10` دقیقاً این را می‌گیرد — و فقط **بعد** از deploy می‌تواند بگیرد.

## ۵ · دروازه‌ها

هر دروازه یک ناحیهٔ `& { ... }` است. **کل ناحیه را یکجا paste کن**، از خط `& {` تا آکولاد بسته.

یک دروازهٔ شکست‌خورده `GATE <id> FAIL <reason>` چاپ می‌کند، `throw` می‌زند، و **پنجره را نمی‌بندد**. شکست در `$global:AFRAKALA_FAILED_GATES` ثبت می‌شود و هر ناحیهٔ بعدی که وضعیت را تغییر می‌دهد، `NOT RUN` چاپ می‌کند و اجرا نمی‌شود.

**این رکورد فقط در همان پنجره زندگی می‌کند.** پنجرهٔ جدید = دروازه‌ها را از اول بزن.

> **چرا `throw` و نه `exit 1`:** اندازه‌گیری شد که `exit 1` در کنسول تعاملی پنجره را می‌بندد و دلیل شکست را با خودش می‌برد. Windows Terminal متن را نگه می‌دارد ولی shell را می‌کشد. هر دو غیرقابل قبول‌اند.

| دروازه | چه چیزی را اثبات می‌کند | چرا وجود دارد |
|---|---|---|
| **PULL** | checkout روی `main` است، **تمیز** است، و به build sha fast-forward شده؛ compose مقادیر را در runtime پاس می‌دهد | بدون pull، compose قدیمی بنر تست می‌دهد حتی با image درست |
| **D1a** | `HEAD` برابر build sha، درخت تمیز | ۲۲ شهریور، release از commit اشتباه اجرا شد |
| **D1b** | هر فایل مهاجرت مجموعه روی دیسک هست | ۲۲ شهریور، ۱۱ از ۱۴ فایل غایب بود و run تا بلوک ۶ رفت |
| **L1** | لجر دقیقاً همان است که سند برایش emit شده؛ دیتابیس replica نیست | اگر دیتابیس بعد از emit تغییر کرده، سند دیگر معتبر نیست |
| **TAR** | tarball بایت‌به‌بایت همان است، در برابر **دو** هش مستقل | فایل خراب یا ناقص |
| **D2** | image **کانتینر در حال اجرا** به‌عنوان `:lan-rollback` تگ شد، **قبل** از جابه‌جایی `:lan`، و بعد از تگ **دوباره از کانتینر خوانده شد** | ترتیب قدیمی نام rollback را روی image جدید می‌برد — «رول‌بکی که به جلو می‌رود». و خواندن دوباره لازم است چون یک mutant که `:lan` را می‌خواند، بدون آن پاس می‌شد |
| **LOAD** | image لود شد و `APP_GIT_SHA` درست را دارد | تگ tarball ممکن است با انتظار runbook نخواند |
| **D3** | `:lan` و `:lan-rollback` **id متفاوت** دارند | اگر یکی باشند، رول‌بک هیچ کاری نمی‌کند |
| **D6(i)** | **هیچ** literal میزبانی در باندل client نیست — default-deny | این همان چیزی است که ۲۲ شهریور کسی نسنجید |
| **D6(ii)** | `__APP_RUNTIME_CONFIG__` در باندل هست | بدون آن، client هیچ آدرسی ندارد |
| **D6(iii)** | image با محیط این هدف، آدرس این هدف را سرو می‌کند — **برابری دقیق** | زیررشته کافی نیست: `.10` داخل `.100` هست |
| **D9** | میزبان سرو‌شده از **مرورگر** قابل دسترس است | یک image تمیز `http://kong:8000` سرو کرد و همهٔ چک‌های ساختاری پاس شدند |
| **D10** | **سایت زنده**، بعد از deploy، آدرس درست را به مرورگر می‌دهد | D6/D9 کانتینر خودشان را می‌سنجند — probe از خودش می‌پرسد |

### D6(i) چطور کار می‌کند — default-deny

یک باندل minified نمی‌تواند «آدرس واقعی» را از «متن راهنما» تشخیص دهد؛ هر دو رشته‌اند. پس probe حدس نمی‌زند:

- **همیشه رد می‌شود:** IP literal · پورت صریح · نام بدون نقطه (`kong`, `localhost`) · پسوند خصوصی (`.local`, `.lan`, `.internal`) · میزبان Supabase
- **متن راهنما** فقط به‌صورت **رشتهٔ دقیق** و تا **تعداد شمرده‌شده** مجاز است — اگر همان رشته به‌عنوان endpoint واقعی استفاده شود، رد می‌شود
- **هر میزبان دیگر** باید در فهرست بازبینی‌شدهٔ اشخاص ثالث عمومی باشد

**قاعدهٔ طلایی:** اگر D6 قرمز شد به‌خاطر عددی بالاتر از سقف، **سقف را بالا نبر**. اول بفهم چه چیزی آن occurrence جدید را وارد باندل کرد.

### تاریخچهٔ D6 — چهار دور، چهار فرار

| کد | فرار | رفع |
|---|---|---|
| B1 | `http://kong:8000` و `.supabase.co` پاس می‌شدند (regex فقط `IPv4:port` می‌گرفت) | default-deny |
| C6 | `Bz="192.168.170.8:9000"` + `"http://"+Bz` — بدون scheme | خواندن `host:port` بدون scheme |
| C7 | `$w="192.168.170.8"` بدون پورت | خواندن IPv4 نقل‌قول‌شدهٔ بدون پورت |
| F1 | `"//192.168.170.8"` با پورت جدا | پذیرفتن `/` قبل از quad |

**هر چهار بار، آدرس حادثه از probe رد شد.** هر بار یک بازبین مستقل پیدایش کرد، نه سازنده.

### شکاف‌های باقی‌مانده — ثبت‌شده، بسته‌نشده

- عدد ده‌دهی (`3232279048`) یا هگز (`0xC0A8AA08`)
- IP در **وسط** یک رشتهٔ بلندتر
- IPv6 خارج از یک URL با scheme

**قضاوت:** blocker نیست. حادثه **تصادفی** بود و مسیرهای تصادفی آدرس را به شکل URL یا `host:port` یا dotted-quad حمل می‌کنند — هر سه گرفته می‌شوند. این اشکال فقط با دست‌کاری عمدی قابل بهره‌برداری است، و کسی که دسترسی commit دارد راه‌های ساده‌تری دارد که هیچ اسکن متنی نمی‌گیرد (مثل `[192,168,170,8].join(".")`).

## ۶ · دو حالت release

### حالت معمولی — وقتی release مهاجرت دارد

نیازمند گزارش rehearsal با نتیجهٔ PASS. `release/rehearse.ps1` دامپ production را روی یک دیتابیس یک‌بارمصرف بازیابی می‌کند و هر مهاجرت را اجرا می‌کند. ساعت‌ها طول می‌کشد.

### حالت `-ImageOnly` — وقتی دیتابیس از قبل جلو است

اگر مهاجرت‌ها خارج از release روی production اعمال شده باشند، چیزی برای تمرین نیست. به‌جای rehearsal، یک **فایل شاهد لجر** می‌گیرد و رد می‌کند مگر اینکه:

۱. فایل شاهد با شمارش ردیف و بالاترین نسخهٔ ثبت‌شدهٔ هدف بخواند
۲. هر فایل مهاجرت روی دیسک یا ردیف لجر داشته باشد یا **تصمیم ثبت‌شده**
۳. هیچ ردیف لجری بدون فایل نباشد

هیچ بلوک مهاجرت و هیچ نوشتن لجری emit نمی‌کند.

> ⚠️ **این حالت روز ۲۳ شهریور نوشته شد و هیچ بازبینی مستقلی ندیده.** بلوک‌های PULL، L1، TAR، LOAD، rollback و sign-off همه از آن می‌آیند. سازنده خودش falsify کرد (`BROKEN_REFUSALS=0`)، ولی falsify کردن کار خود آدم جای بازبینی را نمی‌گیرد.

## ۷ · دستورالعمل اجرا

### روی کامپیوتر تست — ساخت بسته

```powershell
cd D:\AfraKalaTest\app
git fetch --all --prune
git worktree add ../wt-release-<date> origin/main
# .env.lan را داخل worktree کپی کن — gitignored است و build بدون آن رد می‌شود
npm run typecheck          # انتظار: ۷۰ خطا در ۶ فایل — baseline است نه regression
```

بعد `release/build.ps1` را اجرا کن — **زیر pwsh 7، نه ۵٫۱**.

> **چرا:** `release/build.ps1` روی خط `git fetch` با `$ErrorActionPreference = "Stop"` کرش می‌کند، چون PowerShell 5.1 خروجی stderr گیت را به خطای پایان‌دهنده تبدیل می‌کند. نقص شناخته‌شده.

> **یک اثر جانبی که باید بدانی:** `deploy/lan/docker-compose.yml` نام `afrakala-app:lan` را hardcode دارد، پس build تگ `:lan` را روی ماشین تست جابه‌جا می‌کند. بعد از build فوراً برگردانش. کانتینر در حال اجرا با image id پین شده، پس تحت تأثیر نیست.

سپس **قبل از اینکه بسته ماشین را ترک کند**، artifact را اثبات کن:

- باندل client و SSR را استخراج کن و literal های میزبان و JWT را بشمار
- image را با مقادیر production-shaped بالا بیاور و ببین چه سرو می‌کند
- همان را با مقادیر تست تکرار کن — **دو رفتار از یک image**
- D6 را روی یک باندل **خراب** بزن و ببین **شکست می‌خورد**

### روی لپ‌تاپ production — اجرای runbook

یک پنجرهٔ PowerShell، `cd C:\afrakala`، هر بلوک به ترتیب، در **همان** پنجره.

هر خط `Expect:` را **حرف‌به‌حرف** مقایسه کن. اولین اختلاف یعنی توقف.

**بلوک deploy هیچ دروازه‌ای ندارد** — خروجی `docker compose` را خودت بخوان.

### اگر SMB شکست خورد

کپی از `\\192.168.170.8\dumps\...` ممکن است `Invalid Signature` بدهد (خطای امضای SMB). راه‌حل: خودت فایل را ببر.

```powershell
Copy-Item -Path "\\192.168.170.8\dumps\release-<date>\*" -Destination "C:\afrakala-release\<date>\" -Force
```

هش باید با آنچه runbook انتظار دارد یکی باشد. بعد به agent بگو مرحلهٔ کپی را رد کند ولی **هر دو مقایسهٔ هش را انجام دهد** — فایل `.sha256` حالا کنار tarball روی همان ماشین است.

## ۱۰ · دام‌های فنی

- **RLS روی SELECT خطا نمی‌دهد** — بی‌صدا صفر ردیف برمی‌گرداند. «داده‌ای نیست» هرگز اثبات نمی‌کند که policy کار می‌کند.
- **RLS روی `security_invoker=true` هزینهٔ واقعی دارد.** یک `count(*)` روی ۱۲۰ هزار ردیف: ۲۲ میلی‌ثانیه به‌عنوان `postgres`، **۵٬۳۰۳ میلی‌ثانیه** به‌عنوان `authenticated`.
- **`CHECK` مقدار NULL را رد نمی‌کند.** یک کلید JSONB غایب یعنی NULL و مقایسهٔ NULL پاس می‌شود. `COALESCE(..., false)` و `IS DISTINCT FROM`.
- **`has_role` و `has_any_role` هرکدام دو overload دارند** و هیچ‌کدام قابل حذف نیست. فراخوانی از `supabase.rpc()` خطای `PGRST203` می‌دهد.
- **`user_roles.role` از نوع TEXT است** روی دیتابیس زنده.
- **`npm run typecheck` حدود ۳ دقیقه** و baseline آن ۷۰ خطا در ۶ فایل است. exit code آن ۲ است، نه ۰.
- **`npm run build` روی ویندوز شکسته است** — فقط داخل Docker.
- **بدون HTTPS:** `getUserMedia`، `crypto.randomUUID` و `crypto.subtle` کار نمی‌کنند.
- **`schema_full_export.sql` غیرقابل اتکاست.** از خروجی زندهٔ `pg_policies` و `pg_get_functiondef` استفاده کن.
- **کسب‌وکار روی `sales_quotes` است، نه `invoices`.** جدول `invoices` اصلاً روی production **وجود ندارد** — هر ارجاعی به آن خطای `PGRST200` می‌دهد.
- **ban کردن در GoTrue توکن‌های refresh موجود را باطل نمی‌کند** — ولی هر استفاده رد می‌شود. عملاً امن.
- **۳۳ از ۳۶ کاربر فیلد `aud` خالی دارند.** جست‌وجوی کاربر در GoTrue بدون هدر `X-JWT-AUD: authenticated` آن‌ها را پیدا نمی‌کند.

## ۱۱ · قواعد کار با agent

۱. **research و execution هرگز در یک قدم.** اول یک سند تحقیق فقط‌خواندنی، بعد یک پرامپت اجرا از روی یافته‌های تأییدشده.

۲. **هر کدی که چیزی را می‌سنجد، باید یک بار روی ورودی بد شکست بخورد.** و در **هر دو جهت** اثبات شود: هم روی ورودی بد شکست بخورد، هم روی ورودی سالم پاس شود. یک probe که همه‌چیز را رد می‌کند، به همان اندازه بی‌فایده است که یکی که همه‌چیز را قبول می‌کند — چون خاموشش می‌کنند.

۳. **agent هرگز کار خودش را نمره نمی‌دهد.** بازبینی توسط نشستی که کد را ننوشته و گزارش سازنده را **آخر** می‌خواند، نه اول.

۴. **شواهد برچسب‌دار:** `cited` (file:line) · `quoted` (خطوط عیناً با محلشان) · `measured` (دستور + خروجی + exit code جدا از pipe) · `compared` (یک probe روی دو چیز).

۵. **هر ادعا بدون این‌ها یک assertion است** و باید همان‌طور برچسب بخورد.

۶. **بخش «آنچه تأیید نشد» نباید خالی باشد** مگر واقعاً همه‌چیز سنجیده شده باشد — و اگر خالی است، بگوید چرا.

۷. **worktree جدا** برای هر agent موازی. صفر کار image. دیتابیس فقط‌خواندنی.

۸. **commit محلی بعد از هر قدم اثبات‌شده.** شاخه‌ها از `C:\afrakala` یا `D:\AfraKalaTest\app` بساز، **نه از پوشهٔ temp** — پاک می‌شوند و کار از بین می‌رود.

۹. **یک توقف در هر پرامپت.** بقیه از پیش مجاز. توقف‌های زیاد یعنی agent منتظر می‌ماند و تو خسته می‌شوی.

۱۰. **عدد ماشین را باور کن، نه عدد خودت.** چند بار پیش آمد که رقمی که من از حافظه گفتم با اندازه‌گیری نخواند — اندازه‌گیری برنده است.

## ۱۲ · بعد از deploy

### چک‌لیست امضا — دستی، در مرورگر

روی یک ماشین **پرسنل**، نه روی لپ‌تاپ سرور:

- [ ] صفحهٔ ورود بالا می‌آید و **هیچ بنری** نیست
- [ ] ورود کار می‌کند
- [ ] صفحات کلیدی بار می‌شوند و داده دارند
- [ ] اعداد فارسی‌اند
- [ ] **نقش‌های دیگر (حسابدار، فروشنده) چیزی از دست نداده‌اند**

**مهم‌ترین بند آخری است.** تنها چیزی که rollback را توجیه می‌کند، از دست رفتن دسترسی مشروع است.

### sweep خودکار — و محدودیت‌هایش

یک agent می‌تواند همهٔ مسیرها را GET کند. در اجرای ۲۳ شهریور: **۲۱۲ مسیر، ۱۳۹ سالم، صفر ERROR**.

برای مسیرهای نیازمند ورود، نشست باید **دستی** ساخته شود — agent نباید `JWT_SECRET` را بخواند:

```powershell
Get-Content C:\afrakala\deploy\lan\.env.lan | Where-Object { $_ -match '^\s*(JWT_SECRET|SUPABASE_PUBLISHABLE_KEY)\s*=' } | ForEach-Object { $k, $v = $_ -split '=', 2; Set-Item -Path ("env:" + $k.Trim()) -Value $v.Trim().Trim('"', "'") }; node <mint-script>; Remove-Item env:JWT_SECRET, env:SUPABASE_PUBLISHABLE_KEY -ErrorAction SilentlyContinue
```

**آنچه یک sweep نمی‌گیرد** — این فهرست را هر بار بخوان، چون PASS آن گمراه‌کننده است:

۱. هر چیزی که **می‌نویسد** — ثبت فیش، صدور پیش‌فاکتور، محاسبه و ذخیره
۲. هر چیزی پشت یک **کلیک** — دیالوگ، تب، فیلتر، صفحهٔ بعد، خروجی اکسل
۳. صفحاتی که داده را از **RPC** می‌گیرند (guard آن‌ها را بلاک می‌کند)
۴. **آپلود فایل** — OCR فیش، اسناد، ایمپورت آسان
۵. **نقش‌های دیگر** — sweep فقط با یک نقش اجرا می‌شود
۶. کار پس‌زمینه — realtime، hookهای زمان‌بندی‌شده
۷. رفتار زیر **بار واقعی** با چند کارمند همزمان
۸. چیدمان موبایل و رندر RTL
۹. اینکه **عددها درست‌اند** — sweep فقط می‌بیند رندر شده‌اند
