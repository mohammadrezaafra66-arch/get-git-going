# خط انتقال AfraKala — راهنمای کامل

> این سند برای دو خواننده نوشته شده: مالک، و هر هوش مصنوعی یا مهندسی که کار را تحویل می‌گیرد.
> هر ادعای این سند از اجرای واقعی ۲۳ شهریور ۱۴۰۵ (۲۰۲۶-۰۹-۱۴) آمده، نه از طراحی.
> نسخه: ۱ · تاریخ: ۲۰۲۶-۰۹-۱۴ · آخرین release موفق: `a935be0b`

---

## ۰ · چرا این خط انتقال وجود دارد

روز ۲۲ شهریور ۱۴۰۵ یک image که روی **کامپیوتر تست** ساخته شده بود روی **لپ‌تاپ production** مستقر شد. آدرس Supabase در زمان build داخل باندل جاوااسکریپت پخته شده بود، پس مرورگر هر کارمند به `http://192.168.170.8:9000` — یعنی Kong ماشین **تست** — وصل شد.

حدود ۹۰ دقیقه، پرسنل روی دیتابیس تست **می‌خواندند و می‌نوشتند**.

فایل `.env.lan` روی production تمام مدت **درست** بود. مقادیرش build arg بودند و deploy با `--no-build` انجام شد، پس هرگز اعمال نشدند. هیچ چکی به **داخل image** نگاه نکرد.

**درس مرکزی:** هر ادعا باید روی همان سطحی سنجیده شود که کاربر تجربه می‌کند. یک فایل env درست، یک باندل غلط را نجات نمی‌دهد.

## ۲ · جریان کار، از ابتدا تا انتها

```
توسعه روی تست
      ↓
شاخهٔ feature/*  →  push به GitHub
      ↓
merge به staging  →  fast-forward به main
      ↓
ساخت بستهٔ release روی تست، از main
      ↓
اثبات artifact قبل از اینکه بسته ماشین را ترک کند
      ↓
کپی بسته به \\192.168.170.8\dumps\release-<date>\
      ↓
اجرای runbook روی production، بلوک به بلوک
      ↓
امضای دستی مالک در مرورگر
```

**production هرگز build نمی‌کند.** فقط یک image از پیش ساخته‌شده را load می‌کند.

## ۳ · قاعده‌های غیرقابل مذاکره

۱. **توسعه هرگز روی `C:\afrakala`.** آن checkout تولید است. ویرایش کد آنجا یعنی توسعه روی production.
۲. **هرگز `--squash` برای رفتن به `main`.** مسیر: `feature/*` → `staging` → fast-forward به `main`.
۳. **`--no-deps` در هر `docker compose up`.** بدون آن کل استک پایین می‌آید.
۴. **`git pull` قبل از `up -d`.** compose قدیمی مقادیر runtime را پاس نمی‌دهد.
۵. **بعد از هر مهاجرت: `docker restart afrakala-lan-rest`.** PostgREST فقط در startup schema را می‌خواند.
۶. **SQL فارسی فقط با `docker cp` + `psql -f`.** هرگز از pipe پاورشل.
۷. **خروجی ترمینال فقط انگلیسی.** فارسی در ترمینال برعکس می‌شود.
۸. **هر exit code روی خط خودش از `$LASTEXITCODE`.** هرگز از `$?`، هرگز از داخل pipe. (`cmd | head` کد خروجی `head` را می‌دهد — این اشتباه سه بار در سه روز تکرار شد.)
۹. **بدون `&&`، `||`، ternary و `??`.** PowerShell 5.1 هیچ‌کدام را ندارد.
۱۰. **بدون double quote داخل رشتهٔ single-quoted `sh -c`.** پاورشل ۵٫۱ آن را می‌بُرد.
۱۱. **رول‌بک image از پیش مجاز است. رول‌بک دیتابیس هرگز.**
۱۲. **هرگز ردیف لجر برای مهاجرتی که اجرا نشده.** این دقیقاً باگ ۵۲۶ بود.

## ۴ · مکانیزم runtime config — قلب کار

### مشکل

`vite.config.ts` با `define` مقدار `import.meta.env.VITE_SUPABASE_URL` را در زمان build با یک رشتهٔ ثابت جایگزین می‌کرد. یعنی آدرس ماشین سازنده داخل باندل می‌پخت.

### راه‌حل

`src/lib/runtime-config.ts` مقادیر را در زمان اجرا از محیط کانتینر می‌خواند. `src/routes/__root.tsx` آن‌ها را به‌صورت `window.__APP_RUNTIME_CONFIG__` داخل `<head>` تزریق می‌کند، **پیش از هر chunk جاوااسکریپت**.

ترتیب خواندن آدرس:
```
APP_SUPABASE_PUBLIC_URL  →  VITE_SUPABASE_URL  →  SUPABASE_URL
```

### چهار مقدار runtime

| کلید | معنی |
|---|---|
| `APP_SUPABASE_PUBLIC_URL` | آدرسی که **مرورگر** به آن می‌رسد |
| `SUPABASE_PUBLISHABLE_KEY` | کلید anon |
| `VITE_APP_ENV` | `production` یا `test` — بنر را کنترل می‌کند |
| `VITE_TRUSTED_HOSTS` | میزبان‌های مورد اعتماد — بنر قرمز را کنترل می‌کند |

### نتیجه

**یک image، روی هر ماشین درست.** همان باندل روی تست بنر زرد می‌دهد و روی production نه — چون `.env.lan` هر ماشین متفاوت است.

### دام

`SUPABASE_URL` روی هر دو ماشین `http://kong:8000` است — نام داخلی شبکهٔ Docker. **هیچ مرورگری آن را resolve نمی‌کند.** اگر `APP_SUPABASE_PUBLIC_URL` خالی باشد، کد به آن می‌افتد و همهٔ صفحه‌ها خالی بالا می‌آیند. `GATE D10` دقیقاً این را می‌گیرد.

## ۵ · دروازه‌ها

هر دروازه یک ناحیهٔ `& { ... }` است. **کل ناحیه را یکجا paste کن**، از خط `& {` تا آکولاد بسته.

یک دروازهٔ شکست‌خورده `GATE <id> FAIL <reason>` چاپ می‌کند، `throw` می‌زند، و **پنجره را نمی‌بندد**. شکست در `$global:AFRAKALA_FAILED_GATES` ثبت می‌شود و هر ناحیهٔ بعدی که وضعیت را تغییر می‌دهد، `NOT RUN` چاپ می‌کند و اجرا نمی‌شود.

**این رکورد فقط در همان پنجره زندگی می‌کند.** پنجرهٔ جدید = دروازه‌ها را از اول بزن.

| دروازه | چه چیزی را اثبات می‌کند | چرا وجود دارد |
|---|---|---|
| **PULL** | checkout روی `main` است، تمیز است، و به build sha fast-forward شده؛ compose مقادیر را در runtime پاس می‌دهد | بدون pull، compose قدیمی بنر تست می‌دهد حتی با image درست |
| **D1a** | `HEAD` برابر build sha، درخت تمیز | ۲۲ شهریور، release از commit اشتباه اجرا شد |
| **D1b** | هر فایل مهاجرت مجموعه روی دیسک هست | ۲۲ شهریور، ۱۱ از ۱۴ فایل غایب بود و run تا بلوک ۶ رفت |
| **L1** | لجر دقیقاً همان است که سند برایش emit شده؛ دیتابیس replica نیست | اگر دیتابیس بعد از emit تغییر کرده، سند دیگر معتبر نیست |
| **TAR** | tarball بایت‌به‌بایت همان است، در برابر **دو** هش مستقل | فایل خراب یا ناقص |
| **D2** | image **کانتینر در حال اجرا** به‌عنوان `:lan-rollback` تگ شد، **قبل** از جابه‌جایی `:lan`، و بعد از تگ دوباره از کانتینر خوانده شد | ترتیب قدیمی نام rollback را روی image جدید می‌برد — «رول‌بکی که به جلو می‌رود» |
| **LOAD** | image لود شد و `APP_GIT_SHA` درست را دارد | تگ tarball ممکن است با انتظار runbook نخواند |
| **D3** | `:lan` و `:lan-rollback` **id متفاوت** دارند | اگر یکی باشند، رول‌بک هیچ کاری نمی‌کند |
| **D6(i)** | **هیچ** literal میزبانی در باندل client نیست — default-deny | این همان چیزی است که ۲۲ شهریور کسی نسنجید |
| **D6(ii)** | `__APP_RUNTIME_CONFIG__` در باندل هست | بدون آن، client هیچ آدرسی ندارد |
| **D6(iii)** | image با محیط این هدف، آدرس این هدف را سرو می‌کند — **برابری دقیق** | زیررشته کافی نیست: `.10` داخل `.100` هست |
| **D9** | میزبان سرو‌شده از **مرورگر** قابل دسترس است | یک image تمیز `http://kong:8000` سرو کرد و همهٔ چک‌های ساختاری پاس شدند |
| **D10** | **سایت زنده**، بعد از deploy، آدرس درست را به مرورگر می‌دهد | D6/D9 کانتینر خودشان را می‌سنجند — probe از خودش می‌پرسد |

### D6(i) چطور کار می‌کند — default-deny

یک باندل minified نمی‌تواند «آدرس واقعی» را از «متن راهنما» تشخیص دهد؛ هر دو رشته‌اند. پس probe حدس نمی‌زند:

- **همیشه رد می‌شود:** IP literal · پورت صریح · نام بدون نقطه (`kong`, `localhost`) · پسوند خصوصی (`.local`, `.lan`, ...) · میزبان Supabase
- **متن راهنما** فقط به‌صورت **رشتهٔ دقیق** و تا **تعداد شمرده‌شده** مجاز است — اگر همان رشته به‌عنوان endpoint واقعی استفاده شود، رد می‌شود
- **هر میزبان دیگر** باید در فهرست بازبینی‌شدهٔ اشخاص ثالث عمومی باشد

**قاعدهٔ طلایی:** اگر D6 قرمز شد به‌خاطر یک عدد بالاتر از سقف، **سقف را بالا نبر**. اول بفهم چه چیزی آن occurrence جدید را وارد باندل کرد.

### شکاف‌های شناخته‌شدهٔ D6 — ثبت‌شده، بسته‌نشده

- آدرس به شکل عدد ده‌دهی (`3232279048`) یا هگز (`0xC0A8AA08`) رد می‌شود
- IP در **وسط** یک رشتهٔ بلندتر
- IPv6 خارج از یک URL با scheme

**قضاوت:** blocker نیست. حادثه **تصادفی** بود و مسیرهای تصادفی آدرس را به شکل URL یا `host:port` یا dotted-quad حمل می‌کنند — هر سه گرفته می‌شوند. این اشکال فقط با دست‌کاری عمدی قابل بهره‌برداری است، و کسی که دسترسی commit دارد راه‌های ساده‌تری دارد که هیچ اسکن متنی نمی‌گیرد (مثل `[192,168,170,8].join(".")`).

## ۶ · دو حالت release

### حالت معمولی — وقتی release مهاجرت دارد

نیازمند یک گزارش rehearsal با نتیجهٔ PASS است. `release/rehearse.ps1` دامپ production را روی یک دیتابیس یک‌بارمصرف بازیابی می‌کند و هر مهاجرت را اجرا می‌کند. ساعت‌ها طول می‌کشد.

### حالت `-ImageOnly` — وقتی دیتابیس از قبل جلو است

اگر مهاجرت‌ها خارج از release روی production اعمال شده باشند، چیزی برای تمرین نیست. به‌جای rehearsal، یک **فایل شاهد لجر** می‌گیرد و رد می‌کند مگر اینکه:

۱. فایل شاهد با شمارش ردیف و بالاترین نسخهٔ ثبت‌شدهٔ هدف بخواند
۲. هر فایل مهاجرت روی دیسک یا ردیف لجر داشته باشد یا **تصمیم ثبت‌شده**
۳. هیچ ردیف لجری بدون فایل نباشد

هیچ بلوک مهاجرت و هیچ نوشتن لجری emit نمی‌کند.

**هشدار:** این حالت روز ۲۳ شهریور نوشته شد و **هیچ بازبینی مستقلی ندیده**. بلوک‌های PULL، L1، TAR، LOAD، rollback و sign-off همه از آن می‌آیند.

## ۷ · دستورالعمل اجرا

### روی کامپیوتر تست — ساخت بسته

```powershell
cd D:\AfraKalaTest\app
git fetch --all --prune
git worktree add ../wt-release-<date> origin/main
# .env.lan را داخل worktree کپی کن — gitignored است و build بدون آن رد می‌شود
npm run typecheck          # انتظار: ۷۰ خطا در ۶ فایل — این baseline است نه regression
```

بعد `release/build.ps1` را اجرا کن. **زیر pwsh 7، نه ۵٫۱** — نقص شناخته‌شده.

سپس **قبل از اینکه بسته ماشین را ترک کند**، artifact را اثبات کن:
- باندل client و SSR را استخراج کن و literal های میزبان و JWT را بشمار
- image را با مقادیر production-shaped بالا بیاور و ببین چه سرو می‌کند
- همان را با مقادیر تست تکرار کن — **دو رفتار از یک image**
- D6 را روی یک باندل **خراب** بزن و ببین **شکست می‌خورد**

> **یک probe که هرگز شکست نخورده، هیچ‌چیز را اثبات نمی‌کند.**

### روی لپ‌تاپ production — اجرای runbook

یک پنجرهٔ PowerShell، `cd C:\afrakala`، هر بلوک به ترتیب، در **همان** پنجره.

هر خط `Expect:` را **حرف‌به‌حرف** مقایسه کن. اولین اختلاف یعنی توقف.

بلوک ۴ (deploy) **هیچ دروازه‌ای ندارد** — خروجی `docker compose` را خودت بخوان.

### رول‌بک

از پیش مجاز است، از لحظه‌ای که `GATE D2` پاس شد:

```powershell
docker tag afrakala-app:lan-rollback afrakala-app:lan; docker compose --env-file deploy/lan/.env.lan -f deploy/lan/docker-compose.yml up -d --no-deps --no-build web
```

بعدش تأیید کن: id کانتینر برابر id `:lan-rollback` باشد، و `/login` مقدار ۲۰۰ بدهد.

**رول‌بک دیتابیس هرگز از پیش مجاز نیست.**

## ۹ · دام‌های فنی

- **RLS روی SELECT خطا نمی‌دهد** — بی‌صدا صفر ردیف برمی‌گرداند. «داده‌ای نیست» هرگز اثبات نمی‌کند که policy کار می‌کند.
- **`CHECK` مقدار NULL را رد نمی‌کند.** یک کلید JSONB غایب یعنی NULL و مقایسهٔ NULL پاس می‌شود. `COALESCE(..., false)` و `IS DISTINCT FROM`.
- **`has_role` و `has_any_role` هرکدام دو overload دارند** و هیچ‌کدام قابل حذف نیست. فراخوانی از طریق `supabase.rpc()` خطای `PGRST203` می‌دهد.
- **`user_roles.role` از نوع TEXT است** روی دیتابیس زنده.
- **`npm run typecheck` حدود ۳ دقیقه** طول می‌کشد و baseline آن ۷۰ خطا در ۶ فایل است.
- **`npm run build` روی ویندوز شکسته است** — فقط داخل Docker.
- **بدون HTTPS:** `getUserMedia`، `crypto.randomUUID` و `crypto.subtle` کار نمی‌کنند.
- **`schema_full_export.sql` غیرقابل اتکاست.** از خروجی زندهٔ `pg_policies` و `pg_get_functiondef` استفاده کن.

## ۱۰ · قواعد کار با agent

اگر این سند را به یک هوش مصنوعی می‌دهی، این‌ها هم بخشی از آن است:

۱. **research و execution هرگز در یک قدم.** اول یک سند تحقیق فقط‌خواندنی، بعد یک پرامپت اجرا از روی یافته‌های تأییدشده.
۲. **هر کدی که چیزی را می‌سنجد، باید یک بار روی ورودی بد شکست بخورد.** چهار دور بازبینی روی همین پروژه **نُه probe شکسته** پیدا کرد در کدی که درست به نظر می‌رسید.
۳. **agent هرگز کار خودش را نمره نمی‌دهد.** بازبینی توسط نشستی که کد را ننوشته.
۴. **شواهد برچسب‌دار:** `cited` (file:line) · `quoted` (خطوط عیناً) · `measured` (دستور + خروجی + exit code) · `compared` (یک probe روی دو چیز).
۵. **هر ادعا بدون این‌ها یک assertion است** و باید همان‌طور برچسب بخورد.
۶. **بخش «آنچه تأیید نشد» نباید خالی باشد** مگر واقعاً همه‌چیز سنجیده شده باشد.
۷. **worktree جدا** برای هر agent موازی. صفر کار image. دیتابیس فقط‌خواندنی.
۸. **commit محلی بعد از هر قدم اثبات‌شده.** شاخه‌ها از پوشهٔ temp نه — پاک می‌شوند.
