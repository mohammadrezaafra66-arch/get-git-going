# طرح انتشار پروداکشن — مسیر مهمان (۴۲۰ + ۴۲۱ + گام‌های ۱ تا ۴)

> **طرح است، نه دستور اجرا. هیچ بخشی از این سند روی پروداکشن اجرا نشده و نباید بشود مگر با تأیید
> جداگانهٔ مالک.** تاریخ تدوین ۲۰۲۶-۰۹-۰۳، بر پایهٔ اندازه‌گیری روی سرور **تست**.

## آنچه منتشر می‌شود

| | |
|---|---|
| مایگریشن | **۴۲۰** (گسترش مجموعهٔ مجاز + `COMMENT`) و **۴۲۱** (اصلاح یک پیام) |
| فلگ | `VITE_FEATURE_QUOTE_CUSTOMER_PICKER` |
| کد | انتخابگر مشتری، دکمهٔ افزودن شماره، چک‌باکس تعهد، برچسب/فیلتر مهمان، نمایش استثنا، ثبت ردها |
| **منتشر نمی‌شود** | `VITE_FEATURE_QUOTE_IDENTITY_FROM_RECORD` — **خاموش می‌ماند** |

## ترتیب — و چرا این ترتیب

```
۱. سنجش پیش‌پرواز روی پروداکشن (فقط خواندن)
۲. تگ بازگشت روی ایمیج فعلی
۳. مایگریشن ۴۲۰ سپس ۴۲۱     ← دیتابیس اول
۴. فلگ در .env.lan          ← فقط بعد از اینکه دیتابیس آماده است
۵. بیلد و استقرار web
۶. تأیید دوشاهدی
```

**دیتابیس باید اول برود.** اگر کد پیش از مایگریشن مستقر شود، فروشنده چک‌باکس را می‌بیند، تیک
می‌زند، و سرور با «نوع تعهد یا تأیید انتخاب‌شده معتبر نیست» ردش می‌کند — یعنی یک بن‌بست کامل در
فروش حضوری.

**عکسش بی‌خطر است:** مایگریشن بدون کد هیچ رفتاری را عوض نمی‌کند. `guest_no_link` صرفاً یک مقدار
مجاز اضافه است که هیچ‌کس نمی‌فرستد. پس فاصلهٔ بین گام ۳ و ۵ امن است و می‌تواند هر قدر لازم باشد
طول بکشد.

**فلگ باید پیش از بیلد تنظیم شود.** Vite مقدار را در **زمان بیلد** درون باندل می‌گذارد؛ تنظیم
`.env.lan` پس از بیلد هیچ اثری ندارد.

## ۱. آنچه باید پیش از انتشار سنجیده شود — همه فقط خواندنی

| # | سنجش | چرا |
|---|---|---|
| ۱ | نام دیتابیس **`postgres`** است نه `afrakala` | این اشتباه یک بار رفت‌وبرگشت هزینه داشته |
| ۲ | `SELECT max(version) FROM supabase_migrations.schema_migrations` | باید ۴۱۹ را داشته باشد؛ اگر ندارد ۴۲۰ زودرس است |
| ۳ | تعریف فعلی `create_sales_quote_with_items` را با `pg_get_functiondef` بگیر و **ذخیره کن** | همان فایل، دستور بازگشت است. **اگر با تعریف تست فرق داشت، متوقف شو** — قاعدهٔ ۴ می‌گوید دیتابیس ممکن است تعریفی قدیمی‌تر از git داشته باشد |
| ۴ | `pg_get_constraintdef` برای `sales_quotes_exception_type_check` | باید همان سه مقدار باشد؛ اگر چهارتاست ۴۲۰ قبلاً رفته |
| ۵ | `owner / prosecdef / proconfig / GRANT`ها | مبنای مقایسهٔ پس از مایگریشن |
| ۶ | شمارش مقادیر `quote_exception_type` و `commitment_confirmed` | مبنای «قبل» |
| ۷ | تعداد مشتریان فعال بدون شماره | تصمیم دربارهٔ فلگ دوم به این عدد گره خورده |
| ۸ | `docker ps` — همهٔ `afrakala-lan-*` بالا، `db-role-fix` روی `Exited (0)` | |

روی سرور تست، مبنای «قبل» این بود: `accounting_approval` ۱۸ · `credit_shortfall` ۳ · `NULL` ۴۲ ·
`overdue` ۰ · `commitment_confirmed=true` ۰ از ۶۳ · مشتری فعال بدون شماره ۵۱ از ۸۶. **اعداد
پروداکشن متفاوت‌اند و باید جداگانه گرفته شوند.**

## ۲. نقاط بازگشت

| مرحله | بازگشت |
|---|---|
| پس از ۴۲۰ | `docs/release/420-rollback-create_sales_quote_with_items.sql` — **فقط تابع.** محدودیت گشاد بماند؛ بخش «بازگشت ۴۲۰ پس از نخستین سند مهمان» را ببینید. `COMMENT` بی‌ضرر است |
| پس از ۴۲۱ | `docs/release/421-rollback-create_sales_quote_with_items.sql` |
| پس از استقرار | **فلگ را خاموش کن و دوباره بیلد بگیر.** خاموش‌کردن بدون rebuild اثری ندارد — مقدار در باندل جاسازی شده |
| اضطراری | `docker start afrakala-lan-web` روی تگ بازگشت |

**بازگشت مایگریشن‌ها بدون بازگشت کد خطرناک است:** کدی که `guest_no_link` می‌فرستد به تابعِ
برگردانده‌شده، رد می‌شود. اگر لازم شد برگردید، **اول فلگ را خاموش و rebuild کنید، بعد مایگریشن**.

### بازگشت ۴۲۰ پس از نخستین سند مهمان — آزموده‌شده روی استیجینگ

**فقط تابع را برگردانید. محدودیت را باریک نکنید.**

**چرا:** تابع دروازه است، نه محدودیت. تابعِ برگردانده‌شده `guest_no_link` را در فهرست سفید خودش رد
می‌کند (`22023 نوع تعهد یا تأیید انتخاب‌شده معتبر نیست`)، پس هیچ سند تازه‌ای با آن مقدار نوشته
نمی‌شود. محدودیتی که از تابع گشادتر است هیچ دری باز نمی‌کند و اسناد موجود دلیل واقعی‌شان را نگه
می‌دارند.

**چرا نمی‌شود باریکش کرد:** به‌محض اینکه یک سند `guest_no_link` وجود داشته باشد، `ADD CONSTRAINT`
سه‌مقداری با `23514` می‌افتد. این روی استیجینگ **واقعاً رخ داد**:

```
ERROR:  check constraint "sales_quotes_exception_type_check" of relation "sales_quotes"
        is violated by some row
```

**پیش‌بررسی اجباری — فقط خواندنی، پیش از هر تلاشی برای باریک‌کردن:**

```sql
-- اگر خروجی ناصفر بود، همین‌جا متوقف شوید. محدودیت را باریک نکنید.
SELECT count(*) AS guest_rows FROM public.sales_quotes WHERE quote_exception_type = 'guest_no_link';
```

**ممنوع مطلق:** بازنویسی آن ردیف‌ها به مقدار دیگر (جعل رکورد حسابرسی) یا حذفشان (حذف داده). هر دو
با قواعد `CLAUDE.md` در تضادند و مسئله را حل هم نمی‌کنند.

## ۳. دستورها — الگو، برای اجرای دستی

```powershell
# ۲. تگ بازگشت
docker tag afrakala-lan-web:latest afrakala-lan-web:rollback-<date>
```

```bash
# ۳. مایگریشن — تحویل از stdin، md5 دوطرفه، تراکنش واحد
cat <mig>.sql | docker exec -i afrakala-lan-db sh -c 'cat > /tmp/m.sql'
docker exec afrakala-lan-db md5sum /tmp/m.sql      # باید با md5sum محلی برابر باشد
docker exec -e PGPASSWORD=$pw afrakala-lan-db psql -U supabase_admin -d postgres \
  -v ON_ERROR_STOP=1 --single-transaction -f /tmp/m.sql
docker exec -e PGPASSWORD=$pw afrakala-lan-db psql -U supabase_admin -d postgres -c \
  "INSERT INTO supabase_migrations.schema_migrations (version) VALUES ('20260903100000') ON CONFLICT DO NOTHING;"
```

> **`-d postgres`** — روی پروداکشن نام دیتابیس این است. و ثبت ردیف دفترچه در همان نفس، وگرنه
> کسی بعداً همان مایگریشن را دوباره اجرا می‌کند.

```powershell
# ۴+۵. فلگ، سپس بیلد. ترتیب مهم است.
# .env.lan باید با خط جدید تمام شود، وگرنه پرچم به متغیر قبلی می‌چسبد.
& "deploy\lan\scripts\check-env-file.ps1"; if ($LASTEXITCODE -ne 0) { throw }
$env:GIT_SHA = (git rev-parse --short HEAD)
$env:BUILD_TIME = (Get-Date -Format o)
docker compose --env-file deploy/lan/.env.lan -f deploy/lan/docker-compose.yml `
  up -d --no-deps --build web
```

`--no-deps` اجباری است و `GIT_SHA` باید روی خط فرمان باشد — بدون آن برچسب دروغ می‌گوید و تنها
بررسیِ «کد درست در حال اجراست» از کار می‌افتد.

## ۴. تأیید دوشاهدی — هیچ‌کدام به‌تنهایی کافی نیست

**ساختاری:**
```bash
docker exec afrakala-lan-web sh -c \
  "grep -ohE 'VITE_[A-Z_]+:\"[^\"]*\"' /app/.output/public/assets/*.js | sort -u"
```
باید `VITE_FEATURE_QUOTE_CUSTOMER_PICKER:"true"` را **به‌عنوان کلید مستقل** نشان دهد، و
`VITE_FEATURE_QUOTE_IDENTITY_FROM_RECORD` باید **خالی** باشد. اگر نام پرچم فقط داخل مقدار متغیر
دیگری دیده شد، پرچم خاموش است.

**رفتاری:** انتخاب مشتری ثبت‌شده → نام و شماره `readOnly` شوند و دکمهٔ قطع اتصال ظاهر شود؛ و برای
نقش فروش، دکمهٔ ثبت تا تیک‌خوردن تعهد غیرفعال بماند.

**و پس از آن:** شمارش مقادیر استثنا باید **دقیقاً** با «قبل» یکی باشد. مایگریشن‌ها هیچ داده‌ای
نمی‌نویسند؛ هر تفاوتی یعنی چیز دیگری اتفاق افتاده.

## ۵. آنچه عمداً منتشر نمی‌شود

- **`FEATURE_QUOTE_IDENTITY_FROM_RECORD` خاموش می‌ماند** تا وقتی «مشتری فعال بدون شماره» به صفر
  برسد. روی تست هنوز ۵۱ از ۸۶ است. روشن‌کردنش امروز یعنی فرستادن رشتهٔ خالی به تابعی که شمارهٔ
  ناتهی می‌خواهد — و ۵۹٪ پروندهٔ مشتریان غیرقابل‌فروش می‌شود.
- **اصلاح `src/lib/audit/index.ts`** — انتشار جدا، اولویت با مالک.
- **راه‌حل ب** — فقط طرح.
- **تریگر PII در `audit_logs`** — دست‌نخورده.

## ۶. ریسک‌های باقی‌مانده

- **زیرساخت تأیید ساختاری، خودش داخل همین ۱۵ کامیت است.** باندل امروزِ پروداکشن هیچ آبجکت
  `VITE_` درون‌خطی و هیچ `BUILD_ID` ندارد (بازبینی مستقل مالک، ۲۰۲۶-۰۹-۰۳، با `GET` عمومی روی
  `index-BzVUZMSo.js` و `_app.sales.quotes.new--Rd0ZTv1.js`). یعنی **پیش از build هیچ‌کس از بیرون
  نمی‌تواند درست‌بودن زنجیرهٔ پرچم روی پروداکشن را ببیند** — شاهد ساختاری تنها *پس از* نخستین
  استقرار در دسترس می‌آید. تا آن لحظه تنها بازرسی ممکن، بررسی محلی فایل `.env` روی همان ماشین است
  (بند «ه» اسکریپت پیش‌پرواز).
- سناریوی نقش فروش روی پروداکشن با مرورگر تأیید نشده؛ فقط شاهد og94 هست.
- شمارش ردهای ثبت‌شده «کف» است، نه شمارش کامل — پنج نقطهٔ کور در
  `docs/design/quote-refusal-logging.md`.
- ۴۲۰ محدودیت را `DROP` و دوباره `ADD` می‌کند. اتمیک است، ولی روی جدولی با ردیف بسیار زیاد،
  اعتبارسنجی دوباره وقت می‌گیرد — تعداد ردیف `sales_quotes` پروداکشن باید در پیش‌پرواز دیده شود.
